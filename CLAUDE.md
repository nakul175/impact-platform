## 1. What this is, and its true status

A multi-tenant monitoring, evaluation, learning and impact-reporting platform: from programme setup and governed indicator definitions, through evidence collection and independent review, to deterministic calculations, locked reporting periods, frozen report packages and controlled publication to named recipients. Public benchmark named in the BRD: TolaData. Non-goals: ledger/payroll, national ID/biometrics, clinical decisions, automatic causal proof, autonomous AI decisions, on-prem at launch (BRD 3.2).

Status is deliberately conservative and must stay that way in anything you write:

- Requirement ledger: 307 requirements (270 functional + 37 non-functional), **74 PARTIAL, 233 PENDING, 0 accepted**. PARTIAL means a bounded, tested subset exists. Nothing is "done".
- Roadmap Release 1 (tenant and user administration) is in progress; releases 2–16 are planned. A build number never means a roadmap release is accepted.
- Evidence: 353 application checks, 143 design-reference checks, 91 browser checks (nine groups), all on **fresh in-memory PGlite (PostgreSQL 17.5) with serialised transactions**. Native PostgreSQL, live identity provider, MFA, workers, email/SMS, backups, load and production operations are unqualified. One test (IT_018, expired offline grant) is deselected and is not a pass.
- Delivered end-to-end path: managed-tenant onboarding → recovery contact → initial admin access → reviewed renewal of that authority before it expires (v0.13) → reviewed grants → programme and manual measurement setup → manual observations → independent review → provisional calculation → period close (OFFICIAL snapshot) → internal report → named-recipient HTML/CSV publication with withdrawal.
- Not delivered at all: forms, offline/Android, participants, evidence repository, evaluation, finance, AI, privacy execution, migration tooling, public/anonymous publication, PDF/DOCX/XLSX, external delivery, background workers.

Never present PGlite evidence as concurrency evidence, a PARTIAL requirement as accepted, or a target-design section as implemented.

## 3. Domain vocabulary (the terms the code uses)

- **Tenant**: the security and data boundary; lifecycle Requested → Provisioning → Active → Suspended → Closing → Archived → Deleted. **Custody**: the owner's accountability for the tenant; never implies data access.
- **Identity → principal → membership → grant**: authentication is not membership, membership is not a grant, a role template is not authority. A **grant** names one capability, one scope, a purpose, start/expiry and issuer. **Delegation ceiling** (`grant_authority`): what an administrator may grant to others; you cannot delegate what is not delegable.
- **Capabilities** are named `<route>.read`, `<route>.draft.create`, `<route>.draft.edit`, or `<singular>.<verb>` (`observation.submit`, `workflow.approve`, `period.close`, `report.publish`). 219 capabilities in `packages/contracts/access-policy.json`; default DENY.
- **Programme** (Draft → Ready → Active; readiness checks gate Ready), **indicator definition** (a governed measurement contract; approved versions are immutable), **indicator instance** (pins a definition version to a programme with collector, independent reviewer and schedule), **collection plan/obligation** (expected submissions per period; the period's obligation snapshot is the coverage denominator).
- **Observation**: source record with `source_namespace` + `source_key` (stable business identity), event time, and an explicit **value state** (PRESENT, MISSING, NOT_COLLECTED, NOT_APPLICABLE, INVALID, UNDEFINED). A blank is never zero.
- **Calculated result**: PROVISIONAL until a **period close** promotes it to a separate OFFICIAL revision inside a locked **snapshot**. Corrections after close go through scoped, expiring **restatement** that creates a new snapshot version; nothing is overwritten.
- **Review**: single independent stage; the approver must be a different **natural person** (`natural_identity_id`) from every material author of the exact candidate revision. Aliases, second logins, groups and delegation never create independence.
- **Report package** binds an approved template and a locked snapshot; numeric narrative uses `{{binding}}` placeholders and bare numbers are rejected. **Controlled publication**: independently reviewed disclosure to named active recipients, immutable HTML/CSV artifacts, per-recipient download flag, access log, withdrawal (downloaded bytes are never "recalled").
- **Operation ID / expected revision**: every mutation carries `operation_id` (in the JSON body) and, for existing objects, `expected_revision`. Same ID + same payload → original receipt; same ID + different payload → `CONFLICT_OPERATION`; stale revision → `CONFLICT_VERSION`. Receipts last 7 days.
- **Recovery contact** (v0.12): a registered person the owner nominates, who consents with fresh assurance, approved by an independent platform operator. It is activation-readiness evidence only; it cannot reset accounts, assume custody or bypass an unavailable owner.
- **Authority renewal** (v0.13): owner proposal → second-administrator confirmation → independent operator approval extends the pinned delegation ceilings, administrative grants, assignments and the second administrator's membership before they expire. The proposal pins the current authority and its hash; anything revoked before is absent, anything revoked after fails approval with `AUTHORITY_CHANGED`. Expired authority cannot be renewed; administrator replacement and expired-authority renewal are deferred to Release 2 (SD-01).

## 4. Rules that must never be broken

Business rules (FSD; RULE01–26):
1. Deny by default; client-supplied IDs are selectors, never proof; missing and hidden resources both return `RESOURCE_UNAVAILABLE` 404.
2. Read, export, approve, publish and sensitive-field access are separate capabilities; export is not implied by read; custody never implies data access.
3. No self-approval; independence is by natural person; editing as a reviewer makes you an author; a stale approval never authorises a newer revision.
4. Approved records are immutable; material change is a new revision; audit is append-only.
5. Official numbers come only from approved, versioned, deterministic rules over approved source revisions. AI (when it exists) proposes; it never supplies official arithmetic.
6. Decimal arithmetic (strings in transport, NUMERIC(38,12) in storage, ≥50-digit intermediates); round half-up once at display (0–6 places); never sum displayed values; pooled percentage = Σnumerators/Σdenominators (50/100 + 1/10 → 51/110 = 46.36, never 30); zero denominator → UNDEFINED, never 0.
7. Coverage denominators come from the period's obligation snapshot, not current membership; zero expected is "not applicable", not 100 %.
8. Close requires every mandatory obligation approved, no blockers, unchanged sources since preview, and an independent decision; late data stays outside the snapshot.
9. Report approval and publication are separate decisions; a wider audience is a new disclosure.
10. Sensitive actions need authentication within the previous 300 seconds plus the configured assurance (ACR); token issuance time does not count, only `auth_time`.
11. Synthetic fixtures only; never commit credentials, keys, `.local/`, participant data or real personal data.

Engineering invariants (HLD/LLD/MIG; verified in code):
12. Every tenant table carries `tenant_id` in its primary key and every foreign key; every new tenant table gets `ENABLE` + `FORCE ROW LEVEL SECURITY` and the `tenant_fence` policy.
13. `set_config('impact.tenant_id', …, true)` is transaction-local and set before any tenant-table access; never session-level; never reuse a connection of uncertain state.
14. Runtime roles (`impact_app`, `impact_identity`, `impact_platform`, …) are NOLOGIN-derived, non-owner, NOBYPASSRLS; the API never holds the migration DSN or `impact_owner`; `store.py` refuses superuser/BYPASSRLS/owner connections in staging and production. Keep that guard.
15. `object_revision` is insert-only (privacy removal through `impact_privacy` under the `revision_removal_guard` trigger is the sole exception). Projections listed as insert-only in migration 0003 stay that way. `operation_receipt` is insert-once.
16. Head + revision + projection + audit event + outbox event + receipt commit in one transaction. No external call inside that transaction. An outbox or `platform_event` row is intent, never proof of delivery.
17. Take the tenant advisory lock (`pg_advisory_xact_lock(hashtextextended(tenant_id,0))`) before any tenant write, before resolving authority; respect the LLD lock order; never auto-retry semantic conflicts.
18. Snapshot members, `official_result_snapshot`, `report_package_binding` and publication artifacts are never re-pointed; corrections create new versions.
19. Server-owned fields (issuer, approver, author, scan state, epochs) never come from request bodies; every write DTO is closed (`additionalProperties:false`); unknown fields and duplicate JSON keys are rejected.
20. `impact_platform` stays inside the RESTRICTIVE object-type lists of migrations 0013/0014; app and identity roles can never create custody, delegation ceilings or recovery evidence (only `accept_custody`, `apply_initial_authority` and the control plane can).
21. Cursors are HMAC-signed, bound to tenant/principal/route/visibility, 15-minute TTL; no `total_rows`.
22. Migrations are additive, ordered, checksum-ledgered; never change a byte of 0001–0016; next is 0017; no destructive down migration.
23. Keep the "current implementation" versus "retained target design" split in every document you touch; a documentation edition is not a product run.

## 5. Architecture as built

`make dev` starts one process tree (`scripts/run.py dev`): PGlite via `tools/dev-db/server.mjs` on `127.0.0.1:55432` (database `impact_dev`; the server only serves the socket; `IMPACT_DEV_DB_PORT` overrides the port, `0` lets the OS choose, and the server reports the actual port in one JSON status line that `scripts/run.py` parses to build every connection string), then `scripts/migrate.py` over the wire (the single migration runner: checksum-ledgered migrations, then `specification/fixtures/seed.sql` when `tenant_root` is empty), then `scripts/bootstrap.py` (fixture grants, role templates, custody, platform operators, RS256 keypair, `passwords.json`), then uvicorn `impact_api.main:create_app` on `127.0.0.1:8000` serving the compiled React client from `apps/web/dist`. The Vite dev server cannot perform writes (Origin must equal `public_origin`); build first. Persistent state under `.local/dev/`; tests use `.local/test-<hex>/` in-memory; `--ephemeral` for a disposable demo.

Request path for a domain command (`apps/api/impact_api/main.py` → `service.py` → `store.py`):
1. Middleware: correlation ID, Host allow-list, 256 KiB body cap, security headers (CSP, no-store, nosniff, HSTS when HTTPS).
2. `auth.resolve`: bearer (RS256; iss/aud/azp/exp/iat; `auth_time`; identity-level `auth_not_before` cutoff) **or** cookie session (HttpOnly, 15 min idle / 8 h absolute, Origin + `X-CSRF-Token` HMAC on mutations). Both together → `CONFLICTING_IDENTITY`. Provider role claims grant nothing.
3. Contract validation against the schema referenced by `openapi.json` for the path and method; a route in code but absent from the regenerated contract fails.
4. Transaction on the app role: tenant advisory lock → `context(write=True)` (active tenant, principal, membership, current grants and group entitlements) → `authorize` (capability, scope, purpose, fresh assurance; state actions need a TENANT-scope purpose-less grant) → operation lock → receipt replay check → `load(lock=True)` and `expected_revision` check → handler → `store.write` → `store.audit` → receipt insert → commit.
5. Error envelope: `{code, message, retryable, correlation_id, permitted_actions, field_errors?, reason_code?}`; database serialisation/lock errors map to `CONFLICT_VERSION` 409; unknown errors to 503 without traceback.

Control-plane commands (`/v1/platform/*`, role `impact_platform`, modules `tenant_lifecycle.py`, `access_bootstrap.py`, `recovery_contacts.py`, `authority_renewal.py`) follow a parallel skeleton authorised by identity (owner / nominee / operator), not by `access-policy.json`, and commit `platform_event` + `platform_receipt` together.

Module map: `auth.py` identity; `store.py` context, RLS, authorisation, revisions, audit/outbox; `contracts.py` loads the generated JSON contracts; `domain.py` decimal rules and SUM/pooled-ratio calculation; `service.py` dispatcher, listing, submit/review, calculate, receipts; `measurement.py` readiness, plans, coverage; `changes.py` governed amendments; `period_governance.py` close/restatement; `reporting.py` packages, HTML/CSV, disclosure, publication; `work.py` invalidation, tasks, notices; `administration.py` and `workspace_administration.py` tenant administration; `account.py` preferences and sessions; `platform_security.py` control-plane helpers. Each feature has a `*_contracts.py` whose `augment()` generates schemas and policy rows at build time — the runtime never calls it.

Frontend: single React SPA (`apps/web/src/main.tsx` plus one file per area). Capabilities from `GET /v1/tenants/{t}/me/access` gate rendering; hidden buttons are never security. Mutations send `{operation_id, expected_revision?, data}`; the operation ID should live in a `useRef` for the life of a dialog so retries are exact. Review dialogs re-fetch the candidate and abort if its revision changed. Report exports use a CSP whose style hash is recomputed from `REPORT_STYLE` in `reporting.py`.

## 6. Data model and database security in brief

- `object_registry(tenant_id, object_id)` holds the head; `object_revision` holds immutable payloads (`payload_sha256`, `revision_number`, `predecessor`); 49 typed `<kind>_current` projections are upserted from payload keys and enforce kind through generated `<ref>_kind` columns and composite foreign keys. Adding a payload property without `ALTER TABLE <kind>_current ADD COLUMN` fails at runtime with sqlstate 42703 → 503.
- Observations are hash-partitioned 32 ways by tenant (`observation_p00`–`p31`, each with its own RLS policy).
- Roles (migrations 0001, 0013): `impact_owner` (migrations only), `impact_app`, `impact_worker`, `impact_identity`, `impact_sensitive`, `impact_privacy`, `impact_observer`, `impact_platform`. `auth_identity` is the only 0002 table without RLS; identity tables have no `tenant_id` and are reached only through `impact_identity`.
- SECURITY DEFINER functions (fixed `search_path`, `REVOKE FROM PUBLIC`, one grantee): `identity_tenants`, `member_natural_identity`, `accept_custody`, `lock_platform_operator`, `lock_deployment_qualification`, `quiesce_tenant`, `tenant_work_impact`, `apply_initial_authority`, `lock_recovery_identities`, `apply_authority_renewal`.
- Control-plane tables (0013–0016: `platform_operator`, `deployment_qualification`, `tenant_onboarding`, `platform_event`, `platform_receipt`, `tenant_access_bootstrap(+_applied)`, `tenant_recovery_contact`, `tenant_authority_renewal`) are readable only by `impact_platform`; app and identity roles cannot read `tenant_recovery_contact` or `tenant_authority_renewal`. `grant_authority` and `member_role_assignment` expiries are re-dated only by the SECURITY DEFINER `apply_authority_renewal`.
- Every migration: `BEGIN;` / `SET LOCAL ROLE impact_owner;` / DDL / `COMMIT;` (runners strip the outer BEGIN/COMMIT; keep exactly one of each; create new roles before `SET LOCAL ROLE`). Extend the `object_registry` type CHECK with the `pg_get_constraintdef`/`regexp_replace` DO-block used in 0006/0007/0008/0012.

## 8. How to change things

Add a domain action on an existing route:
1. In the feature's `*_contracts.py` `augment()`: add `<Name>Data` and `<Name>` schemas, the path with `x-capability`, and a policy row `{operation_id, method, path, capability, role_templates, purpose_required, fresh_assurance_seconds, audit}` (`work_contracts.action()` is the smallest template). Register new modules in `scripts/build_contracts.py`.
2. `python scripts/build_contracts.py` then `python scripts/export_implemented_api.py` (regenerates `openapi.json`, `access-policy.json`, `event.schema.json`, `openapi-platform.json`, `openapi-implemented.json`, `docs/API-INVENTORY.md`).
3. Register the action in `service.ACTIONS` (or route in `READ_ROUTES`/`WRITE_ROUTES`) and add the branch in `Service.command`; TENANT-scope requirement set if it is a state action. New object kinds need a migration extending the type CHECK and projection columns.
4. Give fixture actors the capability in `scripts/bootstrap.py` (hard-coded capability list) or live tests get 403.
5. Tests in `qualification/test_<area>.py` using `live`, `cmd/expect` (`test_live_application.py`) or `command/expect/signed/provision_identity` (`test_administration.py`): positive actor; `other_tenant` → 404; revoked → 401/404; wrong role → 403; self-approval → `INDEPENDENCE_REQUIRED`; stale revision → 409; exact retry identical; changed payload same ID → conflict; database assertions (one revision, audit, outbox, receipt) via `live.db()`. Browser: copy `tools/browser/recovery-check.mjs`, add a mode in `scripts/run.py` and the Makefile.
6. Docs together (the repository's governance rule): `docs/RELEASE-0.N.md` (title `vN — <feature>`; first line build/schema/API/ledger counts; sections Delivered, Contract and persistence, Limits, reproduction commands), `docs/IMPLEMENTATION.md`, `docs/QUALIFICATION.md`, `docs/NEXT-DELIVERY.md`, `docs/current/CURRENT-API-INVENTORY.md`, `docs/current/CHANGELOG.md`, `SCREEN-COVERAGE.csv`, `EXECUTION-REGISTER.csv`, `TRACEABILITY.csv`; add evidence paths to the matching group in `scripts/build_completion_ledger.py` and run `make ledger`. ## 9. Security model essentials

Evaluation order: identity → tenant Active → membership active/unexpired → exact capability grant → scope (TENANT or `scope_member`) → purpose/classification → fresh assurance → subject/policy epochs → natural-person independence → lifecycle/expected revision → audit. Sixteen operations are purpose-required and fail closed; 41 carry `fresh_assurance_seconds: 300` (invitations, grants, membership state, roles/groups/org units, ownership, period close/restate, publish, privacy, support, rotation). Fifteen fixed role templates (OWNER … EXTERNAL) are starting bundles; system templates are uneditable; custom roles are bounded by the creator's `grant_authority`. Threat register TH01–TH32: TH01–TH10, TH15, TH28, TH30 have local evidence; TH11–TH14, TH16–TH27, TH29, TH31, TH32 are entirely pending (no imports, files, connectors, workers, AI, support sessions, backups, SBOM, quotas). No penetration test, live MFA, restore drill or distributed revocation test has been run.

## 10. What comes next (Release 1 — Usable core)

Scope decision SD-01 (28 Sep 2026, `docs/DELIVERY-PLAN.md` §7) replaced the 16-stage family roadmap with three delivery releases; the ledger's own R1/R2/R3 requirement tags are untouched. Release 1 must make the product usable by one organisation on hosted infrastructure with real logins. Sequence: v0.14 native PostgreSQL qualification (separate login roles, upgrade path, native concurrency, restart persistence, restore drill, one migration runner, per-test signed tokens, regenerated fixture) → v0.15 live identity provider (Keycloak in CI, PKCE/nonce/ACR/MFA, logout and refresh-token revocation) → v0.16 worker, outbox dispatcher and email adapter (invitations, channel verification, notices) → v0.17 deployment package, secrets, logs, metrics, backups, first staging deployment → v0.18 results framework and planning → v0.19 indicator and calculation completion with golden corpus → v0.20 web forms → v0.21 import and data quality → v0.22 object store and evidence attachments → v0.23 PDF/XLSX/DOCX exports → v0.24 dashboards → v0.25 security and privacy P0 → v0.26 non-functional qualification and acceptance preparation. Deferred to Release 2: administrator replacement and expired-authority renewal, legacy tenant adoption, unavailable-owner recovery, lifecycle closure, access certification, organisation reorganisation, offline/Android, participants, evaluation, integrations, migration tooling. Release 3: AI, advanced analytics, finance. Owner decisions that gate v0.15–v0.17: hosting provider, identity-provider deployment model, email provider. Delivered in v0.13: reviewed extension of unexpired delegated authority.
