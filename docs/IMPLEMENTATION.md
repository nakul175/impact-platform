## Components and transaction design

`auth.py` establishes identity. `store.py` creates transaction-local database roles and tenant context, evaluates scopes, reads immutable revisions, writes current projections and records audit/outbox entries. `contracts.py` validates requests against the versioned JSON schemas. `service.py` implements measurement/domain commands. `administration.py` implements access changes; `period_governance.py` owns close/restatement reconciliation; `reporting.py` owns frozen-package reconciliation, deterministic rendering, disclosure validation, publication access and withdrawal; `work.py` owns personal visibility, durable calculation invalidation, safe notices and recalculation resolution. Their additive schemas and policies live in the matching contract modules, including `publication_contracts.py`. `identity_profile.py` normalizes verified email identifiers. `delivery.py` writes delivery intents (closed templates, sealed recipients, derived invitation links and channel codes); `worker.py` is the separate worker process and its SMTP and synthetic adapters; `worker_status.py` serves the operator heartbeat view. `domain.py` keeps numeric rules independent of persistence. `tenant_lifecycle.py`, `access_bootstrap.py`, `recovery_contacts.py` and `authority_renewal.py` implement the separately privileged control plane; `bootstrap_profile.json` freezes its reviewed capability catalogue. `main.py` exposes a bounded HTTP surface and serves the compiled web client.

The React client carries no bearer tokens in browser storage. It uses HttpOnly session cookies and keeps the CSRF token in memory. Forms retain an operation ID for retry; since v0.15 the work-centre recalculate/acknowledge and change-request submit controls do too, through `usePendingOperations` in `apps/web/src/operations.ts`, which keeps one identifier per pending action while its payload is unchanged and releases it on success (issue #18). Since v0.14 the work-centre and period-governance views re-run their loaders when the capability set arrives instead of loading once on mount. Server authorization runs independently of the visibility of buttons. An error after changing an already committed command requires reopening the form with a new operation ID; the server never silently changes the original receipt.

Every successful domain command commits these records together: current registry head and projection, immutable revision (notice acknowledgement, which changes no object content, records only the audit event, outbox event and receipt), audit event, reference-only outbox event and delivery marker, and an operation receipt. Since v0.16 a command that needs a message (an invitation, a notice, a recovery-channel request) also writes a `delivery.requested` outbox event and its `outbox_delivery` row with a channel, template and reference in that transaction; the row stays intent, and only the worker records an outcome. Workflow/calculation commands also commit their related candidate, workflow, decision, job, or lineage records in the same transaction. The receipt is retained for seven days. Exact retries return its original content after current access is checked; changed content under the same operation ID returns a conflict.

Tenant writes take an advisory lock to serialize domain changes within a tenant. This keeps a calculation source set consistent with this implementation's writes, but limits write throughput. The local PGlite runner additionally serializes database transactions because it exposes one backend. Neither mechanism is evidence of meeting enterprise concurrency targets. Since v0.14 the native-only suite races simultaneous approvals, exact and conflicting operation replays, two close reviews of one period, a renewal approval against a grant revocation, and reads beside a held tenant lock, and asserts one consistent outcome and the exact rows written; it does not race two edits of one record, exercise the lock order across objects under concurrent writers, use a connection pooler or run any load profile, so scale claims still need those.

Version 0.2 takes that lock before resolving current write authority, so a command waiting behind revocation re-evaluates the changed authority. Previously admitted reads and delivered bytes are not retroactively cancelled. Suspension/revocation cancels queued work, marks running jobs for cancellation and pauses active owned schedules. Since v0.16 a worker exists: it marks jobs whose cancellation was requested and that had not started as Cancelled (no job class is executed, so this was exercised with test-inserted jobs), never claims deliveries held by a suspension, and does not release them on reactivation; external side-effect interruption of a running job is still unproven, and reactivation does not resume work.

Sensitive administrative writes require both a trusted authentication timestamp within five minutes and the configured provider assurance class. Since v0.15 both are exercised against a live provider: a password-level session is refused every fresh-assurance operation, a TOTP session is accepted until 300 seconds after the provider's own `auth_time`, and the step-up is demanded by the provider. MFA enrolment completion, recovery and action-bound step-up remain unqualified. Sessions retain a verified-email snapshot; provider email changes and account recovery need lifecycle integration before production.

Reads combine current grants, classification, restriction state and RLS. Cross-tenant, missing and unavailable objects return the same resource-unavailable response. Cursors are HMAC protected, bound to the current tenant/principal/route/access state and expire after 15 minutes. Lists default to 50 and are capped at 100. Calculation inputs are capped at 10,000 and requests at 256 KiB. The new setup UI follows paginated results up to an explicit 500-record cap per type; legacy selectors display at most 100 choices and still need pagination. See RELEASE-0.3.md for other configuration limits.

## Live identity provider

Outside loopback development, identity comes only from the configured OpenID Connect provider. Since v0.15 that path is qualified against Keycloak 26.7.4, pinned by version and SHA-256 and started per run by `scripts/idp.py` in development mode with an in-memory database, using the qualification realm `tools/idp/qualification-realm.json` (public client `impact-web` with S256 PKCE, audience `impact-api`, no refresh tokens, 120-second access tokens, back-channel logout with a required session identifier, and a step-up browser flow mapping `urn:impact:acr:password` to level 1 and `urn:impact:acr:mfa` to level 2).

Sign-in: `/auth/login` stores a one-use state with the PKCE verifier and nonce, binds it to the browser with the `impact_oidc` cookie, and redirects with `code_challenge_method=S256`, `max_age=0` and the required ACR. `/auth/callback` consumes the state, then — outside any database transaction — exchanges the code (with HTTP Basic client authentication only when `client_secret` is configured), reads only the ID token (any access or refresh token in the response is discarded unread), verifies signature, issuer, audience, nonce and an optional `sid`, requires a provider `auth_time` within 300 seconds, resolves the identity by issuer and subject, and creates the session with the provider's `auth_time`, ACR/AMR, `sid` and the sealed logout hint. Fresh assurance is judged from that stored `auth_time`, never from token issuance. Bearer requests are verified through the provider JWKS and must carry `typ: Bearer`; provider role claims never grant anything.

Logout: `POST /auth/logout` revokes the session and, with a live provider and `end_session_url`, returns `logout_url` — the end-session endpoint with `client_id`, `post_logout_redirect_uri` and, when the sealed hint opens with the presented cookie, `id_token_hint`; the client sends the browser there. The hint is the ID token encrypted with AES-256-GCM under a key derived from the cookie secret and the session cookie value, which the database never stores. A logout with a dead session cookie revokes that row if it exists, deletes the cookie and returns the URL without a hint. `POST /auth/backchannel-logout` exists only with a live provider: it reads at most 16 KiB + 64 bytes of form body, verifies the logout token (RS256 via JWKS, header `typ: logout+jwt`, issuer, audience = client, `iat` within 300 s, `exp`, `jti`, the back-channel event, `sid`, no `nonce`), records `(issuer, jti)` once in `oidc_logout_token`, revokes the platform sessions of that provider session and subject, and writes a `session.provider_logout` security event for each; a replay or any invalid token is `LOGOUT_TOKEN_INVALID` 400.

What this does not establish: provider-side recovery, completion of MFA enrolment, key rotation, provider outage, the confidential-client path and a managed provider were not exercised; elapsed time is emulated by moving `auth_time` or the last activity back in the database; a bearer access token remains valid until `exp` after a provider logout; the `id_token_hint` travels in a URL query; the Host allow-list requires the provider to call the back-channel endpoint by the public hostname. The owner's identity-provider deployment-model decision is open.

## Results framework and planning

`apps/api/impact_api/planning.py` (contracts in `planning_contracts.py`) adds two governed kinds that follow the definition lifecycle — Draft → InReview → Approved | Returned | Rejected, Approved → Superseded — through the single independent review stage. A **framework** belongs to one programme; its nodes carry a stable `node_id`, a type (IMPACT, OUTCOME, OUTPUT, ACTIVITY), title, description, owner and the indicator instances placed on them. Every save refuses structural invalidity (duplicate node identity, orphan parent, containment cycle, a child above its parent's level, an indicator placed twice or from another programme, a duplicate exception, and in a child draft the removal of a node that places indicators in the approved baseline); these can never be excepted. `GET /frameworks/{id}/completeness` lists errors and warnings with rule, object and resolver; a warning (orphan node, unmeasured impact/outcome/output, programme indicator not placed) can be excepted with a reason and a review date not in the past, the server stamps `recorded_by` and `recorded_at`, and submission is refused with `FRAMEWORK_INCOMPLETE` while anything is unresolved. Approval appends to the insert-only `framework_baseline` register; a programme has one root baseline and each later change is a child draft that names the approved revision it supersedes and an effective date after it, so each revision is superseded at most once and a draft on a superseded base is refused.

A **target** belongs to one indicator instance and one period of the programme's calendar: VALUE, RANGE (inclusive bounds) or MILESTONE (label and due date in the period), a direction matching the kind, a basis (ORIGINAL, BASELINE, REVISED) and an explicit value state — only PRESENT carries a value, a blank is never zero (also a CHECK in 0019). Submission pins the indicator's approved definition revision; approval appends to the insert-only `target_binding` register per indicator, period and slot (TARGET, BASELINE or one milestone label). A revised target or a corrected baseline supersedes the approved one with a reason; the register keeps the chain. A locked period refuses new or revised targets (`PERIOD_LOCKED`); restated comparisons are not implemented.

`GET /programmes/{id}/targets-vs-actuals` pages by indicator (1–100 per page, signed cursor, optional `period_id`) and returns, per indicator and period with a target, a result or a snapshot, the approved target, baseline and milestones, the actual with its source, the progress and the placing framework nodes. OFFICIAL comes only from this programme's locked snapshot under the definition revision the target pins; otherwise the actual is PROVISIONAL from this programme's own calculations, or NONE; the seeded fixture OFFICIAL 46.36 (bound to no programme) is never attributed, and without result access the actual is withheld. Progress uses stored decimals: uncapped attainment, signed deviation for lower-is-better targets, inclusive ranges, `ASSESSMENT_REQUIRED` for milestones, Undefined for a zero target and for the percentage change from a zero or negative baseline (`NON_POSITIVE_BASELINE`), and `ARITHMETIC_OVERFLOW` on a single row rather than a failed read. A period close pins the approved target revisions and the governing framework revision (the latest baseline effective before the period ends) into the snapshot and its fingerprint; locked rows are placed by that pinned revision.

What this does not establish: FR-PLN-002/004/005/007/008/009, restated comparisons (FR-IND-004), status thresholds, disaggregated or cumulative targets, a per-exception acceptance record (the approver of the revision is the authority), a readiness gate on the framework, targets for the seeded WATER-A programme (it has no reporting calendar), or any concurrent planning writers (PGlite serialises transactions; the native run adds only the register fence test).

## Worker and delivery

The worker (`python -m impact_api.worker`, `apps/api/impact_api/worker.py`) is a separate process that reads only its own configuration (`IMPACT_WORKER_CONFIG_FILE` and `IMPACT_<FIELD>` variables), never the API's. On native PostgreSQL it connects as `impact_worker_login`, a member of exactly `impact_worker`, and with unprivileged connections required it refuses a superuser, BYPASSRLS, owner-member or foreign login at start. `make dev` starts one with the synthetic sink; `make worker` adds another.

Each iteration asks `impact.worker_tenants(at)` for the Provisioning, Active and Suspended tenants and their due counts, then per tenant, under the tenant advisory lock and a transaction-local tenant context, claims due rows with `FOR UPDATE SKIP LOCKED` (LEASED, owner, generation + 1, 60-second expiry, attempt + 1). Per row it renews the lease in its own transaction (fenced on owner and generation, only while live and not held), rechecks the intent — current invitation generation, pending challenge, active recipient — and builds the message; the adapter is called with no transaction open; the outcome is recorded by an UPDATE fenced on owner and generation, so a stale holder's outcome is refused. All lease, due and expiry comparisons use the database clock. Failures back off (`min(3600, 30·2^(attempts-1))·U[0.5,1)` s) and become DEAD after six claims or at once on a permanent class; intents that are no longer current become SUPERSEDED. IN_APP delivery commits the SENT state, a `notification_delivery` row and a consumer receipt together, so it is exactly once; email is at least once only when one send outlives a whole lease (the Message-ID is stable across retries). Only an error class is recorded.

Nothing secret is stored in the outbox: invitation links are re-derived with the invitation secret and sent only for the current generation; recovery codes are an HMAC of the challenge under `delivery_secret`, and only a differently keyed HMAC is kept; addresses are AES-256-GCM sealed and bound to tenant, template and reference. `delivery_secret` (48+ characters, distinct from the cookie and invitation secrets) is shared by the API and the worker and is mandatory in staging and production; without it invitations stay manual-only and channel requests answer `DELIVERY_NOT_CONFIGURED`. The SMTP adapter requires verified STARTTLS for any non-loopback host and refuses non-loopback hosts outside staging and production; staging and production require it (with an HTTPS public origin). Rows held by a suspension are never sent and not replayed on reactivation. For Active tenants the worker also records 14- and 3-day delegated-authority expiry reminders once per principal, instant and threshold, authored by the tenant's SERVICE principal (no identity, membership or grant), and cancels queued jobs whose cancellation was requested. Operators see heartbeats through `GET /v1/platform/workers` and the Workers panel.

What this does not establish: a real email provider, bounces, SPF/DKIM or outbound rate limits (only a plain loopback SMTP sink and the synthetic sink were used, so the STARTTLS and AUTH paths are unexercised); exactly-once email; execution of any job class; a narrowed `impact_worker` grant set (0003's broad grants remain); an operator re-queue for held or DEAD rows; delivery intents in `event.schema.json`. A compromised worker can mint invitation links for existing invitations (acceptance stays identity-bound).

## Native PostgreSQL posture

On native PostgreSQL the platform runs on five login roles provisioned outside the migration set by `scripts/provision_logins.py`: `impact_app_login`, `impact_identity_login` and `impact_platform_login` for the API's three connections, `impact_worker_login` for the worker (since v0.16) and `impact_migrator` for `scripts/migrate.py`, each NOINHERIT and NOBYPASSRLS, each a member of exactly one NOLOGIN privilege role and holding CONNECT on one database. The API assumes the privilege role with `SET LOCAL ROLE` inside every transaction as before; what is new is that `IMPACT_REQUIRE_UNPRIVILEGED_DB` (always on in staging and production) makes readiness and every transaction verify that the three connections are distinct unprivileged logins and refuse to serve otherwise with `PRIVILEGED_RUNTIME_CONNECTION`, `SHARED_RUNTIME_LOGIN` or `PLATFORM_NOT_CONFIGURED` — a reason code, never a login name — re-verified every 60 seconds and never cached after a refusal. The native runner hands the API process none of the fixture, migration or administrator connections, the login passwords or any libpq `PG*` variable, and the restart check asserts that from the process environment.

`scripts/migrate.py` is the only migration runner: PGlite and native PostgreSQL receive the same checksum-ledgered files over the wire, run as `impact_owner` unless a superuser runs them, and the PGlite server process no longer interprets migrations or the fixture. Native evidence lives apart from the PGlite evidence in `docs/evidence/native-application-tests.xml`, `native-qualification.json` and `native-restore-drill.json`; the PGlite counts in `application-tests.xml` never include a native result. Cookie sessions are read without a row lock and their activity timestamp is advanced at most every 30 seconds, so parallel requests on one browser session no longer serialise on the session row; the effective idle limit lies between 14.5 and 15 minutes of true inactivity and the eight-hour absolute limit is unchanged. The synthetic fixture was regenerated on 28 September 2026 to expire on 2027-09-01 (`fixture_version 2026-09-28`; 472 revision payloads re-hashed), and the qualification suite mints one signed token per actor on demand rather than at suite start. What native qualification has established, and what it has not, is recorded per requirement in COMPLETION-LEDGER.json (FR-SEC-003, FR-OPS-005, VF-DIN-002 and VF-DR-003 are PARTIAL on this evidence; VF-DR-002 is not, because only the API process is restarted and no component is interrupted during a write).

## Data and contract changes

The schema is nineteen additive, checksum-ledgered migrations; version 0.18 adds 0019, and the native run, the restore drill and the upgrade check (a populated schema-18 database, with populated framework and target projections, migrated to 19) each verified all nineteen SHA-256 values against the ledger in CURRENT-DATA-DICTIONARY.md. In execution order: 0001 creates the privilege roles and the owned schema; 0002 the domain tables; 0003 the tenant-table grants and forced row-level security; 0004 sessions, natural authorship, result bindings and receipt immutability; 0005 access administration; 0006 measurement configuration; 0007 governed amendments and responsibility reassignment; 0008 programme-period state, close/restatement state and immutable snapshot membership; 0009 append-only report-package bindings; 0010 immutable calculation-invalidation identity and per-recipient notice acknowledgement; 0011 controlled-publication timestamps, immutable publication artifacts and append-only access events; 0012 tenant-fenced group entitlements, unique organisation codes, session identifiers/assurance, identity preferences/security events/cutoff and the constrained custody-acceptance function (organisation moves are immediate and preserve history; future-effective impact planning is still open); 0013 the control-plane role and tenant onboarding; 0014 reviewed initial access and its applied marker; 0015 recovery contacts; 0016 the `tenant_authority_renewal` review table (one pending proposal per tenant), grants on it to the control-plane role only, and the constrained SECURITY DEFINER applicator `apply_authority_renewal`, which re-dates only the pinned delegation ceilings and administrative assignments after re-verifying state, deadlines, operator status, natural-person independence, tenant state and the original bootstrap marker; 0017 adds `web_session.provider_sid` (with a partial index) and `web_session.provider_logout_hint` (the sealed ID token, 29–16,412 bytes), both nullable and left NULL by development sign-in, and the identity table `oidc_logout_token(issuer, jti, expires_at, accepted_at)` with primary key `(issuer, jti)`, granted SELECT, INSERT and DELETE to `impact_identity` only and, like the other identity tables, without `tenant_id` or row-level security. No provider access or refresh token is stored. 0018 adds the dispatch columns of `outbox_delivery` (channel, closed template, reference and generation, sealed recipient, state PENDING/LEASED/SENT/DEAD/SUPERSEDED, lease owner/generation/expiry, next and last attempt, error class, completion; legacy rows keep a NULL channel and are never dispatched) and revokes UPDATE on it from `impact_app`; `notification_delivery`, `recovery_channel_challenge` (one pending challenge per contact) and `authority_reminder`, each with forced RLS; `tenant_recovery_contact.channel_verified_at/channel_challenge_id` with `UNIQUE(tenant_id, contact_id)`; the SECURITY DEFINER functions `enqueue_recovery_channel_delivery` (platform) and `worker_tenants` (worker); `worker_heartbeat` (no tenant data); SELECT on `member_invitation` and `grant_authority` for the worker; and a `tenant_work_impact` that counts only open dispatchable intents as unsent. 0019 adds the framework and target payload columns (`framework_current.effective_from/supersedes_revision/exceptions`, `target_current.indicator_id/milestone_label/due_at/supersedes_revision/reason`, typed kind columns and composite foreign keys), the CHECK `target_blank_is_not_zero`, and the insert-only registers `framework_baseline` and `target_binding` (forced RLS, `tenant_fence`, SELECT and INSERT for `impact_app` only, nothing for the control plane; each approved revision is recorded once and superseded at most once). The control-plane role's write surface on existing tables is unchanged since migration 0014 apart from `recovery_channel_challenge` and the two recovery-contact columns. The bytes of every applied migration are preserved.

Tenant-owned additions have forced RLS. Identity-directory and tenant-bound natural-person functions have fixed search paths and no PUBLIC execution privilege. The ordinary app role cannot manufacture custody or delegation authority, update/delete approved plan or snapshot bindings, mutate an approved report package or publication artifact, rewrite invalidation trigger identity, or read back the publication-access log. On native PostgreSQL these denials are now asserted under the provisioned login roles as PostgreSQL `insufficient_privilege` or an empty fenced result (`qualification/test_native_roles.py`), not only through the API.

## Development fixture adaptation

The original records and SQL under `specification/fixtures` are preserved. The explicit bootstrap appends revisions to correct these development mismatches:

- General fixture grants originally carry purpose `QUALIFICATION`. Non-purpose operations receive revised grants with that purpose removed; purpose-required grants remain constrained. No authorization bypass is added.
- Additive capabilities are provisioned as actual grant objects for matching fixture role templates. Runtime JWT roles still have no authority. Active managed fixture role templates receive immutable revisions when their capability bundles change; pinned pending invitations may require reissue.
- The seeded dataset-mode indicator receives a new manual definition revision and a new instance revision for this delivery. The original dataset definition and original official-result fixture remain intact.
- Seed content authorship is backfilled using only the exact preserved fixture revisions. Restarting the local runner does not turn later review decisions into content authorship.
- Access administration receives actual grants, six constrained role bundles and separately provisioned delegation ceilings for the synthetic administrator/owner. A designated custodian is recorded. The `invitee` identity has no membership before acceptance. Runtime role labels never create authority. Bootstrap does not restore revoked original or additive administrative capabilities.

Fixture loading is allowed only with an explicit flag and database names `impact_dev`, `impact_test` or `impact_test_<suffix>` (parallel disposable native databases). The local socket runs on loopback and uses development-only authentication assumptions. Every fixture grant, delegation ceiling, role assignment, platform operator and deployment qualification expires at `FIXTURE_EXPIRES_AT` in `scripts/fixture_support.py`, 2027-09-01 since the regeneration of 28 September 2026 (`fixture_version 2026-09-28` in `api-fixture.json`); `scripts/redate_fixture.py` is the only way to move it, re-hashing every changed revision payload, and `scripts/run.py` refuses to start within 90 days of expiry. No generated credentials, private keys or local data are shipped in the archive.

## Production release gates still open

This build must not be represented as enterprise-ready. Native PostgreSQL qualification now exists at CI scale (separate app/identity/platform/migrator logins, API restart, restore drill, schema-15 upgrade, native concurrency cases) on single-node ephemeral servers; still pending are a connection pooler, persistence across a database restart, narrowing the worker role's grants, hosting, and a backup regime with measured RPO/RTO. Other pending gates include a hosted or managed identity provider with MFA enrolment, recovery and key rotation (the live-provider qualification uses a development-mode Keycloak per run); a production email provider (bounces, SPF/DKIM, sending limits) and identity provisioning; remaining tenant-onboarding acceptance, renewal of expired authority, administrator replacement and unavailable-owner recovery; bearer access-token lifetime after provider logout (tokens are not revoked before `exp`); shared-device handling and draft timeout warnings; distributed rate limits; tested key rotation; encrypted managed artifact storage; secrets management; penetration testing; dependency/SBOM review; disaster recovery exercises; SLO/load tests; accessibility review; deployment/rollback automation; and the missing functional modules above. Implemented membership and controlled-publication lifecycles are not substitutes for that full identity and operational programme.

Staging/production configuration rejects development identity, fixture flags, local serialization and non-HTTPS identity endpoints. Runtime connections in staging and production, and anywhere `IMPACT_REQUIRE_UNPRIVILEGED_DB` is set, must be three distinct logins that are not superuser, BYPASSRLS or members of the schema owner; readiness and every transaction verify this and refuse with a reason code otherwise, so a platform DSN is required there. Those guards support future deployment; they do not replace completion of the release gates.

Staging/production also requires a distinct invitation signing secret of at least 48 characters and, since v0.16, a distinct delivery secret of at least 48 characters shared by the API and the worker (the worker additionally requires the SMTP adapter and an HTTPS public origin there). Key rotation is not automated: revoke and reissue pending invitations under a coordinated rotation procedure. Replacing the key alone does not revoke stored token hashes; retry-link regeneration requires the original key. See `RELEASE-0.2.md` through `RELEASE-0.9.md` for the access, measurement, amendment, period-governance, reporting, work-centre and controlled-publication increments and their bounded implementation profiles.
