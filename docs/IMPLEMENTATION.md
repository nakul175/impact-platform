# Implementation boundary · v0.14.0

Version 0.14 changes no contract and no schema. It qualifies the existing platform on native PostgreSQL the way it must be deployed: four provisioned login roles instead of one superuser session, a runtime guard that refuses privileged or shared database connections on every transaction, one migration runner for the embedded and the native database, an API restart persistence check, a backup and restore drill, a populated schema-15 to schema-16 upgrade check, native-only concurrency and login-role tests, a regenerated fixture (expiry 2027-09-01) and per-actor signed test tokens. Version 0.13 added reviewed renewal of unexpired delegated authority; version 0.12 added identity-bound recovery contacts. Read RELEASE-0.14.md and RELEASE-0.13.md for exact boundaries and COMPLETION-LEDGER.json for requirements (76 PARTIAL, 231 PENDING, 0 accepted of 307 at build 0.14.0; VF-DIN-002 and VF-DR-003 moved to PARTIAL on native evidence and VF-DR-002 stayed PENDING). There are 138 domain operations (API 1.10.0), 28 separately documented control-plane operations (API 1.3.0) and migrations through 0016. Release 1 and the full product remain incomplete.

Status: functional development delivery, qualified on 28–29 September 2026 (PGlite gate on 28 September; browser groups and the native PostgreSQL run on 29 September). This document distinguishes delivered behaviour from the complete design. The original specifications remain authoritative for the full product; this is an incremental implementation record, not a declaration that all requirements have been met.

## Components and transaction design

`auth.py` establishes identity. `store.py` creates transaction-local database roles and tenant context, evaluates scopes, reads immutable revisions, writes current projections and records audit/outbox entries. `contracts.py` validates requests against the versioned JSON schemas. `service.py` implements measurement/domain commands. `administration.py` implements access changes; `period_governance.py` owns close/restatement reconciliation; `reporting.py` owns frozen-package reconciliation, deterministic rendering, disclosure validation, publication access and withdrawal; `work.py` owns personal visibility, durable calculation invalidation, safe notices and recalculation resolution. Their additive schemas and policies live in the matching contract modules, including `publication_contracts.py`. `identity_profile.py` normalizes verified email identifiers. `domain.py` keeps numeric rules independent of persistence. `tenant_lifecycle.py`, `access_bootstrap.py`, `recovery_contacts.py` and `authority_renewal.py` implement the separately privileged control plane; `bootstrap_profile.json` freezes its reviewed capability catalogue. `main.py` exposes a bounded HTTP surface and serves the compiled web client.

The React client carries no bearer tokens in browser storage. It uses HttpOnly session cookies and keeps the CSRF token in memory. Forms retain an operation ID for retry, except the work-centre recalculate/acknowledge and change-request submit controls, which still mint a new identifier per click (issue #18, planned for v0.15 in DELIVERY-PLAN.md). Since v0.14 the work-centre and period-governance views re-run their loaders when the capability set arrives instead of loading once on mount. Server authorization runs independently of the visibility of buttons. An error after changing an already committed command requires reopening the form with a new operation ID; the server never silently changes the original receipt.

Every successful domain command commits these records together: current registry head and projection, immutable revision (notice acknowledgement, which changes no object content, records only the audit event, outbox event and receipt), audit event, reference-only outbox event and delivery marker, and an operation receipt. Workflow/calculation commands also commit their related candidate, workflow, decision, job, or lineage records in the same transaction. The receipt is retained for seven days. Exact retries return its original content after current access is checked; changed content under the same operation ID returns a conflict.

Tenant writes take an advisory lock to serialize domain changes within a tenant. This keeps a calculation source set consistent with this implementation's writes, but limits write throughput. The local PGlite runner additionally serializes database transactions because it exposes one backend. Neither mechanism is evidence of meeting enterprise concurrency targets. Since v0.14 the native-only suite races simultaneous approvals, exact and conflicting operation replays, two close reviews of one period, a renewal approval against a grant revocation, and reads beside a held tenant lock, and asserts one consistent outcome and the exact rows written; it does not race two edits of one record, exercise the lock order across objects under concurrent writers, use a connection pooler or run any load profile, so scale claims still need those.

Version 0.2 takes that lock before resolving current write authority, so a command waiting behind revocation re-evaluates the changed authority. Previously admitted reads and delivered bytes are not retroactively cancelled. Suspension/revocation cancels queued work, marks running jobs for cancellation and pauses active owned schedules. There is no worker implementation to prove external side-effect interruption, and reactivation does not resume work.

Sensitive administrative writes require both a trusted authentication timestamp within five minutes and the configured provider assurance class. Exact ACR enforcement is tested locally; live-provider MFA, enrolment, recovery and action-bound step-up remain unqualified. Sessions retain a verified-email snapshot; provider email changes and account recovery need lifecycle integration before production.

Reads combine current grants, classification, restriction state and RLS. Cross-tenant, missing and unavailable objects return the same resource-unavailable response. Cursors are HMAC protected, bound to the current tenant/principal/route/access state and expire after 15 minutes. Lists default to 50 and are capped at 100. Calculation inputs are capped at 10,000 and requests at 256 KiB. The new setup UI follows paginated results up to an explicit 500-record cap per type; legacy selectors display at most 100 choices and still need pagination. See RELEASE-0.3.md for other configuration limits.

## Native PostgreSQL posture

On native PostgreSQL the platform runs on four login roles provisioned outside the migration set by `scripts/provision_logins.py`: `impact_app_login`, `impact_identity_login` and `impact_platform_login` for the API's three connections and `impact_migrator` for `scripts/migrate.py`, each NOINHERIT and NOBYPASSRLS, each a member of exactly one NOLOGIN privilege role and holding CONNECT on one database. The API assumes the privilege role with `SET LOCAL ROLE` inside every transaction as before; what is new is that `IMPACT_REQUIRE_UNPRIVILEGED_DB` (always on in staging and production) makes readiness and every transaction verify that the three connections are distinct unprivileged logins and refuse to serve otherwise with `PRIVILEGED_RUNTIME_CONNECTION`, `SHARED_RUNTIME_LOGIN` or `PLATFORM_NOT_CONFIGURED` — a reason code, never a login name — re-verified every 60 seconds and never cached after a refusal. The native runner hands the API process none of the fixture, migration or administrator connections, the login passwords or any libpq `PG*` variable, and the restart check asserts that from the process environment.

`scripts/migrate.py` is the only migration runner: PGlite and native PostgreSQL receive the same checksum-ledgered files over the wire, run as `impact_owner` unless a superuser runs them, and the PGlite server process no longer interprets migrations or the fixture. Native evidence lives apart from the PGlite evidence in `docs/evidence/native-application-tests.xml`, `native-qualification.json` and `native-restore-drill.json`; the PGlite counts in `application-tests.xml` never include a native result. Cookie sessions are read without a row lock and their activity timestamp is advanced at most every 30 seconds, so parallel requests on one browser session no longer serialise on the session row; the effective idle limit lies between 14.5 and 15 minutes of true inactivity and the eight-hour absolute limit is unchanged. The synthetic fixture was regenerated on 28 September 2026 to expire on 2027-09-01 (`fixture_version 2026-09-28`; 472 revision payloads re-hashed), and the qualification suite mints one signed token per actor on demand rather than at suite start. What native qualification has established, and what it has not, is recorded per requirement in COMPLETION-LEDGER.json (FR-SEC-003, FR-OPS-005, VF-DIN-002 and VF-DR-003 are PARTIAL on this evidence; VF-DR-002 is not, because only the API process is restarted and no component is interrupted during a write).

## Data and contract changes

The schema is sixteen additive, checksum-ledgered migrations; version 0.14 adds none, and the native run, the restore drill and the upgrade check each verified all sixteen SHA-256 values against the ledger in CURRENT-DATA-DICTIONARY.md. In execution order: 0001 creates the privilege roles and the owned schema; 0002 the domain tables; 0003 the tenant-table grants and forced row-level security; 0004 sessions, natural authorship, result bindings and receipt immutability; 0005 access administration; 0006 measurement configuration; 0007 governed amendments and responsibility reassignment; 0008 programme-period state, close/restatement state and immutable snapshot membership; 0009 append-only report-package bindings; 0010 immutable calculation-invalidation identity and per-recipient notice acknowledgement; 0011 controlled-publication timestamps, immutable publication artifacts and append-only access events; 0012 tenant-fenced group entitlements, unique organisation codes, session identifiers/assurance, identity preferences/security events/cutoff and the constrained custody-acceptance function (organisation moves are immediate and preserve history; future-effective impact planning is still open); 0013 the control-plane role and tenant onboarding; 0014 reviewed initial access and its applied marker; 0015 recovery contacts; 0016 the `tenant_authority_renewal` review table (one pending proposal per tenant), grants on it to the control-plane role only, and the constrained SECURITY DEFINER applicator `apply_authority_renewal`, which re-dates only the pinned delegation ceilings and administrative assignments after re-verifying state, deadlines, operator status, natural-person independence, tenant state and the original bootstrap marker. The control-plane role's write surface on existing tables is unchanged since migration 0014. The bytes of every applied migration are preserved.

Tenant-owned additions have forced RLS. Identity-directory and tenant-bound natural-person functions have fixed search paths and no PUBLIC execution privilege. The ordinary app role cannot manufacture custody or delegation authority, update/delete approved plan or snapshot bindings, mutate an approved report package or publication artifact, rewrite invalidation trigger identity, or read back the publication-access log. On native PostgreSQL these denials are now asserted under the provisioned login roles as PostgreSQL `insufficient_privilege` or an empty fenced result (`qualification/test_native_roles.py`), not only through the API.

The additive API contract is version 1.10.0, with 138 implemented domain operations including access administration, measurement configuration, period governance, frozen internal reporting, controlled publication and personal recalculation work. The separate control-plane contract is version 1.3.0 with 28 operations (tenant lifecycle, initial access, recovery contacts and authority renewal). `openapi.json` still contains the broader design. Use `openapi-implemented.json` and `API-INVENTORY.md` for the implemented surface. Unsupported operations fail closed. Supplementary implemented routes are:

## Development fixture adaptation

The original records and SQL under `specification/fixtures` are preserved. The explicit bootstrap appends revisions to correct these development mismatches:

- General fixture grants originally carry purpose `QUALIFICATION`. Non-purpose operations receive revised grants with that purpose removed; purpose-required grants remain constrained. No authorization bypass is added.
- Additive capabilities are provisioned as actual grant objects for matching fixture role templates. Runtime JWT roles still have no authority. Active managed fixture role templates receive immutable revisions when their capability bundles change; pinned pending invitations may require reissue.
- The seeded dataset-mode indicator receives a new manual definition revision and a new instance revision for this delivery. The original dataset definition and original official-result fixture remain intact.
- Seed content authorship is backfilled using only the exact preserved fixture revisions. Restarting the local runner does not turn later review decisions into content authorship.
- Access administration receives actual grants, six constrained role bundles and separately provisioned delegation ceilings for the synthetic administrator/owner. A designated custodian is recorded. The `invitee` identity has no membership before acceptance. Runtime role labels never create authority. Bootstrap does not restore revoked original or additive administrative capabilities.

Fixture loading is allowed only with an explicit flag and database names `impact_dev`, `impact_test` or `impact_test_<suffix>` (parallel disposable native databases). The local socket runs on loopback and uses development-only authentication assumptions. Every fixture grant, delegation ceiling, role assignment, platform operator and deployment qualification expires at `FIXTURE_EXPIRES_AT` in `scripts/fixture_support.py`, 2027-09-01 since the regeneration of 28 September 2026 (`fixture_version 2026-09-28` in `api-fixture.json`); `scripts/redate_fixture.py` is the only way to move it, re-hashing every changed revision payload, and `scripts/run.py` refuses to start within 90 days of expiry. No generated credentials, private keys or local data are shipped in the archive.

## Production release gates still open

This build must not be represented as enterprise-ready. Native PostgreSQL qualification now exists at CI scale (separate app/identity/platform/migrator logins, API restart, restore drill, schema-15 upgrade, native concurrency cases) on single-node ephemeral servers; still pending are a connection pooler, persistence across a database restart, a worker login role (there is no worker), hosting, and a backup regime with measured RPO/RTO. Other pending gates include real OIDC/MFA; production email and identity provisioning; remaining tenant-onboarding acceptance, renewal of expired authority, administrator replacement and unavailable-owner recovery; provider-wide logout and refresh-token revocation; shared-device handling and draft timeout warnings; distributed rate limits; tested key rotation; encrypted managed artifact storage; secrets management; penetration testing; dependency/SBOM review; disaster recovery exercises; SLO/load tests; accessibility review; deployment/rollback automation; and the missing functional modules above. Implemented membership and controlled-publication lifecycles are not substitutes for that full identity and operational programme.

Staging/production configuration rejects development identity, fixture flags, local serialization and non-HTTPS identity endpoints. Runtime connections in staging and production, and anywhere `IMPACT_REQUIRE_UNPRIVILEGED_DB` is set, must be three distinct logins that are not superuser, BYPASSRLS or members of the schema owner; readiness and every transaction verify this and refuse with a reason code otherwise, so a platform DSN is required there. Those guards support future deployment; they do not replace completion of the release gates.

Staging/production also requires a distinct invitation signing secret of at least 48 characters. Key rotation is not automated: revoke and reissue pending invitations under a coordinated rotation procedure. Replacing the key alone does not revoke stored token hashes; retry-link regeneration requires the original key. See `RELEASE-0.2.md` through `RELEASE-0.9.md` for the access, measurement, amendment, period-governance, reporting, work-centre and controlled-publication increments and their bounded implementation profiles.
