# Current roadmap and next delivery

Release 1 — **Usable core** — is **in progress**. Build v0.20 added web forms: form versions with independent review and a publication register, bounded relevance and server-side validation, and submissions that become FORM-namespace observations with explicit value states inside the existing observation review (RELEASE-0.20.md); the next slice that needs no owner decision is v0.21 import and data quality, while v0.17 still waits on the hosting decision. Build v0.19 completed the P0 calculation methods, disaggregation and the golden corpus with its reconciliation harness (RELEASE-0.19.md); the next slice that needs no owner decision is v0.20 web forms, while v0.17 still waits on the hosting decision. Before it, build v0.18 added the results framework and planning — built ahead of v0.17, whose staging step waits on the hosting decision — following v0.16 (worker runtime, outbox dispatcher and email adapter), v0.15 (sign-in, step-up MFA and logout against a live identity provider) and v0.14 (native PostgreSQL qualification with separately provisioned login roles). On 28 September 2026 scope decision SD-01 reorganised the delivery sequence into three releases so that the first one is usable on its own by one organisation; the sequenced increments, the decision record and the quality backlog are in [DELIVERY-PLAN.md](DELIVERY-PLAN.md). A build number does not mean a release is accepted. The original 307-requirement ledger has 87 PARTIAL and 220 PENDING requirements (v0.20 moved FR-FRM-001, FR-FRM-002, FR-FRM-003 and FR-FRM-006 to PARTIAL; v0.19 moved VF-DIN-001 and FR-IND-006); none is declared fully accepted, and the ledger's own R1/R2/R3 requirement tags are unchanged by SD-01.

**v0.14 delivered (28–29 September 2026).** The platform now runs and qualifies on native PostgreSQL on four provisioned login roles (`impact_app_login`, `impact_identity_login`, `impact_platform_login`, `impact_migrator`; `scripts/provision_logins.py`), with a runtime guard (`IMPACT_REQUIRE_UNPRIVILEGED_DB`, always on in staging and production) that refuses privileged, shared or missing connections at readiness and on every transaction; one migration runner for PGlite and native; a two-phase API restart persistence check; a scripted backup and restore drill; a populated schema-15 to schema-16 upgrade check; 25 native-only login-role, session and concurrency cases; a fixture regenerated to expire on 2027-09-01; per-actor signed test tokens; cookie sessions read without a row lock; and the frontend loader fix behind the CI browser flake. Evidence: 354 passed / 27 skipped / 1 deselected on PGlite, 379 passed / 2 skipped / 1 deselected on PostgreSQL 16.13, restart, restore and upgrade checks PASS, 143 reference and 91 browser checks, and the CI native job on PostgreSQL 17.11 for commit c759e9e. Not delivered: persistence across a database restart, a connection pooler, a backup regime with retention and measured RPO/RTO (the drill is CI-scale), lock-order evidence across objects, any load profile, a live identity provider, hosting, and the Release 2 tenant-administration items (administrator replacement, renewal of expired authority, legacy adoption, unavailable-owner recovery, closure). VF-DIN-002 and VF-DR-003 moved to PARTIAL on this evidence; VF-DR-002 did not, because no component was interrupted during a write.

**v0.15 delivered (29 September 2026).** The platform runs against a live Keycloak 26.7.4 (pinned by SHA-256, development mode, in-memory database, started per run by `scripts/idp.py` with a qualification realm derived from the specification realm): the real authorization-code flow with S256 PKCE, state, browser binding and nonce; step-up from password to TOTP with fresh assurance measured from the provider's `auth_time`; disabled-account refusal; RP-initiated logout with a sealed `id_token_hint`; verified back-channel logout with a `jti` replay register (migration 0017); logout of dead sessions; bearer validation through the JWKS including the token type; the same suite on PGlite, on the native login roles and in CI; and backlog items #18, #19 and #22. Evidence: 372 passed / 43 skipped / 1 deselected on PGlite, 397 passed / 18 skipped / 1 deselected on PostgreSQL 16.13 with restart, restore and 16→17 upgrade checks PASS, 16 live-provider tests on PGlite and 16 on the native login roles, 2 live-provider browser checks, 143 reference and 91 browser checks. Not delivered: refresh tokens (none are issued; refresh-token revocation is replaced by not issuing them, for the owner to accept), provider-side recovery, MFA enrolment completion, key rotation, provider outage, the confidential-client path, a managed provider and hosting; bearer access tokens outlive a provider logout until `exp` (120 s in the realm). No requirement moved: FR-IAM-002, FR-IAM-003, FR-IAM-006 and FR-IAM-009 gained bounded evidence; VF-IAM-001 stays PENDING.

Evidence: 405 passed / 51 skipped / 1 deselected on PGlite, 437 passed / 19 skipped / 1 deselected on PostgreSQL 16.13 with restart, restore and 17→18 upgrade checks PASS, 16 + 16 live-provider tests, 143 reference, 93 browser and 2 live-provider browser checks. Not delivered: a live email provider, bounces, SPF/DKIM and outbound rate limits (only a loopback SMTP sink and the synthetic sink were used, so STARTTLS and AUTH are unexercised), exactly-once email (a send that outlives a whole lease can repeat), any worker-executed job class, narrowing of `impact_worker`'s migration-0003 grants, an operator re-queue for held or DEAD rows. The next planned slice is **v0.17, deployment package and operations** (container images, compose and Helm charts, secrets from the environment or a secret store, TLS, structured logs, metrics and alerts, scheduled backups with the restore runbook, a single version source, first staging deployment). Its packaging, logging and backup work can be built in CI, but its staging deployment is **blocked on the owner's hosting decision**. Meanwhile **v0.18, results framework and planning**, was built ahead of it and is delivered (branch `release/0.18-results-framework`, stacked on v0.16, migration 0019, its own pull request), and **v0.19, indicator and calculation completion**, is in progress on branch `release/0.19-indicator-calculation` (it takes migration 0020). v0.17 is waiting on hosting, not abandoned: it remains required for Release 1. The owner decisions still open are the hosting provider (gates v0.17 staging), the email provider (v0.16 was qualified against a local SMTP sink and a synthetic sink; real credentials are needed only at staging), the identity-provider deployment model (self-hosted Keycloak or a managed provider; evidence on the chosen provider needs the owner's accounts) and acceptance of the no-refresh-token substitution of v0.15.
