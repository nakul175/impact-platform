# QA 2026-10 — qualified degradation behaviour

Branch `qa/2026-10-degradation` from `integration/0.25` (build 0.25.0, schema 27), 1 October 2026. No version, schema, contract or policy change; no migration.

Scope: what the platform does when one dependency fails while the others stay healthy (VF-AVL-002 *Dependency degradation*, parent NFR-AVL-002: "AI, email, external data collection and BI failures shall be isolated where possible. Users shall see the affected function, stale data and queued actions. Core manual workflows shall remain available when their independent dependencies are healthy"; its failure rule: "Do not claim isolation when the failed dependency is actually required for the tested journey; declare that dependency"). The database and the identity provider are **required** dependencies of every authenticated journey: for them the claim tested is *fail closed, say so, recover without restart*, not isolation. AI, survey connectors and BI retrieval do not exist in this build and were not tested.

Evidence: `qualification/test_native_degradation.py` (six tests; five run on PGlite and natively, one is native-only and skips on PGlite with a stated reason) and one unit test in `qualification/test_evidence_unit.py`. The database, provider and store scenarios drive an in-process API (`impact_api.main.create_app` over the suite's own configuration, only the named fields changed) so the failing dependency can be controlled from the test: a TCP proxy in front of the suite database, a stub OpenID key-set/token endpoint, a store directory and an injected `fsync` failure.

Runs recorded on 1 October 2026:

- PGlite (`IMPACT_PORT=8347 scripts/run.py test --pytest-path qualification/test_native_degradation.py`): **5 passed, 1 skipped** (the native-only mid-write cut).
- Native PostgreSQL 16.13, private UTF8 cluster, empty `impact_test_deg`, API on the provisioned logins with `IMPACT_REQUIRE_UNPRIVILEGED_DB=1`, worker on `impact_worker_login` (`scripts/run.py test --native --skip-restart-check --skip-restore-drill --skip-upgrade-check --pytest-path qualification/test_native_degradation.py`): **6 passed**.
- Before the fixes (same PGlite command with `apps/` reverted): 2 passed, **3 failed** — no reason code on database or store failures, and a valid bearer token answered `401 AUTH_REQUIRED` during a provider outage.
- `make unit` 302 passed / 53 skipped; `make lint` clean.

## Defects fixed

- **D1 — database unavailability was indistinguishable from any other failure** (`apps/api/impact_api/main.py`). A refused, lost or shut-down connection answered a bare `503 SERVICE_UNAVAILABLE` and readiness gave no reason. Now `psycopg.OperationalError` with no SQLSTATE, class `08` or `57P01/57P02/57P03` answers `503` with `reason_code DATABASE_UNAVAILABLE` (readiness included, through the same handler). Behaviour was already fail closed; only the diagnosis changed.
- **D2 — a provider outage was reported as the caller's fault** (`apps/api/impact_api/auth.py`). With the key-set cache expired, a valid bearer token answered `401 AUTH_REQUIRED` (a client would re-authenticate, which cannot succeed), and a callback whose code exchange could not reach the provider answered 401 too. Now `PyJWKClientConnectionError`, an `httpx.TransportError` or a 5xx from the token endpoint answer `503 SERVICE_UNAVAILABLE` with `reason_code IDENTITY_PROVIDER_UNAVAILABLE` and a log line without detail. Refusal semantics are unchanged: no token is accepted without a verified key; a 4xx from the token endpoint (e.g. a wrong PKCE verifier) is still 401.
- **D3 — object-store failures surfaced as an unclassified exception** (`apps/api/impact_api/object_store.py`). An `OSError` from a write or a read reached the generic handler (bare 503, the error type logged as `unexpected failure`). Now `FilesystemObjectStore.put/get` map ENOSPC/EDQUOT to `OBJECT_STORE_FULL` and any other `OSError` to `OBJECT_STORE_UNAVAILABLE` (`FileNotFoundError` on read stays `OBJECT_MISSING`); the existing temporary-file cleanup is unchanged. The scan path already turned a store failure into a FAILED verdict (never CLEAN).

## Limits (not covered)

- No real database restart or crash: the proxy refuses or drops connections in front of a running server; PostgreSQL itself was never stopped, and no connection pooler exists.
- No live Keycloak outage: the provider scenario uses a stub key-set and token endpoint over the same `PyJWKClient` and `httpx` code paths; Keycloak was not stopped under `scripts/idp.py`. Bearer tokens therefore keep verifying for up to 60 s after the provider becomes unreachable (cache lifespan); a bearer token also outlives logout until `exp` (unchanged, TH06).
- No real full disk: ENOSPC is injected at `fsync`; no quota or read-only mount was exercised.
- SMTP: connection refusal only (rejection codes were already covered in `test_worker.py`); no real provider, no STARTTLS/AUTH.
- The user-facing side of NFR-AVL-002 ("users shall see the affected function, stale data and queued actions") is not met by these tests: the API returns reason codes, but no screen labels a degraded dependency (the operator Workers panel and `GET /v1/platform/metrics` show worker heartbeats and queue counts only). AI, survey-connector and BI dependencies do not exist.
- The error contract's `code` enum names `DEPENDENCY_UNAVAILABLE` but the implementation answers `SERVICE_UNAVAILABLE` (as everywhere since v0.1); not changed here.
