# v0.14 — Native PostgreSQL qualification

Build 0.14.0; schema 16 (no new migration); domain API 1.10.0 (138 operations) and control-plane API 1.3.0 (28 operations) unchanged. Roadmap Release 1 remains in progress. The ledger moves from 74 PARTIAL and 233 PENDING to **76 PARTIAL and 231 PENDING** requirements: VF-DIN-002 (concurrent change integrity) and VF-DR-003 (recovery testing and backups) gain bounded native evidence, VF-DR-002 (ordinary failure durability) stays PENDING, and none is declared fully accepted.

## Delivered

Until this build every recorded run of the live suite used one superuser session on embedded PGlite, or, in the single CI native run recorded for v0.13, the disposable superuser fixture connection. This increment makes the platform run and qualify on native PostgreSQL the way it must be deployed: on separate least-privilege login roles, with the API unable to hold any privileged connection, and with restart, backup-restore and upgrade behaviour measured rather than assumed.

**Provisioned login roles.** `scripts/provision_logins.py` is the cluster-level step that migrations must never contain. It creates or re-provisions four LOGIN roles — `impact_app_login`, `impact_identity_login`, `impact_platform_login` and `impact_migrator` — each `NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOBYPASSRLS NOREPLICATION`, each a member of exactly one NOLOGIN privilege role (`impact_app`, `impact_identity`, `impact_platform`, `impact_owner`; any other membership that accumulated is revoked), each with CONNECT on one database, and gives `impact_owner` CREATE on that database so that a non-superuser migration session can create the schema migration 0001 owns. The eight privilege roles are created only when absent and exactly as migrations 0001 and 0013 define them, so a fresh cluster can be provisioned before its first migration. Passwords arrive through `IMPACT_LOGIN_PASSWORD_APP/IDENTITY/PLATFORM/MIGRATOR` and are never printed. The script refuses to run unless the administrator connection is a superuser or holds CREATEROLE, ownership of the database and ADMIN OPTION on all eight privilege roles, verifies the resulting topology and, unless `--no-verify` is given, connects as each login to prove it can assume its own privilege role and none of the other seven. `--revoke-public-connect` (off by default) additionally revokes PUBLIC's default CONNECT on the database; without it any login of the cluster can still open the database, and the result reports `public_connect` either way.

**Runtime guard.** `IMPACT_REQUIRE_UNPRIVILEGED_DB` makes `Database.verify_topology()` run at `/health/ready` and before every transaction: the app, identity and platform connections must resolve to three distinct logins, none of them superuser, BYPASSRLS or a member of `impact_owner`. A verified topology is trusted for 60 seconds and then re-resolved; a refusal is never cached, is logged server-side with the login names, and reaches the caller as `SERVICE_UNAVAILABLE` 503 with only a reason code: `PRIVILEGED_RUNTIME_CONNECTION`, `SHARED_RUNTIME_LOGIN` or `PLATFORM_NOT_CONFIGURED`. Each transaction additionally re-checks the privilege flags of the connection it opens. Staging and production always require unprivileged connections and, because the check covers the platform connection, now fail readiness without a platform DSN. The flag, like `IMPACT_DEV_AUTH` and `IMPACT_DEV_DB_SERIAL`, accepts `1/true/yes/on` and `0/false/no/off` case-insensitively; any other spelling is a startup error rather than a silent false, and the configuration file must carry JSON booleans.

**One migration runner.** `scripts/migrate.py` is now the only migration runner for PGlite and native PostgreSQL alike; `tools/dev-db/server.mjs` only serves the embedded database on `IMPACT_DEV_DB_PORT` (55432 in `make dev`, a port chosen by the operating system in test and browser modes) and reports the actual port in one JSON status line that `scripts/run.py` parses to build every connection string. The runner gains `--until N` (apply versions up to N, still checksum-verifying every applied file), `--fixture-if-empty` for the persistent development database and `--json`; a superuser runs the files as written, any other session must be `impact_owner` or a member of it and runs as `impact_owner`. The fixture-target guard in `seed.sql`, `scripts/migrate.py` and `scripts/bootstrap.py` also accepts `impact_test_<suffix>` so that several disposable native databases can coexist on one server.

**Native runner and evidence separation.** `scripts/run.py test --native` (`make native`) provisions the four logins on the disposable database named by `IMPACT_FIXTURE_DSN` (with throwaway passwords unless `IMPACT_LOGIN_PASSWORD_*` are supplied), migrates as `impact_migrator`, loads the fixture as the superuser, and starts the API on the three runtime logins with `IMPACT_REQUIRE_UNPRIVILEGED_DB=1`. The API process environment contains neither `IMPACT_FIXTURE_DSN`, `IMPACT_MIGRATION_DSN`, `IMPACT_ADMIN_DSN` nor any `IMPACT_LOGIN_*` or libpq `PG*` variable; both restart phases read `/proc/<pid>/environ` of the running API and assert this, and that `config.json` names the three provisioned logins and never the fixture connection. Native results go to `docs/evidence/native-application-tests.xml`, `native-qualification.json` and `native-restore-drill.json`, never to the PGlite evidence files. After the suite the runner stops the API cleanly, starts a fresh process on the same database and configuration, runs the second restart phase, then the restore drill and the upgrade check, and merges all three into `native-qualification.json`.

**API restart persistence.** `qualification/test_native_restart.py` runs in two phases around that restart. Phase 1 writes a programme draft, an observation draft submitted for review and a cookie session, and records every identifier. Phase 2, on a process with a different PID, asserts that the exact retries return the identical receipts byte for byte, that the objects read back with unchanged revisions and a stale expected revision is still refused, that the cookie session and its CSRF token are still valid and a wrong token still refused, that readiness and the runtime manifest are unchanged, and that the database holds exactly the rows phase 1 left. Recorded: clean shutdown of the first process (PID 1428, stopped in 0.21 s), second process (PID 12381) ready in 0.81 s, both phases PASS.

**Backup and restore drill.** `scripts/restore_drill.py` dumps the database the suite just used with `pg_dump -Fc`, creates `<database>_restored`, restores it with `pg_restore --exit-on-error`, grants the provisioned logins CONNECT and `impact_owner` CREATE on the copy without touching any role or password, runs `scripts/migrate.py` against the copy as `impact_migrator` (which must apply nothing and find all 16 ledgered checksums in place) and verifies by direct query that the seeded OFFICIAL result 46.36 (51/110) is present in its seeded snapshot revision with the seeded payload hash, that every table of the `impact` schema holds exactly as many rows as the source, that every table is owned by `impact_owner`, that RLS flags, policies, SECURITY DEFINER functions and grants are identical to the source, and that `impact_app` reads nothing without a transaction-local tenant, exactly one tenant with one, and no control-plane table. The copy is dropped afterwards. Recorded on 29 September 2026 against PostgreSQL 16.13: dump 3,427,234 bytes in 0.45 s, restore in 1.56 s, 151 tables and 30,016 rows compared with no difference, all checks true, `credentials_altered: false`, PASS in 2.39 s.

**Upgrade check.** `scripts/native_upgrade_check.py` migrates a fresh database to schema 15 as the migrator, loads the fixture there (2 tenants, 507 revisions), applies 0016 as the migrator and verifies with direct queries that `impact.schema_migration` holds 16 rows with exactly the SHA-256 values ledgered in `CURRENT-DATA-DICTIONARY.md`, that the maximum version is 16, that the table 0016 adds exists and that the tenant and revision counts are unchanged; the counts are part of the failure condition. Recorded: PASS in 1.34 s, `data_preserved: true`.

**Native-only concurrency tests.** `qualification/test_native_concurrency.py` (11 cases) releases simultaneous requests through a barrier against the API on native PostgreSQL and asserts both the HTTP outcomes and the database rows: two independent reviewers approving one candidate revision (one 200, one `CONFLICT_VERSION`; one decision, one new revision each of candidate and workflow, one audit event, one outbox event, one receipt); the same command from two threads (both receive the original receipt; one revision, one receipt row); the same operation identifier with different payloads (one 201, one `CONFLICT_OPERATION`); two independent close reviews of one programme period (one OFFICIAL snapshot version, the other `INVALID_STATE` / `PERIOD_ALREADY_SNAPSHOTTED`); an operator's renewal approval raced against the owner revoking a pinned grant, five repetitions (three unbiased and one per forced order, winners recorded in the evidence: approval won the three unbiased races), where approval first leaves the later revocation with a stale revision (`CONFLICT_VERSION`) and revocation first fails the approval with `AUTHORITY_CHANGED` and moves no ceiling; ten parallel reads completing while a transaction holds the tenant advisory lock and a write queues behind it, with the negative control that a write held past `lock_timeout` is refused with `CONFLICT_VERSION` and no receipt; and eight threads of mixed writes on both fixture tenants with no deadlock recorded by PostgreSQL and no failure line in the API log. That last case is a no-regression smoke test, not lock-order evidence: every write serialises on its tenant's advisory lock and the two tenants share no rows.

**Login-role boundaries and sessions.** `qualification/test_native_roles.py` (11 cases) derives every expected denial from the GRANT and row-level-security statements of the migrations and asserts it as PostgreSQL `insufficient_privilege` (42501) or an empty fenced result: each login assumes exactly its own privilege role; `impact_app` cannot read the control-plane tables and sees nothing without a transaction-local tenant; `impact_identity` reads identity tables only; `impact_platform` inserts revisions of its RESTRICTIVE object types only and cannot re-date ceilings or assignments; `impact_migrator` runs the migration runner and a domain login cannot; the runtime guard refuses privileged and shared connections in-process for every transaction kind and through a second API process started on the app login for all three connections, with no login name in any response; and `--revoke-public-connect` admits a login without a grant before the revocation and refuses it after while the provisioned logins still connect. `qualification/test_native_sessions.py` (3 cases) sends ten parallel cookie-authenticated requests and requires 200 from all with no conflict, checks the 30-second activity-recording rule and the idle limit, and confirms a revoked session is refused in parallel. Behind it, `auth.resolve` no longer takes `FOR UPDATE` on `web_session` for every request and advances `last_seen_at` only when the stored value is older than 30 seconds, under a predicate so concurrent requests write once; the lag can shorten the effective idle window to between 14.5 and 15 minutes but never extend it, and login keeps its `FOR UPDATE` on `auth_identity`.

**Fixture regeneration and per-actor tokens.** `scripts/redate_fixture.py` moved the fixture expiry from 2026-12-01 to 2027-09-01: it first recomputed all 507 revision payload hashes in `seed.sql` (507/507 matched), then rewrote the expiry instant in 472 revision payloads (471 grants and the one external membership) and their projection columns, re-hashed each, rewrote `records.json`, moved `FIXTURE_EXPIRES_AT` in `scripts/fixture_support.py` and stamped `api-fixture.json` with `fixture_version 2026-09-28` and `fixture_expires_at`; `fixture_id` is unchanged. `scripts/run.py` refuses to start when the stamp and the constant disagree or when the fixture expires within 90 days, because the suites nominate contacts, initial access and renewals that expire up to 60 days out and must stay inside the fixture ceilings. `qualification/conftest.py` mints one RS256 token per actor on demand with `auth_time` now and reuses it for at most 60 seconds, so no fresh-assurance operation depends on how long the suite has run; the suite-start `IMPACT_TOKEN_*` tokens remain for the reference-v1 suite and the browser tooling. `test_administration.py::test_delegation_expiry_cannot_be_exceeded` no longer assumes where in the calendar the fixture ceiling lies, and `test_measurement.py` exposes its builder for reuse.

**Client and CI.** The personal work centre and the period-governance view now re-run their loaders when the capability set arrives, which is the root cause of the browser flake recorded as issue #24: a fast navigation on a slow runner rendered an empty view and the measurement browser check timed out waiting for the recalculation task. The `native-postgresql-gate` CI job now generates masked throwaway passwords, provisions the four logins as the `postgres` superuser, runs the suite on those logins followed by the restart check, installs the PostgreSQL 17 client tools from the PGDG repository after verifying the signing key's fingerprint, runs the restore drill with `IMPACT_PG_BIN` pointing at them, runs the upgrade check, and uploads the three native evidence files. A unit test covers the boolean-flag spellings.

## Contract and persistence

There is no contract or schema change. The 138 domain operations (API 1.10.0) and 28 control-plane operations (API 1.3.0) are unchanged, `openapi.json`, `openapi-implemented.json`, `openapi-platform.json` and `access-policy.json` are unchanged, and the readiness gate still requires schema version 16. Migrations 0001–0016 are byte-identical to the ledgered checksums: the native run verified all sixteen as `impact_migrator`, the restore drill verified them again on the restored copy, and the upgrade check verified them after applying 0016 to a populated schema-15 database.

What changes is the environment around the schema. Login roles are provisioned by `scripts/provision_logins.py` outside the migration set and carry the only credentials; `scripts/migrate.py` is the single runner, running as `impact_owner` unless a superuser runs it; the API is started only with the three runtime logins and refuses to serve when they are privileged, shared or incomplete. Evidence for the native run is separate from the PGlite evidence: `docs/evidence/native-application-tests.xml` (JUnit), `native-qualification.json` (login topology, migration, runtime manifest, suite summary with the renewal-race winners, restart check, restore drill, upgrade check) and `native-restore-drill.json` (the drill on its own). The PGlite files `application-tests.xml`, `reference-tests.json` and the nine `*browser-tests.json` files keep their meaning.

## Limits

Native evidence comes from PostgreSQL 16.13 in the development workspace (29 September 2026) and 17.11 in the GitHub Actions service container (28 September 2026, commit c759e9e). Both are single-node, ephemeral servers reached over loopback, with no connection pooler, no replica and no persistence exercised across a *database* restart: only the API process is restarted, so nothing here is evidence that a database failure or an interrupted write preserves an acknowledged receipt, which is why VF-DR-002 stays PENDING. No live identity provider, MFA, email, worker or hosting exists; nothing was deployed.

The restore drill is a CI-scale drill of a disposable qualification database (a 3.4 MB dump), not a backup regime: there is no scheduled backup, retention window, off-site or immutable copy, protection against alteration or credential compromise, monthly restore cadence, quarterly disaster exercise, key recovery, attachment integrity or deletion/restriction replay before reopening, and no RPO or RTO is established. The upgrade check exercises only 0015 → 0016, which adds a table and a function and alters no populated table; it is not evidence for a migration that rewrites data. The mixed-write concurrency case is a no-regression smoke test; the LLD lock order across objects has no concurrent-writer test, and no load profile was run. Two concurrent edits of one record, repeated import commands and interrupted bulk jobs, named in VF-DIN-002, are not raced (no import or bulk job exists).

`--revoke-public-connect` is off by default, so PUBLIC keeps CONNECT on the database unless the administrator uses it; the disposable qualification clusters share their database with the superuser fixture connection. `/health/ready` exposes the topology reason codes (no secrets, no login names) to unauthenticated callers, as it already exposed a bare 503 for a schema-readiness failure. With the flag set, the topology check adds one privilege query to every transaction and one round of three connections every 60 seconds. Administrator replacement, renewal of expired authority, legacy tenant adoption, unavailable-owner recovery and lifecycle closure remain deferred to Release 2 under SD-01.

## Reproduction

Native: with an empty disposable database and a superuser connection to it, `IMPACT_FIXTURE_DSN=postgresql://postgres:<password>@127.0.0.1:5432/impact_test make native` (optionally `IMPACT_ADMIN_DSN`, `IMPACT_LOGIN_PASSWORD_*` to choose the login passwords, `IMPACT_PG_BIN` when the `pg_dump` on PATH is older than the server; `--skip-restart-check`, `--skip-restore-drill` and `--skip-upgrade-check` through `.venv/bin/python scripts/run.py test --native`). Local: `make lint build test reference browser`. Continuous integration: jobs `local-reference-and-browser` and `native-postgresql-gate` in `.github/workflows/qualification.yml`.
