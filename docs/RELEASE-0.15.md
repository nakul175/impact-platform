# v0.15 — Live identity provider

Build 0.15.0; schema 17 (migration 0017); domain API 1.10.0 (138 operations) and control-plane API 1.3.0 (28 operations) unchanged. Roadmap Release 1 remains in progress. The ledger stays at **76 PARTIAL and 231 PENDING** requirements (0 accepted of 307): FR-IAM-002, FR-IAM-003, FR-IAM-006 and FR-IAM-009, already PARTIAL, gain bounded live-provider or policy evidence; FR-IAM-008 and FR-IAM-011 are unchanged; VF-IAM-001 (revocation time) stays PENDING because bearer access tokens outlive a provider logout until they expire and no revocation latency is measured.

## Delivered

Until this build every sign-in in every recorded run used the loopback development login or bearer tokens the test harness signed itself; the OIDC path in `auth.py` had never met a real provider. This increment runs the platform against a live Keycloak, drives the real browser flow end to end, and adds the logout half of the protocol that did not exist.

**Pinned Keycloak runner.** `scripts/idp.py` downloads Keycloak 26.7.4 once into `.local/keycloak/`, verifies the archive against the pinned SHA-256 `04823c336b797a7e18889a44262a7a64e6bf624cbbcc518c85e2622176ff2eee` before unpacking, and starts it in development mode on an operating-system-chosen loopback port with the in-memory H2 database (`--db=dev-mem`). Passwords, TOTP secrets and the throwaway administrator password are generated at every start and written only to `<local>/idp.json`, created with mode 0600; they are never printed and never reach the repository or the evidence. `scripts/idp.py fetch` (CI cache step), `realm` (regenerate the realm file) and `serve` (manual exploration; stops Keycloak on SIGTERM) are the entry points. Java 21 is required.

**Qualification realm.** `tools/idp/qualification-realm.json` is derived from `specification/environment/keycloak-dev-realm.json` (same users, subjects, enabled flags and e-mail addresses): the public `impact-web` client with S256 PKCE, the platform callback and post-logout redirect, back-channel logout to `<origin>/auth/backchannel-logout` with a required session identifier, no refresh tokens, an `impact-api` audience, a step-up browser flow (level 1 password, level 2 TOTP) with an ACR-to-level map (`urn:impact:acr:password` → 1, `urn:impact:acr:mfa` → 2), a 120-second access-token lifespan, and the provider roles `OWNER` and `TENANT_ADMIN` given to the author so the platform can be shown to ignore them. A second realm of the same provider, `impact-foreign`, carries the same client and an author user (Keycloak user identifiers are unique across realms, so its subject is derived from the author's); its tokens must be refused. The bootstrap re-points the fixture identities whose subjects exist in the realm to its issuer; identity identifiers, natural persons, memberships and grants stay exactly as the fixture defines them.

**Authorization code with PKCE and nonce, for real.** `qualification/test_live_idp.py` (16 cases) drives the flow over HTTP the way a browser does: `/auth/login` redirects to the provider with `code_challenge_method=S256`, `max_age=0`, `acr_values=urn:impact:acr:mfa`, state and nonce; the provider's login and TOTP forms are completed; `/auth/callback` exchanges the code and sets the session. A replayed state, a second browser without the `impact_oidc` binding cookie and a forged binding cookie are refused without consuming the state of the browser that started the sign-in. An injected authorization response (a code minted for the platform's PKCE challenge and state but a different nonce) passes the provider's PKCE check and fails the platform's nonce check, while the same crafted request with the stored nonce succeeds. A code bound to one challenge is refused by the provider with another verifier or none (`invalid_grant`), and a code delivered to another attempt's state is exchanged with that attempt's verifier and refused. A disabled provider account cannot sign in. Nonce replay is covered through the single-use state record: a consumed state cannot deliver its nonce twice.

**Step-up assurance and fresh authentication by the provider's clock.** A session whose provider authentication is level 1 (the user agent drops `acr_values`) reads normally but is refused every fresh-assurance operation, tenant and account alike; an unmodified sign-in makes the provider demand the second factor, and a user without one is sent to TOTP enrolment before any code is issued. After TOTP the session records `urn:impact:acr:mfa`, the provider's `sid`, and an `auth_time` the test proves equal to the ID token's own claim (recovering the ID token from the sealed logout hint). A fresh-assurance operation succeeds, and 301 seconds after the provider authentication it is refused with `FRESH_AUTHENTICATION_REQUIRED` while reads still work.

**Bearer tokens through the provider JWKS.** Access tokens are verified with the provider's published keys; issuer, audience (`impact-api`), authorised party, expiry and — new in this build — the token type are checked: only `typ: Bearer` is a bearer credential, so the ID token (audience `impact-web`, type `ID`) is refused as one. A tampered signature, a token signed with a key outside the provider's JWKS, a token from the foreign realm and a token past its expiry (realm lifespan lowered to 5 seconds for one token, 5-second leeway) are all refused with 401. The provider's `OWNER` and `TENANT_ADMIN` role claims confer nothing, through a bearer token or a session: the author still cannot invite members or grant capabilities and is neither operator nor owner.

**RP-initiated logout.** `POST /auth/logout` revokes the local session at once and, with a live provider, returns the provider's end-session URL with `client_id`, `post_logout_redirect_uri` (`<origin>/`) and `id_token_hint`. The hint is the ID token sealed with AES-256-GCM under a key derived from the cookie secret and the session cookie value, which the database never stores, so only a request presenting the session can unseal it. The platform sends nothing to the provider itself; the browser visits the URL, the provider ends its session without a confirmation page and redirects back, and a later `prompt=none` authorization request returns `login_required`. A logout of a dead session (idle or absolute timeout, revoked or unknown cookie) now clears the cookie, marks the row revoked and returns the end-session URL without a hint, instead of answering 401 and leaving the cookie; bearer requests and live sessions failing the Origin/CSRF check are refused as before.

**Back-channel logout.** `POST /auth/backchannel-logout` accepts a form body with exactly one `logout_token`, read through a bounded reader (16 KiB + 64 bytes; a chunked body beyond it gets 413 before any authentication) and answers 404 without reading anything when no live provider is configured. The token must be RS256-signed by a key in the provider JWKS, carry header `typ: logout+jwt`, the configured issuer, audience `impact-web`, `iat` at most 300 seconds old, `exp`, `jti`, the back-channel logout event, a non-empty `sid`, and no `nonce`. A valid token revokes exactly the platform sessions created from that provider session (and subject, when present), records a `session.provider_logout` identity security event per session, and records `(issuer, jti)` in the insert-once `oidc_logout_token` table in the same transaction; a replay of the same token is refused with the same `LOGOUT_TOKEN_INVALID` 400, and at most 100 records expired for more than five minutes are purged per call. Live: an administrator ending one of two provider sessions of the owner revokes exactly the matching platform session within the polling window while the other stays valid; ending all of the user's provider sessions revokes the rest. Unit level (`qualification/test_backchannel_logout.py`, 14 cases in the default and native suites, local RSA key and synthetic issuer): a valid token revokes once and its replay is refused; a nonce, stale `iat`, missing or empty `sid`, missing `jti`, missing `exp`, missing or wrong events, wrong audience, wrong issuer and a header type other than `logout+jwt` are each refused without revoking anything; expired replay records are purged.

**One runner, PGlite and native login roles, and CI.** `scripts/run.py test --idp keycloak` runs the live suite on PGlite (`docs/evidence/idp-tests.xml`); with `--native` it runs it on the provisioned app, identity and platform logins under `IMPACT_REQUIRE_UNPRIVILEGED_DB` exactly as in the native suite (`idp-native-tests.xml`), leaving the restart check, restore drill and upgrade check to the full native run. Both merge into `idp-qualification.json` under `runs.pglite` and `runs.native` with the provider version, distribution hash, realm, client, audience and required ACR. `scripts/run.py idp-browser --idp keycloak` drives Chromium through sign-in with the TOTP step and sign-out, waiting for the browser's own request to the end-session endpoint and proving with a `prompt=none` request that the provider session ended (`idp-browser-tests.json`, 2 checks). `make idp` runs both. The CI job `live-identity-provider` (Temurin 21, cached and verified distribution) runs the PGlite suite and the browser check; the `native-postgresql-gate` job gains a step that runs the live suite on its login roles in a separate empty database. Loopback providers are excluded from proxying by `NO_PROXY` in the runner; the code exchange otherwise honours the proxy environment as before. Outside development and test a plain-HTTP provider is refused, and within them it is allowed only on loopback.

**Backlog items closed.** #18: the work-centre recalculate and acknowledge controls and the change-request submit control now take their operation identifier from `apps/web/src/operations.ts` (`usePendingOperations`), which keeps one identifier per pending action while its payload is unchanged and releases it on success, so a retry after a lost response repeats the exact command; the measurement browser check was extended accordingly. #19: `scripts/build_contracts.py` drops policy rows whose operation is absent from the generated contract, which removes exactly the orphan `create_organisation_units` row (capabilities 219 → 218); custom roles accept only capabilities of the 138 implemented operations (84 delegable capabilities), refusing a design-only capability with `CAPABILITY_NOT_DELEGABLE` even inside the creator's delegation ceiling, at create and at revise (`test_workspace_administration.py::test_custom_roles_delegate_only_implemented_capabilities`). #22: `Service.command` resolves the request schema through `request_schema()`, so a route or method absent from the regenerated contract, or an operation absent from the policy, answers `RESOURCE_UNAVAILABLE` 404 before any database work instead of 503 (`test_unit.py::test_route_missing_from_contract_is_not_found`).

## Contract and persistence

Migration 0017 (`infrastructure/migrations/0017_provider_logout.sql`, SHA-256 `4378cafe2bacbf6266e0d18f5886966a29c0a53b2ba51566b7afc4c04c9c000b`, ledgered in CURRENT-DATA-DICTIONARY.md) adds two nullable columns to `web_session` — `provider_sid varchar(255)` with a partial index, and `provider_logout_hint bytea` (29 to 16,412 bytes) — and the identity table `oidc_logout_token(issuer, jti, expires_at, accepted_at)`, primary key `(issuer, jti)`, with SELECT, INSERT and DELETE granted to `impact_identity` only; like the other identity tables it has no `tenant_id` and therefore no row-level security. Development sign-in leaves both columns NULL. No provider access or refresh token is stored anywhere. Readiness now requires schema version 17. Migrations 0001–0016 are byte-identical to their ledgered checksums; the native run, the restore drill and the upgrade check each verified all seventeen, and the upgrade check now migrates a populated schema-16 database to 17 and verifies that the provider-logout columns and the replay table exist with tenants, revisions and sessions preserved.

There is no API contract change. The 138 domain operations (API 1.10.0) and 28 control-plane operations (API 1.3.0) are unchanged, `openapi.json`, `openapi-implemented.json` and `openapi-platform.json` are unchanged, and `/auth/*` routes remain outside the versioned contracts as before. `access-policy.json` loses one orphan row (306 → 305 rows, 219 → 218 capabilities); the 16 purpose-required and 41 fresh-assurance operations are unchanged. New configuration: `end_session_url` and `client_secret` (normally `IMPACT_CLIENT_SECRET`, at least 32 characters and only with a live provider, for a confidential client; the qualification client is public and leaves it empty). Evidence for the live provider is kept apart: `docs/evidence/idp-tests.xml`, `idp-native-tests.xml`, `idp-qualification.json` and `idp-browser-tests.json`; the default and native suites skip the 16 live cases with a stated reason.

## Limits

No refresh token is issued to the client and the platform holds none, so refresh-token revocation (planned for this slice) has been replaced by not issuing refresh tokens; the owner must accept that substitution. Provider-side account recovery, completion of MFA enrolment (the test stops at the enrolment page), signing-key rotation, provider outage, the confidential-client path (`IMPACT_CLIENT_SECRET`) and a managed provider were not exercised. Elapsed time since authentication and session idleness are emulated by moving `web_session.auth_time` or the last activity back in the database, because Keycloak cannot be clock-skewed; the platform's own rule is what is tested. The platform cannot check PKCE itself — only the provider can refuse a wrong verifier, and the tests show that it does.

A bearer access token outlives a back-channel logout until its `exp` (120 seconds in the qualification realm): logout revokes cookie sessions, not access tokens already issued, which is why VF-IAM-001's 60-second bound is not claimed. The `id_token_hint` travels in the query string of the end-session URL the browser visits, so it can appear in the provider's access logs and the browser history. Custom roles created before v0.15 keep any design-only capabilities they were given; the #19 check runs at create and revise only, not retroactively. The Host allow-list admits only the public hostname, so the provider's back-channel calls must address the platform by its public hostname. The provider is single-node development-mode Keycloak with an in-memory database, started per run; nothing was deployed, and no hosting exists. The owner's decision on the identity-provider deployment model (managed, self-hosted, customer-provided) is still open and gates acceptance of this slice.

## Reproduction

Live provider (Java 21 on PATH; the first run downloads and verifies Keycloak): `make idp`, or `.venv/bin/python scripts/run.py test --idp keycloak` and `.venv/bin/python scripts/run.py idp-browser --idp keycloak`. On native login roles: `IMPACT_FIXTURE_DSN=postgresql://postgres:<password>@127.0.0.1:5432/impact_test_idp .venv/bin/python scripts/run.py test --native --idp keycloak` against an empty disposable database. Full native: `IMPACT_FIXTURE_DSN=... make native`. Local: `make lint unit build test reference browser`. Continuous integration: jobs `local-reference-and-browser`, `live-identity-provider` and `native-postgresql-gate` in `.github/workflows/qualification.yml`.
