# v0.16 — Worker runtime, outbox dispatcher and email adapter

Build 0.16.0; schema 18 (migration 0018); domain API 1.10.0 (138 operations, unchanged) and control-plane API 1.4.0 (31 operations, three added). Roadmap Release 1 remains in progress. The ledger stays at **76 PARTIAL and 231 PENDING** requirements (0 accepted of 307): FR-IAM-001, FR-TEN-001 and FR-WFL-006, already PARTIAL, gain bounded worker and delivery evidence; FR-IAM-007 stays PENDING because a recovery contact's email confirmation is not an identity change or recovery and no test exercises its validation text; FR-ACC-008 was not touched; VF-IAM-001 stays PENDING.

## Delivered

Until this build an `outbox_delivery` row was written with every command and nothing ever read it: there was no worker, no dispatcher and no email. This increment adds a separate worker process that delivers in-app notices and email under database-enforced leases, the email adapter behind it, and the first three things it delivers — invitations, recovery-contact channel codes and in-app notices including authority expiry reminders.

**Worker process and fifth login.** `python -m impact_api.worker [--once] [--worker-id ID]` (`apps/api/impact_api/worker.py`) is a separate process. It reads only its own configuration (`IMPACT_WORKER_CONFIG_FILE`, a JSON file, then `IMPACT_<FIELD>` variables of `WorkerSettings`), never the API's configuration or connection strings, and keeps its connection string and secrets out of its `repr`. On native PostgreSQL it runs on a fifth provisioned login, `impact_worker_login`, a member of exactly `impact_worker` (`scripts/provision_logins.py`, `IMPACT_LOGIN_PASSWORD_WORKER`); with unprivileged connections required (always in staging and production) it refuses a superuser, BYPASSRLS, owner-member or foreign login at start with `PRIVILEGED_WORKER_CONNECTION` or `WORKER_LOGIN_TOPOLOGY` and exit code 3. `make dev` starts one worker (`--worker-id dev-worker`, synthetic mail sink `.local/dev/synthetic-mail.jsonl`, log `.local/dev/worker.log`; `--no-worker` omits it) and `make worker` attaches another to a running stack. `scripts/bootstrap.py` writes the worker's own `worker.json` beside the API configuration: worker DSN, public origin, the invitation and delivery secrets it shares with the API, and the sink.

**Leases on database time, fenced by generation, renewed per row.** Each iteration asks the SECURITY DEFINER `impact.worker_tenants(at)` for the Provisioning, Active and Suspended tenants with their state and due counts (identifiers only), then, per tenant, under the tenant advisory lock and a transaction-local tenant context, claims due rows (`channel IS NOT NULL`, not held, PENDING and due, or LEASED with an expired lease) with `FOR UPDATE SKIP LOCKED`, setting LEASED, the owner, `lease_generation + 1`, a 60-second expiry and one more attempt. Before building each message the worker renews that row's lease in its own transaction, fenced on owner and generation and only while the lease is live and the row is not held; a row whose lease ran out or was taken over is skipped unsent. The message is built from the rechecked intent, the connection is closed, the adapter is called outside any transaction, and a new transaction records the outcome with an UPDATE that carries owner and generation, so a stale holder's outcome matches no row. Every lease, due and expiry comparison uses `statement_timestamp()`, never the worker host's clock (`Worker(skew=...)` offsets it in tests only). SIGTERM or SIGINT finishes the delivery in progress, releases leases claimed but not started (restoring their attempt) and writes the heartbeat STOPPED.

**Backoff, DEAD and SUPERSEDED.** A failure is retried after `min(3600, 30·2^(attempts-1))·U[0.5,1)` seconds and becomes DEAD after six claims, or at once on a permanent class: `RECIPIENT_REFUSED`, `SMTP_PERMANENT_REJECTION`, `SMTP_HOST_REFUSED`, `RECIPIENT_UNREADABLE`, `SIGNING_KEY_MISMATCH` or `PREPARE_DEFECT`. MAIL FROM refusals (`SMTP_SENDER_REJECTED`) and 530/534/535/538 (`SMTP_AUTHENTICATION`) are retried because they are the operator's to fix, not the recipient's. An expired lease at the attempt limit becomes DEAD `LEASE_EXPIRED`. An intent that is no longer current is SUPERSEDED, never sent: `INVITATION_RESENT`, `INVITATION_CLOSED`, `INVITATION_EXPIRED`, `CHALLENGE_CLOSED`, `CHALLENGE_EXPIRED`, `RECIPIENT_CHANGED`, `RECIPIENT_INACTIVE`. Only the error class is recorded, never a server message, an address or a secret. A tenant pass that fails is logged by class, counted in the heartbeat's `failures` and never stops the loop.

**IN_APP exactly once.** An in-app intent is delivered transactionally: the fenced SENT update, one `notification_delivery` row (primary key tenant, notification, channel) and the consumer receipt `worker.in_app` commit together, and the notice gains `delivered_at` beside `acknowledged_at`. Every `WorkCenter.notify` notice now records such an intent; a notice whose recipient is no longer active is SUPERSEDED.

**SMTP adapter and synthetic sink.** `SmtpAdapter` uses the standard library: STARTTLS with certificate verification is mandatory for any non-loopback host; a non-loopback host is refused outside staging and production (`SMTP_HOST_REFUSED`), so development and test can never send real mail; staging and production require `email_adapter=smtp` and an HTTPS public origin. The Message-ID is `<event_id@host>`, stable across retries. Templates are a closed set of plain-text messages (`MEMBER_INVITATION`, `RECOVERY_CHANNEL_VERIFICATION`; `IN_APP_NOTICE` for the in-app channel), repeated as a CHECK constraint in the database. `SyntheticAdapter` writes one JSON line per message to a sink file and can inject failures and delay for tests.

**Nothing secret in the outbox.** An intent is one `delivery.requested` outbox event plus its `outbox_delivery` row written in the business transaction (`apps/api/impact_api/delivery.py`). No token, code or clear address is stored: the invitation link is re-derived from (tenant, invitation, generation) with the invitation signing secret and sent only while that generation is current; the recovery code is `HMAC(delivery_secret, challenge)` mod 10^8, and the challenge table keeps only a differently keyed HMAC of it; addresses are AES-256-GCM sealed under a key derived from `delivery_secret` with tenant, template and reference as associated data, so a sealed value cannot be moved onto another intent. `delivery_secret` (at least 48 characters, distinct from the cookie and invitation secrets; mandatory in staging and production) is shared by the API and the worker.

**Invitations by email.** Creating an invitation records an email intent; resending records a new one that reuses the first intent's sealed address, and the earlier intent becomes SUPERSEDED `INVITATION_RESENT` when the worker reaches it. A revoked, expired or accepted invitation's intent is SUPERSEDED too. The email carries the link; acceptance is unchanged and still requires the invited, verified identity and the inviter's current authority, so receiving the email proves nothing. Without `delivery_secret` (development configurations written before this build) invitations stay manual-only.

**Recovery-channel verification.** Two nominee-only control-plane actions: `channel-request` (`{email, reason}`; the address must hash to the contact's and to the identity's verified email) records a PENDING challenge and, through the SECURITY DEFINER `enqueue_recovery_channel_delivery`, exactly one email intent; `channel-confirm` (`{challenge_id, code, reason}`) accepts the eight-digit code within 15 minutes and 5 attempts. A wrong or expired code commits the spent attempt or the expiry and a `*-refused` platform event, then answers 403 without a receipt; a used code answers 409 `CHANNEL_CODE_USED`; at most three requests per contact per hour (429 `CHANNEL_REQUEST_LIMIT`); both actions only while the tenant is Provisioning, Active or Suspended; without `delivery_secret` a request answers 503 `DELIVERY_NOT_CONFIGURED`. A confirmation records `channel_verified_at` on the contact. It is **evidence only**: readiness, activation, eligibility and what a recovery contact may do are unchanged, and a contact still receives no workspace access.

**In-app notices and authority expiry reminders.** For Active tenants the worker scans delegated authority (`grant_authority`) and records `AUTHORITY_EXPIRING_14D` and `AUTHORITY_EXPIRING_3D` notices once per principal, expiry instant and threshold, registered in `authority_reminder` and excluded in SQL so that a batch limit cannot starve later groups; the notices and their audit events are written as the tenant's SERVICE principal `uuid5("impact-worker-principal-v1:" + tenant)`, created on first use with no identity, membership or grant.

**Cancellation of jobs that had not started.** The worker marks jobs with `cancellation_requested_at` that are still Requested, Validating or Queued as Cancelled (generation + 1, a `job_item` `cancellation` row `CANCELLED_BEFORE_START`) and records `NOT_CANCELLED_STARTED` for a job that had started. No job class is executed by the worker; the pass was exercised with test-inserted jobs.

**Suspension.** Rows queued before a suspension carry `held_at` (set by `quiesce_tenant` since v0.10) and are never claimed or sent; a held row whose lease ends returns to PENDING and stays held; reactivation does not release or replay them, consistent with the v0.10 rule that reactivation never replays queued work. The operator's suspension preview (`tenant_work_impact.unsent_events`) now counts only open dispatchable intents (PENDING or LEASED with a channel), not legacy `object.changed` rows or finished ones, and the preview text says undelivered notices or emails.

**Operator view and UI.** `GET /v1/platform/workers` (operator only; 404 for anyone else) lists up to 50 heartbeat rows — worker, build, state, start, last beat, stop, stale flag (no beat for 60 s by the database clock), iterations, sent, retried, dead, failures — and no tenant data. The tenant-lifecycle console gains a **Workers** panel for operators (`apps/web/src/Workers.tsx`). **Recovery contacts** (`RecoveryContacts.tsx`) gains the nominee's flow: **Email me a verification code**, then **Enter verification code**, with the masked address, the confirmation state and time, and explained refusal reasons. The browser checks run one worker iteration against the run's own `worker.json` and read the synthetic sink (`tools/browser/worker-run.mjs`).

**Qualification.** `qualification/test_worker.py` (31 cases in the default and native suites, one of them PGlite-only) covers the invitation intent holding no token or address and being sent once, supersession of resent and revoked invitations, lease takeover refusing the stale holder's outcome, backoff with jitter then DEAD, permanent and transient SMTP rejections (sender, authentication and recipient cases parameterised), released leases on stop, SMTP to a local sink with no transaction open during the call, refusal of non-loopback SMTP outside staging, refusal of a privileged connection, exactly-once in-app delivery of a stale-calculation notice, supersession for an inactive recipient, idempotent 14- and 3-day reminders, cancellation of a queued job and not of a running one, the single-use channel code, its expiry and five-attempt lock, refusal for a closed contact, rate limit and state gate, a challenge contact of another tenant, worker-role tenant fencing, the app role being unable to record outcomes, operator-only heartbeats, the signing secret needed for an invitation link, a batch row whose lease ran out, a held row, the unsent-events count, a failing tenant or template not stopping the worker, and settings that never print secrets. `qualification/test_native_worker.py` (8 native-only cases, worker subprocesses on `impact_worker_login`) covers SMTP from a real worker process with no transaction open, two worker processes never delivering the same row, simultaneous claims being disjoint, a lease takeover while the first holder is sending, SIGTERM finishing the current send and releasing the rest, refusal of a privileged or foreign login, the worker login holding only the worker role, and a batch outliving its lease sending every row once. Two unit tests cover the production delivery-secret rule and sealing bound to its intent. The recovery browser group gains the nominee's email-code confirmation and the tenant group the operator's Workers panel (93 browser checks in nine groups).

## Contract and persistence

Migration 0018 (`infrastructure/migrations/0018_worker_delivery.sql`, SHA-256 `bd2defdfb56f3332f0cdb1706fd330893497cc3eeb8f45f4277922f0eca9e8b7`, ledgered in CURRENT-DATA-DICTIONARY.md and verified with `sha256sum`) adds dispatch columns to `outbox_delivery` — `channel` (IN_APP/EMAIL), closed `template`, `reference_id`, `reference_generation`, `recipient_sealed` (29–300 bytes), `state` (PENDING/LEASED/SENT/DEAD/SUPERSEDED), `lease_owner`, `lease_generation`, `lease_expires_at`, `next_attempt_at`, `last_attempt_at`, `last_error_class`, `completed_at` — with four CHECK constraints, a partial due index and a reference index; legacy and `object.changed` rows keep `channel` NULL and are never dispatched. It revokes UPDATE on `outbox_delivery` from `impact_app` (outcomes are the worker's alone); adds `notification_delivery` (RLS; worker SELECT/INSERT, app SELECT); `recovery_channel_challenge` (RLS; platform SELECT/INSERT/UPDATE, worker SELECT; one PENDING challenge per contact; composite foreign key to the contact) and `tenant_recovery_contact.channel_verified_at/channel_challenge_id` with `UNIQUE(tenant_id, contact_id)`; the SECURITY DEFINER functions `enqueue_recovery_channel_delivery` (platform) and `worker_tenants` (worker) with owner-only SELECT policies on `tenant_root` and `outbox_delivery` for the latter; SELECT on `member_invitation` and `grant_authority` for `impact_worker`; `worker_heartbeat` (no tenant data; worker writes, platform reads); `authority_reminder` (RLS; worker SELECT/INSERT); and replaces `tenant_work_impact` so that `unsent_events` counts only open dispatchable intents. Readiness now requires schema version 18. Migrations 0001–0017 are byte-identical to their ledgered checksums; the native run, the restore drill and the upgrade check each verified all eighteen, and the upgrade check migrates a populated schema-17 database with a `web_session` row and an `outbox_event`/`outbox_delivery` row to 18, so 0018's ALTER runs on a populated table.

The control-plane contract (`openapi-platform.json`) moves from 1.3.0 to 1.4.0 with three operations — `recovery_contact_channel_request`, `recovery_contact_channel_confirm` and `list_workers` — for 31 in all; the contact representation gains `channel_verification` (state, challenge, expiry, verification time). The domain contract (API 1.10.0, 138 operations), `openapi-implemented.json`, `access-policy.json` (305 rows, 218 capabilities) and `event.schema.json` are unchanged; `delivery.requested` events are internal delivery intents outside `event.schema.json`. New configuration: `delivery_secret` for the API (`IMPACT_DELIVERY_SECRET`) and the worker's own settings (`worker_dsn`, `public_origin`, `invitation_secret`, `delivery_secret`, `email_adapter` smtp/synthetic, `smtp_host`, `smtp_port`, `smtp_username`, `smtp_password`, `smtp_from`, `smtp_timeout`, `synthetic_sink`, `lease_seconds`, `poll_seconds`, `batch_size`, `max_attempts`, `scan_seconds`, `require_unprivileged_db`); see OPERATIONS-GUIDE.md "Worker and email delivery".

## Limits

No live SMTP provider has been configured or used: every email in every recorded run went to a local SMTP sink on loopback (`qualification/smtp_sink.py`, plain SMTP without STARTTLS or AUTH) or the synthetic sink. The STARTTLS-with-verification path that the adapter enforces for non-loopback hosts, and SMTP AUTH, are therefore implemented but not exercised against a server; only the refusal of a non-loopback host outside staging and production is tested. Bounces, complaints, SPF, DKIM and DMARC alignment, provider sending limits and any rate limiting of outbound mail do not exist. The owner's decision on the email provider is still open and gates staging.

Email is at least once, not exactly once, in one case: a single send that itself outlives a whole lease period mid-SMTP. Its holder may already have handed the message to the relay before its outcome is refused, and the new holder sends it again (`test_native_lease_takeover_while_the_first_holder_is_sending` shows both sends); the stable Message-ID is the only receiver-side deduplication. A batch that outlives its lease no longer duplicates mail, because each row's lease is renewed just before its message is built. Only IN_APP delivery is exactly once.

`impact_worker` still holds migration 0003's SELECT/INSERT/UPDATE on nearly every domain table; 0018 adds what the worker needs but does not narrow the rest. No job class is executed by the worker: the cancellation pass acts only on `cancellation_requested_at`, which today only membership revocation and suspension set (both already cancel queued jobs themselves), so it was exercised with test-inserted jobs. Rows held by a suspension are never re-sent after reactivation and no operator re-queue exists; an operator inspects DEAD and held rows only through the database (OPERATIONS-GUIDE.md). Delivery intents are outside `event.schema.json`.

The worker holds the invitation signing secret, so a compromised worker, or its configuration file, can mint invitation links for existing invitations; acceptance still requires the invited, verified identity and the inviter's current authority. The worker's SERVICE principal is accepted by `store.py` as a "P" (principal) reference in audit and notice authorship; it has no identity, membership or grant. FR-ACC-008 (privileged support access) was listed for this increment in the delivery plan and was not touched. Recovery-channel verification does not change activation readiness, recovery-contact eligibility or what a contact can do, and is not account recovery (FR-IAM-007 stays PENDING).

On PGlite the worker and the API take turns on the single socket connection, so worker contention is exercised only by the native-only cases. The native evidence is single-node PostgreSQL 16.13 without a pooler; the upgrade check covers 0017 → 0018 only. No hosting exists and nothing was deployed.

## Reproduction

Local: `make lint unit build test reference browser`; the worker cases run inside `make test`. A development stack with one worker: `make dev` (messages in `.local/dev/synthetic-mail.jsonl`); one more worker: `make worker`. Full native, including the native worker cases on `impact_worker_login`: `IMPACT_FIXTURE_DSN=postgresql://postgres:<password>@127.0.0.1:5432/impact_test make native` against an empty disposable database (`IMPACT_LOGIN_PASSWORD_WORKER` joins the other login passwords when they are chosen explicitly). Live provider: `make idp`, and on native login roles `IMPACT_FIXTURE_DSN=<empty impact_test_idp> .venv/bin/python scripts/run.py test --native --idp keycloak`. Continuous integration: jobs `local-reference-and-browser`, `live-identity-provider` and `native-postgresql-gate` in `.github/workflows/qualification.yml`.
