# v0.17 — Deployment package and first staging

Build 0.17 deployment package on top of build 0.20.0 (it keeps main's version literals; no application code, schema, contract or policy changed): schema 21 (no migration), domain API 1.13.0 and control-plane API 1.4.0 unchanged. Roadmap Release 1 remains in progress. The ledger stays at **87 PARTIAL and 220 PENDING** requirements (0 accepted of 307): FR-SEC-006, FR-OPS-005, VF-OBS-001, VF-DR-001 and VF-AVL-001 are not moved, because no executed test exercises their validation text on the deployed server (see Limits).

Owner decisions recorded 30 September 2026: one DigitalOcean droplet (Bangalore, Ubuntu 24.04, 2 vCPU / 4 GB, daily DigitalOcean backups) running everything with Docker Compose; self-hosted Keycloak on the same server; no refresh tokens (the v0.15 substitution, accepted); cheapest and simplest options; host names from sslip.io instead of a purchased domain; no email provider yet.

## Delivered

Until this build the platform ran only on a developer machine or a CI runner. This increment packages it for a real server and adds everything needed to deploy, operate and check that server without logging in to it.

- **Container image** (`deploy/Dockerfile`, `.dockerignore`): multi-stage — Node 24 compiles the web client, Python 3.12 slim runs the API, the worker, the database job and the bootstrap from one image. Python packages come from `deploy/requirements.runtime.txt`, the runtime subset of `requirements.lock` pinned by SHA-256 (`deploy/hash_requirements.py` regenerates it; a unit test fails when the two disagree) and installed with `pip --require-hashes`, wheels only. Runs as a non-root user; only the files the processes read are copied (no tests, fixtures, documentation or local state). The API runs without an access log (the reverse proxy logs requests with authorization codes, state and nonces redacted).
- **Compose stack** (`deploy/compose.yaml`, project `impact`): PostgreSQL 17 on an internal network with no route out; Keycloak 26.7.4 in production mode (`start`) on its own database and login, behind the proxy with `KC_PROXY_HEADERS=xforwarded`, health on the management port; the API as `staging` on the three runtime logins with `IMPACT_REQUIRE_UNPRIVILEGED_DB=1`, HTTPS origin, issuer, JWKS and endpoints of the realm and `required_acr` `urn:impact:acr:mfa`; the worker on `impact_worker_login`; Caddy 2 with automatic HTTPS for both host names (Let's Encrypt; `CADDY_TLS_MODE=internal` switches to Caddy's own CA for CI), HSTS, HTTP→HTTPS, Keycloak's administration console and master realm not published, the only published ports 80 and 443; a `backup` service. Health checks, `restart: unless-stopped`, log rotation (10 MB × 5), read-only root filesystems, all capabilities dropped and `no-new-privileges` for the application containers. Inside the stack Caddy answers to both public names, so the API fetches the provider's keys, and Keycloak calls the back-channel logout URL, by their public HTTPS names.
- **Mail capture instead of an email provider** (`deploy/mail_sink.py`): the worker refuses the synthetic adapter in staging (`SMTP_AND_HTTPS_REQUIRED`, unchanged), so it runs its SMTP adapter against a loopback capture service that shares its network namespace; each message is recorded as one JSON line in a 0600 file and nothing is sent. `SMTP_*` in `/opt/impact/config.env` points the worker at a real provider later.
- **Database preparation** (`deploy/prepare_database.py`, the one-shot `migrate` job): provisions the five logins with `scripts/provision_logins.py --revoke-public-connect`, creates or re-passwords Keycloak's own login and database (closed to PUBLIC), revokes PUBLIC's connect on the maintenance database, then runs `scripts/migrate.py` as `impact_migrator`. It never loads the fixture and refuses to run with `IMPACT_ALLOW_FIXTURE_LOAD` set.
- **Pull-based deployment** (`deploy/update.sh` with `deploy/lib.sh`), run as root by the server's `impact-sync` timer after it resets the checkout to `main`: idempotent on a fresh server and on every later run; stops the first-boot key service; generates `/opt/impact/secrets.env` once (random hex secrets: PostgreSQL superuser, five login passwords, Keycloak database and administrator passwords, a 96-character cookie secret and distinct invitation and delivery secrets; mode 0600; never printed); derives the host names from the DigitalOcean metadata IP through sslip.io unless `/opt/impact/config.env` overrides them; builds the image once per commit on the server; prepares the database; starts the stack; imports the realm only when absent (afterwards only the web client's origin-dependent URLs are re-aligned; users are never touched); creates the owner's provider account and the first platform operator when absent; waits for health; keeps the last three images; writes `/opt/impact/status.json`, also served at `https://<app host>/deploy-status.json` and, so that a certificate failure stays diagnosable, at the same path over plain HTTP (commit, times, step, outcome, service states, schema version, operator outcome, and the last 40 log lines with every stored secret value replaced). A commit that is already deployed and healthy only refreshes the status. A lock prevents overlapping runs.
- **Staging realm** (`deploy/keycloak/realm-staging.json`), derived from the qualification realm without users or provider roles: realm `impact`; self-registration and "forgot password" off; email as username; brute-force protection (5 failures, waits up to 15 minutes); password policy of at least 12 characters, not the username or email; the same password-then-TOTP step-up flow and ACR map (`urn:impact:acr:mfa` = level 2); the public client `impact-web` with S256 PKCE, no refresh tokens, no direct grants, the callback, post-logout and back-channel logout URLs on the application origin and the `impact-api` audience mapper.
- **First administrator.** `scripts/bootstrap_operator.py` (in the image, on the migration login) registers a provider account as a platform identity and makes it the first platform operator for 365 days, and records the deployment qualification the control plane checks tenant requests against (staging, region `do-blr1`, the realm issuer and ACR, privacy reference `staging-privacy-notice-v1`, recovery reference, up to 3,650 days' retention, valid 365 days); it refuses (exit 3) when any other operator exists and changes nothing when re-run for the same identity; `identity` registers further people with no authority. `deploy/keycloak_admin.py` (internal admin REST API, standard library only) imports the realm, creates accounts with email marked verified, required actions UPDATE_PASSWORD and CONFIGURE_TOTP and a temporary password, reports account status and resets passwords or authenticators. `deploy/first-admin.sh`, run by the owner in the DigitalOcean Web Console, shows the one-time password only while it is still pending and only to a terminal; `--reset` / `--reset-totp` are the recovery path while no email exists. `deploy/add-user.sh` gives another person a sign-in and an identity with no authority.
- **Backups** (`deploy/backup.sh`): nightly `pg_dump -Fc` of the application and Keycloak databases at 21:00 UTC into the `backups` volume, each read back with `pg_restore --list` before it is kept; 7 daily and 4 weekly (Sunday) dumps; one dump at first start; `backup.sh --now` takes one on demand.
- **Checks from outside**: `scripts/smoke.py <base url>` (TLS chain and host name, HTTP→HTTPS, live and ready, security headers, web client, development sign-in off, `/auth/login` redirect with S256 PKCE, callback and ACR, the realm's discovery and login page, administration console hidden, status file without secret-looking fields; JSON report, exit 1 on failure) and `scripts/staging_first_login.py` (the owner's first sign-in without a browser: temporary password, authenticator enrolment from the enrolment form's secret, new password, profile if asked, return to the platform, then platform operator and a fresh-assurance control-plane request that passes the MFA gate and stops at the missing qualification with 404, writing nothing).
- **CI job `container-stack`**: runs `deploy/update.sh` on the runner as on the server (internal CA, fake host names mapped to 127.0.0.1), then the smoke check over verified HTTPS, a second `update.sh` run that must take the unchanged path, `first-admin.sh` (reveals only to a terminal-allowed stream, then nothing once the password was replaced), the first sign-in check, `add-user.sh`, a dump taken on demand (`backup.sh --now`) restored into a scratch database with its migration and operator rows checked, and a final smoke check; on failure it publishes the status and service logs as annotations.
- **Plain-language guide**: [DEPLOYMENT-GUIDE.md](current/DEPLOYMENT-GUIDE.md) (what runs where, cost, how deploys happen, status, first-admin steps, email, backups and restore, rollback, configuration, limits).

## Contract and persistence

No application code, migration, contract, policy row or fixture changed. Readiness requires schema 21 (main's readiness gate); the database job applies all 21 migrations. New code is confined to `deploy/`, `scripts/bootstrap_operator.py`, `scripts/smoke.py`, `scripts/staging_first_login.py`, `qualification/test_deploy_unit.py`, the Makefile (`unit` includes the deployment tests; `lint` covers `deploy/`) and the workflow. The bootstrap writes `auth_identity`, `platform_operator` and `deployment_qualification` rows as `impact_owner` (the tables are "provisioned by deployment administration, never writable by HTTP runtime roles", migration 0013). It does not write a `platform_event`: every event row belongs to a tenant (`tenant_id NOT NULL REFERENCES tenant_root`), and changing that would need a migration; the evidence of the bootstrap is the operator row's authority reference (who, commit) and the JSON the job prints into the deployment log.

## Limits

- **One server** runs database, identity provider and application; no redundancy, no load test, sizing unmeasured (VF-AVL-001 not evidenced). The CI stack is the only place the package has run; the first real deployment happens when this is merged, and its outcome is visible only through `deploy-status.json`.
- **Backups:** the nightly dumps sit on the same server; DigitalOcean's daily droplet backups are the off-server copy. No RPO/RTO is defined; the restore of a dump is exercised in CI only, not on the server (VF-DR-001 not evidenced); a scheduled restore drill does not exist.
- **No email provider:** invitation and recovery-contact emails are captured on the server, not delivered; "forgot password" is off and the console reset is the recovery path. Bounces, SPF/DKIM and sending limits remain open, and the worker has no route out until a provider is configured.
- **Host names from sslip.io** (a free third-party DNS service) and Let's Encrypt limits on that shared domain; a real domain is a configuration change.
- **Observability:** no metrics, alerting or central logs (VF-OBS-001, FR-OPS-005 not evidenced); container logs rotate on the server and the status file is the only external signal. Structured request logs exist only at the proxy.
- **Secrets** live in a root-only file on the server and in container environments (FR-SEC-006 key governance and rotation not evidenced); rotating the cookie, invitation or delivery secret signs everyone out or invalidates queued mail and codes.
- **Operators:** only the first operator is automated. The platform's independence rules need at least three people to activate a tenant (requesting operator, a different owner, a second operator who is neither), plus a recovery contact; a second operator, operator renewal and qualification renewal are manual database changes. Every person needs an `auth_identity` row before signing in (`add-user.sh`), because the platform never creates identities from a provider login.
- **Staging only:** synthetic or test data only (rule 11); no penetration test; Keycloak key rotation, provider outage and managed-provider comparisons not exercised; back-channel logout from Keycloak to the API is not exercised in CI (Java does not trust Caddy's internal CA there) and is expected to work on the server with Let's Encrypt certificates, untested.
- **Single version source** (planned for v0.17 in the delivery plan) is not delivered: version literals are still set by hand at merge; Helm charts are not provided (one server, owner decision).
- Base images follow their tags (`python:3.12-slim-bookworm`, `node:24-bookworm-slim`, `postgres:17`, `caddy:2`) and are refreshed at each build; Keycloak is pinned by tag, not digest.
- Docker Hub and quay.io are not reachable from the development sandbox, so the image and the stack were built and run only in CI; the parts that do not need containers were rehearsed locally (below).
