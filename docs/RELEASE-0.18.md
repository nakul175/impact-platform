## Delivered

Until this build a programme had indicator instances, plans, periods and results, but no results framework, no targets and no baselines: nothing said which outcome an indicator measured or what value a period was expected to reach. This increment adds both as governed objects with the same draft, independent review and immutable approval as indicator definitions, and one read that compares approved targets with results.

**Framework hierarchy.** A framework (`/frameworks`) belongs to one programme and holds typed nodes — IMPACT, OUTCOME, OUTPUT, ACTIVITY — each with a stable `node_id`, title, description, intended result level, owner and the indicator instances placed on it. Editing a draft keeps node identities, so renaming an output keeps its identity and its indicator placement (no duplicate node). Every save refuses structural invalidity: duplicate node identities, a parent that is not in the framework (`ORPHAN_PARENT`), containment cycles including a node containing itself (`CONTAINMENT_CYCLE`), a child at a higher level than its parent (`LEVEL_ORDER`), an indicator placed twice (`INDICATOR_LINKED_TWICE`) or taken from another programme (`INDICATOR_PROGRAMME_MISMATCH`), duplicate exceptions, and, in a child draft, removal of a node that places indicators in the approved baseline (`NODE_REFERENCED`). An unknown indicator identifier answers 404. Theory-of-change relationships are not implemented: the design's `relationships` array is accepted only empty, and assumption or input nodes are refused.

**Completeness review with exceptions.** `GET /frameworks/{id}/completeness` lists issues with severity, rule, object, message and assigned resolver (the node owner, or the framework owner): errors for incomplete nodes and an empty framework; warnings for orphan nodes, unmeasured impact/outcome/output nodes (`UNMEASURED_RESULT`) and programme indicators not placed on any node (`ORPHAN_INDICATOR`). Only a warning can be excepted, and only with a reason and a review date that is not in the past; the server stamps who recorded the exception and when (`recorded_by`, `recorded_at`), and client-supplied authorship is refused. An exception that matches no current warning becomes an error (`EXCEPTION_NOT_APPLICABLE`), and one whose review date has passed is refused (`EXCEPTION_REVIEW_DATE_PASSED`). Submission (`framework.submit`) is refused with `FRAMEWORK_INCOMPLETE` while any error or unexcepted warning remains. Accepted exceptions stay in the approved revision, so they remain visible in the baseline evidence.

**Independent review and immutable baselines with a supersession chain.** Submission creates the single-stage review used by other governed records; the approver must be a different natural person from every author of the candidate revision (a reviewer who edits the draft becomes an author), and the reviewer's candidate view includes the completeness report and, for a child draft, the revision it supersedes. Approval appends one row to the insert-only `framework_baseline` register — programme, baseline version, framework revision, the revision it supersedes, effective date, workflow, approver and time — and the superseded framework becomes Superseded. A programme has one root baseline (`FRAMEWORK_BASELINE_EXISTS`); a later change is a child draft naming the approved revision it supersedes, with an effective date after the previous one (`EFFECTIVE_DATE_ORDER`); a draft built on a baseline that has since been superseded is refused (`FRAMEWORK_BASELINE_CHANGED`), so a second child cannot be approved after the first. The completeness read of a child draft includes a comparison with its base (nodes added, removed, changed). The earlier approved revision keeps its approved language.

**Targets, baselines and milestones.** A target (`/targets`) belongs to one indicator instance and one programme period of the programme's reporting calendar (`PERIOD_NOT_IN_PROGRAMME_CALENDAR`, `PERIOD_OUTSIDE_PROGRAMME`). Kinds are VALUE, RANGE (inclusive low and high bounds) and MILESTONE (label and due date inside the period); directions HIGHER, LOWER, RANGE and MILESTONE must match the kind; bases are ORIGINAL, BASELINE and REVISED. Values are decimal strings under the existing decimal rules and carry an explicit value state: only a PRESENT target carries a value or bounds, a blank target is never zero, and migration 0019 repeats that as a CHECK constraint. Submission pins the indicator's approved definition revision (a draft can never carry the pin). Approval appends a row to the insert-only `target_binding` register per indicator, period and slot (TARGET, BASELINE, or one per milestone label); a second approved target for a slot is refused (`TARGET_ALREADY_APPROVED`) and a change is a REVISED target that names the approved revision it supersedes and gives a reason, so the original stays in the chain.

**Baseline correction.** An approved baseline is corrected the same way: a new BASELINE target supersedes the approved one, is independently reviewed, and the register keeps both rows.

**Targets versus actuals.** `GET /programmes/{id}/targets-vs-actuals` (capability `targets.read`, optional `period_id`, `limit` 1–100 indicators per page, HMAC-signed cursor) returns per indicator and period the approved target, baseline and milestones, the actual, the progress and the framework nodes that place the indicator. The actual is OFFICIAL only from this programme's own locked snapshot, read under the definition revision pinned by the target, with its source shown (`PROGRAMME_SNAPSHOT` and the snapshot identity); otherwise it is PROVISIONAL from this programme's own calculations, or NONE. The seeded OFFICIAL 46.36 sits in a fixture snapshot bound to no programme and is never attributed, and a shared definition never borrows another programme's official result. Without result access the actual is withheld (`RESULT_ACCESS_REQUIRED`). Progress uses stored values, not displayed ones: attainment for a higher target is uncapped (actual 120 against 100 is 120.00 percent), a lower target reports status and signed deviation without inverting success (target 10, actual 8: ACHIEVED, deviation −2), range bounds are inclusive, milestones need an assessment (`ASSESSMENT_REQUIRED`), a zero target is `ZERO_TARGET` with attainment Undefined, a blank target or actual is never zero (`NO_TARGET`, `NO_ACTUAL`), and a change from baseline has no percentage when the baseline is zero or negative (`NON_POSITIVE_BASELINE`). An arithmetic overflow beyond NUMERIC(38,12) empties that one row with reason `ARITHMETIC_OVERFLOW` instead of failing the read.

**Close pins targets and the governing framework revision.** A period close pins the approved target revisions (`target_versions`) and the framework revision that governs the period (the latest approved baseline effective before the period ends, `policy_context.framework_revision`) into the snapshot; both enter the close fingerprint, so a target approved after the preview makes the request stale, and a close without targets or a framework keeps the pre-0.18 fingerprint. Locked rows are placed by the pinned framework revision, so a later revision does not re-place a locked period. A new or revised target for a locked period is refused (`PERIOD_LOCKED`).

**UI and browser check.** A **Results framework** area (`apps/web/src/Planning.tsx`) has four tabs: **Framework** (logframe editor and hierarchy tree, completeness review with **Document exception**), **Targets**, **Targets vs actuals** (with the actual's source and **Load more** paging) and **Reviews** (the independent reviewer re-fetches the candidate before deciding). Mutations keep their operation ID for the life of a dialog, so a retried submission is exact. The new `planning-browser` mode (`tools/browser/planning-check.mjs`, seven checks) builds a logframe, accepts a documented exception, retries a lost submission exactly, approves the baseline as an independent reviewer, approves a target, asserts that no borrowed official result is shown, and checks a 390 px viewport.

**Qualification.** `qualification/test_planning.py` (24 cases: 22 functions, one parameterised over two routes, one native-only) covers draft, review, baseline and child version; refused structures; the unmeasured-output acceptance case; access boundaries (other tenant, revoked, EXTERNAL, enumerator); exact retry, conflicting reuse and stale revision; targets, baselines, milestones and provisional progress; blank targets and decimal round-trips; target rules and the calendar; close pinning targets and reading the OFFICIAL result; the seeded fixture official never attributed; no borrowing across programmes sharing a definition; withheld actuals; paging by indicator; baseline correction; per-row overflow; the blank-state CHECK; the pinned framework revision at close; exception authorship and review date; the second child refused; a reviewer who edits becoming an author; the degraded candidate view; permission-filtered listing; and, natively, that both registers are tenant-fenced and insert-only for the app role. `qualification/test_planning_unit.py` (13 cases) covers the structure rules and the progress arithmetic.

## Contract and persistence

Twelve domain operations are added (API 1.10.0 → 1.11.0, 150 operations): `list_frameworks`, `create_frameworks`, `get_frameworks`, `patch_frameworks`, `action_frameworks_submit`, `framework_completeness`, `list_targets`, `create_targets`, `get_targets`, `patch_targets`, `action_targets_submit` and `programme_targets_vs_actuals`. Approval uses the existing workflow approve, return and reject actions. `access-policy.json` gains two rows (307 rows) and keeps 218 capabilities; the implemented operations now use 92 capabilities (84 before), so custom roles may delegate the eight planning capabilities (`frameworks.read`, `frameworks.draft.create`, `frameworks.draft.edit`, `framework.submit`, `targets.read`, `targets.draft.create`, `targets.draft.edit`, `target.submit`). None requires a purpose or fresh assurance. The control-plane contract (1.4.0, 31 operations) and `event.schema.json` are unchanged.

Migration 0019 (`infrastructure/migrations/0019_results_framework.sql`, SHA-256 `e12728cf4bbb2ff544c75183ac9c5371b393f498f7d61ed791d8a08b356c4161`, ledgered in CURRENT-DATA-DICTIONARY.md and verified with `sha256sum`) adds `framework_current.effective_from`, `supersedes_revision` (with a generated kind column and a composite foreign key to a Framework revision) and `exceptions` (a JSON array); `target_current.indicator_id` (typed, foreign key to an IndicatorInstance), `milestone_label`, `due_at`, `supersedes_revision` (typed, foreign key to a Target revision) and `reason`, plus the CHECK `target_blank_is_not_zero`; and two registers, `framework_baseline` (primary key tenant, programme, baseline version; unique framework revision and unique superseded revision, so each revision is superseded at most once; version 1 exactly when nothing is superseded; the superseded revision must itself be a register row of the same programme) and `target_binding` (primary key tenant, indicator, period, slot, binding version; the same chain rules per slot). Both carry typed `_kind` columns and composite foreign keys, forced row-level security with the `tenant_fence` policy, and are **insert-only**: `impact_app` has SELECT and INSERT only, and the control plane has nothing. Readiness now requires schema version 19. Migrations 0001–0018 are byte-identical to their ledgered checksums; the native run, the restore drill and the upgrade check each verified all nineteen, and the upgrade check migrates a populated schema-18 database, including populated `framework_current` and `target_current` projections, to 19.

## Limits

Not implemented: FR-PLN-002 (theory-of-change relationships and assumptions), FR-PLN-004, FR-PLN-005, FR-PLN-007, FR-PLN-008 and FR-PLN-009; FR-IND-004 restated comparisons (a new or revised target for a locked period is refused, not restated); status thresholds, disaggregated targets and cumulative targets (planned for v0.19), so no cumulative-to-flow conversion exists; charts and dashboard widgets (the comparison is a table). There is no per-exception acceptance record: the independent approver of the framework revision is the authority that accepts its exceptions. A framework cannot delete an obsolete draft (no delete operation exists). Programme readiness is not gated on an approved framework. The seeded WATER-A programme has no reporting calendar, so it cannot carry targets. Targets-versus-actuals rows appear only for periods with an approved target, a result or a snapshot unless the read is filtered by `period_id`; a page is capped by indicators (at most 100), so its row count is indicators × periods with data.

The native evidence is single-node PostgreSQL 16.13 without a pooler; the upgrade check covers 0018 → 0019 only. On PGlite every transaction is serialised, so no concurrent planning writers were exercised. No hosting exists and nothing was deployed.
