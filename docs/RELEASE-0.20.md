## Delivered

Until this build the only way to record a value was a manual observation. This increment adds governed web forms: a form version is designed, independently reviewed and published, and a response captured on it becomes observations that enter the existing observation review, calculation and period-close path.

**Form versions (FR-FRM-001, FR-FRM-003).** A Form revision carries its fields, answer rules and indicator bindings, so the version a reviewer approves is exactly the version a response is validated against. A field has a stable `field_id`, a stable code, a position, a type (TEXT, DECIMAL, INTEGER, BOOLEAN, SINGLE_CHOICE), label, help, `required`, numeric bounds, a maximum text length or choices, and optionally the indicator instance and role (VALUE, NUMERATOR, DENOMINATOR) its answer feeds, or the disaggregation dimension a choice supplies. Drafts are validated as they are saved; submission for review requires a complete version and refuses unsupported combinations before publishing (`FORM_FIELD_INVALID`, `FORM_FIELD_DUPLICATE`, `FORM_RELEVANCE_INVALID`, `FORM_BINDING_INVALID`: a binding to a non-manual indicator, to another programme's indicator, a ratio without both components, a value role on a text field, a dimension the bound definition does not declare or a multiselect dimension). A field that supplies an exhaustive dimension must be `required` and either always relevant or relevant under exactly the bound fields' rule (`FORM_DIMENSION_FIELD_INVALID`), so a published version cannot accept a present value whose dimension is blank or hidden. The lifecycle is Draft → Submitted → Approved (the ordinary single independent review, natural-person independence) → Published: publication (fresh authentication within 300 seconds, `form.publish`) writes a new revision with the approved content and one row in the insert-only `form_publication` register (`version_number` 1..n, the approved revision pinned, each version superseded at most once). A published form is revised through a new draft; the published version keeps collecting until its successor publishes.

**Relevance and server validation (FR-FRM-002).** Relevance is one bounded rule per field (`relevant_when`: an earlier yes/no or choice field equals a stated code); references must point to an earlier field and a declared code, so cycles cannot form (`FORM_RELEVANCE_INVALID`). The server evaluates the same rules in field order: a submission needs every relevant required answer, refuses an answer to a field that is not relevant (`ANSWER_NOT_RELEVANT`; a tampered payload cannot carry a hidden answer), checks types, bounds, text length and choice codes, and refuses unknown fields. The web client evaluates the same rule to show or hide a question.

**Submissions and value states (FR-FRM-003, FR-FRM-006).** A submission draft pins a published `form_version` (required at creation, `FORM_VERSION_REQUIRED`, and immutable afterwards) and an optional `unit_key`. Drafts are saved on the server and resumed with the same submission identity and version. Submit validates the response and, for each bound indicator, writes one observation in the reserved `FORM` namespace with source key `<unit_key or submission id>/<indicator id>` and `source_version` the form revision, then submits it into the existing independent observation review in the same transaction; each observation and its review workflow get their own audit and outbox events, and the command's receipt is the submission's. A blank answer is MISSING, an explicit reason keeps NOT_COLLECTED, NOT_APPLICABLE or MISSING, a question that is not relevant is NOT_APPLICABLE, numerator and denominator answers pool into a ratio (a zero denominator is UNDEFINED, never zero; negative components and a percentage numerator above its denominator are refused), and dimension answers become the observation's codes. Every natural author of the response (drafters and submitter) becomes an author of each observation, so none of them can approve it. A response captured on a version that has since been superseded is kept exactly as received as `Quarantined` with no observations (FT-FRM-003: never completed or mapped to the new version). Collection plans count a response when an obligation names `FORM/<unit_key>/<indicator id>`.

**Access.** Submitting a response to a form with indicator bindings creates and submits observations, so besides `submission.submit` the caller must hold `observation.submit` at TENANT scope (`POLICY_DENIED`, reason `OBSERVATION_SUBMIT_REQUIRED`) and read access to the bound indicator instances, their definitions and programme and the workflow template, exactly as a manual observation submit reads them; the policy row of `action_submissions_submit` declares this (`additional_capabilities_when_bound`). A form without bindings needs only `submission.submit`. The fixture ENUMERATOR holds `submission.submit` but not `observation.submit`, so it can draft and submit unbound responses and draft bound ones; a bound submit is refused with the reason above. The `FORM` source namespace is reserved: a direct observation create or patch using it is refused (`SOURCE_NAMESPACE_RESERVED`).

**UI.** A Forms area per programme: a designer (questions, type, bounds, choices, indicator and role, "ask only when" rule), send for review, publish, a new version from a published form, and a fill-in dialog that shows the version number, hides questions that are not relevant, records explicit reasons for blanks, saves a server draft and submits with an operation identifier kept for the life of the dialog, so the retry after a lost response returns the original receipt. Submit is offered only when the viewer holds what the server requires. The fixed sidebar now scrolls (below).

## Limits

- Not implemented: groups and repeat groups, classification per field, calculated fields, media, GPS, photos, preview modes, isolated test, logic rules beyond one equality rule per field, dependency recalculation with a confirmation to clear newly irrelevant answers (the client simply hides them and the server refuses them), translations and language versions (FR-FRM-004), compatibility declarations and acceptance cutoffs (only `LOCK_PUBLISHED`), reviewed mapping of quarantined responses, revocation of an unsafe published form, collection rounds and assignments (FR-FRM-005), offline packages and Android.
- Returned work: a returned or rejected form observation cannot yet be corrected through a linked submission correction revision (FR-FRM-006), because the `FORM` namespace is reserved and no submission correction exists; the approved-value amendment path applies after approval. There is no local (browser) draft and no unsaved-changes warning; only server drafts exist.
- The publication register enforces one row per revision, `version_number = 1` exactly when nothing is superseded and each version superseded at most once; contiguous version numbers are enforced by the service under the tenant lock, not by a database constraint.
- A required dimension field may still be answered with an explicit missing reason; a PRESENT bound value then fails at submit with the dimension error rather than at design time.
- Responses without a `unit_key` are unplanned contributions and are excluded from coverage when a plan exists.
- Native evidence is single-node PostgreSQL 16.13 without a pooler; on PGlite every transaction is serialised. No hosting exists and nothing was deployed.
