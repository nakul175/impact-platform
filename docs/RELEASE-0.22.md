Build number, API version and ledger counts are set by the integrator (this branch bumps no version literal); schema 23 (migration 0023; 0022 belongs to another increment and is not a dependency); domain API **170 operations** on this branch (ten added to the 160 of build 0.20.0: upload create, status, content and completion; evidence create, edit, attach and mediated content; the evidence cited by an observation and by a calculated result) and control-plane API unchanged. Roadmap Release 1 remains in progress. Proposed ledger movement (for the integrator, see "Integration notes"): FR-EVD-001 and FR-SEC-005 from PENDING to **PARTIAL**; nothing is accepted.

## Delivered

Until this build the platform held no files: the `upload_session`, `upload_part`, `file_blob` and `evidence_current` tables existed since migration 0002 with tenant fences, but nothing wrote them. This increment adds a private object store, evidence upload sessions with content checks and a scanning verdict, evidence revisions backed by a CLEAN file or an external reference, attachments that cite exact revisions, and downloads that only ever leave through the API.

**Object store.** `apps/api/impact_api/object_store.py` defines a write-once, content-addressed `ObjectStore` interface (`put`, `get`, `exists`) and implements it on the filesystem: one configured private directory (`object_store_dir`, absolute), keys `<tenant_id>/<sha256[:2]>/<sha256>`, directories 0700 and files 0600, written to a temporary file, fsynced and renamed, and every read re-hashed (`OBJECT_INTEGRITY_FAILED`, `OBJECT_MISSING`, both 503). Identical bytes are stored once per tenant; a key never holds other bytes. The store is never served directly. An S3-compatible backend is described in the module as the next adapter of the same interface and is refused by configuration (`object_store_backend` accepts only `filesystem`). Development and test runs use `.local/<run>/objects`; staging mounts the named volume `objects` at `/var/lib/impact/objects` in the API container only.

**Upload sessions (FR-SEC-005 subset, TH12, TH19 subset).** Whole-file mode for evidence media only (`purpose` EVIDENCE_MEDIA, `mode` WHOLE). `POST /uploads` declares the file name, media type, size (at most 25,000,000 bytes) and SHA-256 before any byte is sent; the media type must be on the allow-list (PDF, PNG, JPEG, plain text, CSV), the name must be a single plain name without path separators or control characters, and its one extension must be one the declared type permits (`MEDIA_TYPE_NOT_ALLOWED`, `FILENAME_INVALID`, `FILE_EXTENSION_MISMATCH`; `report.pdf.exe` and `photo.png` declared as PDF are refused). `PUT /uploads/{id}/content` (`application/octet-stream`) is the only route whose body is not JSON: the 256 KiB cap stays for every other route, this route alone accepts up to 25,000,000 bytes and never more than the upload's own declared size (`FILE_TOO_LARGE` 413, read only after the caller is authorised as the upload's owner). The bytes must match the declared size and digest exactly (`SIZE_MISMATCH`, `HASH_MISMATCH`) and their magic bytes the declared type (`CONTENT_TYPE_MISMATCH`); executable formats (PE, ELF, Mach-O, shebang scripts) are refused whatever the declaration (`EXECUTABLE_REFUSED`), PDFs naming scripts, launch or open actions, additional actions, rich media or embedded files are refused (`ACTIVE_CONTENT_REFUSED`), and text must be UTF-8 without control characters or leading markup. Refused bytes are never stored. Accepted bytes are written to the store first and then bound to a `file_blob` row in QUARANTINED; an identical replay returns the same status and different bytes are refused. `POST /uploads/{id}/actions/complete` seals the upload (QUARANTINED, blob SCANNING) in one transaction; the scan then runs outside any transaction and a second transaction records the verdict: CLEAN makes the upload CLEAN, INFECTED or FAILED makes it REJECTED. A replay of the same completion returns its receipt and finishes a scan that an interrupted attempt left unfinished. Upload sessions are visible to their owner only; another member's upload is RESOURCE_UNAVAILABLE.

**Scanning.** `content_safety.Scanner.scan(bytes) -> (state, detail)` is the pluggable interface. Two scanners ship: `eicar-signature` (deterministic: INFECTED when the bytes contain the EICAR anti-virus test file, otherwise CLEAN) and `none` (every scan FAILED, so nothing is ever downloadable). **Neither is an anti-malware engine.** The configuration names the scanner explicitly whenever an object store is configured (no default); development, test and staging use `eicar-signature`, and staging can switch to `none` with `IMPACT_EVIDENCE_SCANNER=none`. A scan that cannot read the exact recorded bytes is FAILED, never CLEAN. The verdict, scanner name, detail code and time are recorded on the blob; a database trigger makes CLEAN and INFECTED final and the blob's key, digest and size immutable for every role, and fixes an upload's declaration once created.

**Evidence revisions (FR-EVD-001 subset).** `POST /evidence` and `PATCH /evidence/{id}` (the design's draft routes, `evidence.draft.create` / `evidence.draft.edit`) take an evidence type, source, date and either a CLEAN upload of the caller or an `https://` external reference (`EVIDENCE_TYPE_REQUIRED`, `EVIDENCE_SOURCE_REQUIRED`, `UPLOAD_NOT_CLEAN`; another member's upload is RESOURCE_UNAVAILABLE). The server copies the file name, media type, size, SHA-256 and the CLEAN verdict into the revision and sets `verification_state` UNVERIFIED; none of these can come from a body (closed schemas). Replacing the file is a draft edit that writes a new revision; the earlier revision and its file stay citable.

**Attachments.** `POST /evidence/{id}/actions/attach` (`evidence.attach`, AUTHOR and DATA_STEWARD templates) cites the evidence head revision (`expected_revision`) from the current revision of an observation or calculated result that the caller can read (`TARGET_REVISION_CHANGED` when the record moved on; `EVIDENCE_ALREADY_ATTACHED` for the same pair). The citation is a row in the insert-only `evidence_attachment` register that pins both revisions; the cited record is not changed, so an approved observation or an OFFICIAL result stays immutable. `GET /observations/{id}/evidence` and `GET /calculated-results/{id}/evidence` list the citations (read access to the record and `evidence.read`; citations of evidence the caller cannot read are omitted), with the cited revision number, whether a newer evidence revision exists, whether the citing record revision is still current, and whether the caller can download it. FT-EVD-001 is exercised: version 1 is attached to an observation, version 2 is uploaded, and the observation still cites and serves version 1.

**Mediated download.** `GET /evidence/{id}/content[?revision=<evidence revision>]` (`evidence.download`) re-authorises every request, is tenant-fenced, serves only an upload whose state and blob verdict are both CLEAN and whose stored bytes still hash to the recorded SHA-256, and answers missing, hidden, quarantined, infected and failed content alike with RESOURCE_UNAVAILABLE 404. The response is `Content-Disposition: attachment` (ASCII fallback plus RFC 5987 name), `X-Content-Type-Options: nosniff`, `Cache-Control: no-store`, `Content-Security-Policy: default-src 'none'; sandbox`, `Cross-Origin-Resource-Policy: same-origin`, the allow-listed media type and the digest as ETag. Each response writes one row to the insert-only `evidence_access` register (principal, membership, exact evidence revision, blob, correlation) and one audit event. No range requests, no signed or redirect URLs.

**Audit.** Upload actions (create, content, complete, scan verdict) each write an audit event and a row in the insert-only `upload_event` register that links the event to its upload (upload sessions are not registry objects, so an audit event cannot reference one). Evidence create, edit and attach go through the ordinary command path (revision or register row, audit event, outbox event, receipt in one transaction).

**UI.** The detail view of an observation or a calculated result shows an Evidence section when `/me/access` grants `evidence.read`: cited files with version, newer-version and earlier-revision notes and a download link when permitted, and, with `upload.create`, `upload.write`, `evidence.draft.create` and `evidence.attach`, a form that hashes the file in the browser, uploads it, waits for the verdict, creates the evidence and attaches it (one operation identifier per step for the life of the panel). The form states that the scan is not malware protection.

## Limits

- Not implemented: MULTIPART uploads and part receipts (TH19 is covered for whole files only: owner checks, exact size and whole-file digest), upload cancellation, expiry sweeping (an OPEN upload simply stops accepting content after 24 hours; nothing marks it EXPIRED or removes its object), SOURCE_IMPORT uploads, archives and office documents (no qualified expansion or macro profile), password-protected files, previews, image re-encoding or metadata stripping, range requests, redaction (FR-EVD-007), verification and dispute (FR-EVD-002), sensitivity and retention fields, repository search (FR-EVD-003), annotations (FR-EVD-004), links to findings and decisions, detaching a citation, external-reference checking, and an S3-compatible backend.
- The scanners are not anti-malware engines: `eicar-signature` recognises only the EICAR test file. Active-content detection in PDFs is a byte search for name objects; names hidden in compressed object streams are not found. Text sniffing refuses markup only at the start of a file. Downloads are always attachments with `nosniff` and a sandboxing CSP, which is the main control against active content.
- A verdict is per content per tenant: a later upload of the same bytes inherits an earlier CLEAN or INFECTED verdict with the scanner that gave it; a FAILED blob is rescanned.
- Attachments do not enter review, period close, snapshots or reports; a citation is an annotation of exact revisions, not part of the approved record.
- Object files are not covered by the nightly `pg_dump`; there is no backup of the `objects` volume, no restore drill for it, and an object deleted outside the platform is reported only at download (503). Bytes written before a failed transaction stay in the store unreferenced (never served).
- Native evidence for the new registers is one test (`test_native_evidence_registers_are_fenced_and_insert_only`), executed by CI only; it was not run locally. No browser check covers the Evidence section.
