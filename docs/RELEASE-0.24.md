## Delivered

Until this build a programme's results could be read one record at a time (Results), or as a targets-versus-actuals table (Results framework). This increment adds a read-only dashboard over the same governed data: per indicator, the official value from the programme's locked snapshot, a clearly separated provisional value, target, baseline, status against the target, coverage and freshness, plus a per-indicator series across periods.

**Programme dashboard.** `GET /v1/tenants/{t}/programmes/{id}/dashboard?period_id=…&limit&cursor` (`programme_dashboard`, capability `dashboards.read`). For one programme and one period, one card per indicator instance (keyset on the instance identifier, at most 100 per page, signed cursor bound to tenant, principal, grants, route, programme and period, 15-minute expiry, no total):

- `official`: only from the latest snapshot bound to *this* programme and period (`period_snapshot_binding` → `official_result_snapshot`), and only when the result was calculated under the definition revision the instance pins. Nothing is attributed through a shared definition; the seeded fixture OFFICIAL 46.36 sits in a snapshot bound to no programme and is shown nowhere.
- `provisional`: the latest `Calculated` result of this indicator and period under the same pin, shown only when there is no official value or when it was calculated after the lock (a restatement in progress). It is never merged into the official slot; the status names which one it compared (`compared_with`).
- `target` / `baseline`: the approved target and baseline; once the period is locked, the revisions the snapshot pinned (`target_versions`), otherwise the current approved binding.
- `status`: only when a target exists (`null` otherwise), computed by the v0.18 `safe_progress` rules from stored decimals (uncapped attainment, signed deviation, undefined percentage for a zero target).
- `coverage`: from the period's obligation set only. A locked period uses the coverage recorded in the close request the snapshot was made from (`source: CLOSE_SNAPSHOT`); an open period uses the approved collection-plan revision bound to the indicator and period (`source: COLLECTION_PLAN`) over the current source rows. Counts: expected, required, received, approved, pending, missing, excluded, excepted, overdue. With no required obligation (or no plan) `applicability` is `NOT_APPLICABLE` and `approval_percent` is `null` — never 100 % and never 0 %. When the reader cannot see every source row or the plan, coverage is `UNAVAILABLE` with a reason and no counts rather than a partial count.
- `freshness`: `stale` (true / false / `null` = unknown), `stale_reasons`, `source_check`, snapshot identity and lock time, official and provisional calculation times, last source change and `checked_at`. The rule is returned verbatim as `stale_rule`: stale when the source observations or the approved plan changed since the shown value was calculated or locked (`SOURCES_CHANGED_SINCE_CALCULATION`/`_CLOSE`, `PLAN_CHANGED_SINCE_CALCULATION`/`_CLOSE`), when an approved amendment left a recalculation pending (`RECALCULATION_PENDING`, the v0.10 invalidation), or when a provisional calculation is newer than the locked official value (`PROVISIONAL_NEWER_THAN_OFFICIAL`). Unknown when the reader cannot read every source observation of the period. A successful read never makes a value fresh.

**Indicator series.** `GET /v1/tenants/{t}/indicator-instances/{id}/dashboard-series?limit&cursor` (`indicator_dashboard_series`, `dashboards.read`): one point per period that holds this programme's snapshot or this indicator's result or target, in calendar order (keyset on period start and identifier, at most 100 per page, signed cursor). Each point has the same official/provisional/target/baseline/status cells and the period state; a value carries its disaggregation breakdown when the result has one (category values, additivity, contributor counts, each displayed from its own stored value).

**Numbers.** Values are the stored decimal strings; each display is recomputed once from the stored value with the pinned definition's `display_decimals` (half-up), never taken from a stored display string and never summed. A value that is not PRESENT has `value: null` and `displayed_value: null` with its state and reason (an UNDEFINED zero-denominator ratio is never 0). Numerator and denominator are shown as stored.

**Access.** The route needs `dashboards.read` (an existing design capability; held by the fixture author, reviewer, partner and revoked actors through seeded grants, not by the enumerator): no grant at all → 403 `POLICY_DENIED`; out of scope, another tenant, a missing or wrong-kind identifier → 404 `RESOURCE_UNAVAILABLE`. Underneath, every record keeps its own read capability: `programmes.read`, `periods.read`, `indicator-instances.read` (listing predicate), `indicator-definitions.read`, `calculated-results.read` (without it no value is shown), `targets.read`, `collection-plans.read` and `observations.read` (coverage and freshness). The read writes nothing (no revision, audit, receipt). `dashboards.read` becomes delegable in custom roles because an implemented operation now uses it.

**UI.** A Dashboards area (sidebar entry; the sidebar already scrolls): programme and period pickers, a locked-snapshot or "no locked snapshot — values are provisional" line, the stale rule, one card per indicator with OFFICIAL and PROVISIONAL badges on separate rows, target, baseline, status (only with a target), coverage and freshness; an indicator trend as inline SVG (official bars from a zero baseline with a direct value label, provisional bars outlined and dashed, target ticks, legend; `role="img"` with a title and a description listing every value) and an equal "Indicator series" table including the official breakdown. Gated by `/me/access` (`dashboards.read`, `programmes.read`, `periods.read`); no new library.

## Limits

- Not implemented: dashboard authoring, saved or published dashboards and widgets (FR-ANA-001, FR-ANA-008: the design's `Dashboard` object routes remain design-only), filters beyond programme and period, drill-down and disclosure slices (FR-ANA-002), pivots, maps, portfolio comparison, alerts, external analytics access (FR-ANA-005–010), dashboard export with embedded context (FT-ANA-004's export half), milestones on cards, cumulative or converted comparisons.
- Performance: no latency, cache or load measurement (VF-PER-002 and the 60 s p95 of VF-PER-006 are not measured). Reads are uncached and computed per request, so a newly approved and calculated result is visible on the next read; each card runs a handful of indexed queries and, for an open period, reads up to 10,000 source rows per indicator to compute coverage and the digest (more than that makes coverage `UNAVAILABLE` and freshness unknown). A 100-indicator page is therefore bounded but not fast; no index was needed for correctness.
- Freshness is about governed inputs only: it does not track external source refresh (no connectors exist), so "last source success" from FR-ANA-004 is the last change of a source observation row, not an external sync time.
- Coverage of an open period is computed at read time against the approved plan revision bound to the period; it does not capture a "period obligation snapshot" separately from that pinned plan revision until the period is closed (then the close request's recorded coverage is used).
- Evidence is PGlite only (serialised transactions); no native or concurrency run of these reads was done in this slice.
