## Delivered

**Versioned keyrings for the application's own secrets** (`apps/api/impact_api/keyring.py`). The cookie secret, the invitation signing secret and the delivery secret each have a current secret plus grace secrets (`cookie_secret_previous`, `invitation_secret_previous`, `delivery_secret_previous`; `IMPACT_<FAMILY>_SECRET_PREVIOUS`, comma-separated, newest first). New values always use the current secret; values made before a rotation keep working while their secret is in grace and fail once it is removed. A key id (kid, 12 hex characters of SHA-256 over family and secret) is embedded where the format allows, with no schema change:

- CSRF tokens are `<kid>.<HMAC>`; a legacy bare-hex token still verifies against any non-retired secret.
- Signed list cursors carry `kid` inside the signed payload (one verifier now serves the domain, dashboard, planning and administration listings: `Administration.listing` reuses `Service.cursor_key`).
- Sealed delivery recipients and sealed provider logout hints start with a 7-byte header (`0x4B` + 6-byte kid) before the AES-GCM nonce; legacy unheaded values are opened by trying each non-retired secret (the GCM tag decides). Both still fit the column limits of migrations 0017/0018 (a logout hint whose ID token exceeds 16,377 bytes is no longer sealed; logout then omits the hint).
- Invitation links and recovery codes have no room for a kid: the worker, a receipt replay and code confirmation use whichever non-retired secret reproduces the stored hash (`delivery.code_secret`, `Administration.invitation_token(c=…)`).
- Development RS256 bearer tokens carry a `kid` header (`rs-` + 16 hex of the DER public key); the API verifies a kid against the current key (`dev_public_key`) and the grace keys of `dev_signing_keys` (a JSON key set); a token without a kid verifies only with the current key. `qualification/conftest.py` and `scripts/run.py` now mint tokens with the kid. Live-provider tokens are unchanged (Keycloak's JWKS by kid).

Settings validation: every secret ≥ 48 characters, a grace secret never equal to the current one, no secret shared across families (API `ValueError`; worker `INVALID_KEYRING`, exit 3). `Settings` now keeps every secret, grace secret and DSN out of its `repr` (the worker already did; it gains the two grace fields).

**Operator procedure.** `scripts/rotate_secrets.py` (`status`, `rotate --family cookie|invitation|delivery|signing|all [--grace-days N]`, `retire --family F --kid K | --all-previous | --expired`, `--dry-run`) edits either a run directory (`--config-dir`: `config.json`, `worker.json`, the development keypair and `signing-keys.json`) or an env file (`--env-file`, with `--sync-to` for a second file). Writes are atomic (temporary file, 0600, fsync, rename); output and the register beside the target (`secrets.env.keys.json` / `keyring-register.json`) name kids, dates, actor and reason, never a value. `deploy/rotate-secrets.sh` wraps it on the staging server: takes the deployment lock, edits `/opt/impact/secrets.env` and `compose.env`, recreates `api` (and `worker` for invitation/delivery) and waits for health. `deploy/compose.yaml` passes the grace variables to both containers. `scripts/bootstrap.py` keeps grace secrets and the key set across `make dev` restarts. The CI `container-stack` job gains a step: rotate all families, smoke, retire all, smoke, and check that no value from `secrets.env` appears in any output.

**Key and encryption register** (`docs/current/KEY-AND-ENCRYPTION-REGISTER.md`): every application secret, what it protects, where its kid is carried, holders and default grace; keys the application does not hold (Keycloak signing keys, database passwords, TLS) and how they rotate; and plainly what is encrypted by the application (sealed recipients and logout hints; hashed session cookies, tokens and codes) and what is not (database files, the evidence object store, dumps, droplet backups, captured mail, logs, the secrets file — protection relies on the disk, host and provider).

**Audit export (VF-AUD-001).** `POST /v1/tenants/{tenant_id}/audit-exports` (`create_audit_export`, capability `audit.export`, templates OWNER and TENANT_ADMIN, purpose-required, fresh assurance 300 s, audited). Body `{operation_id, data: {window_start, window_end, purpose, reason, limit?, cursor?}}`; purposes `SECURITY_REVIEW`, `INCIDENT_INVESTIGATION`, `REGULATORY_REQUEST`, `INTERNAL_AUDIT`; the window must have ended and be at most 366 days; at most 1000 events per page (default 500). Response: `content` (JSON Lines ordered by occurrence and event id; fields `sequence, event_id, revision_id, revision_sha256, occurred_at, action_type, outcome, real_actor_id, effective_actor_id, object_reference, correlation_id, specification_ref, chain`), `manifest` (tenant, window, purpose, page, first sequence, count, completeness, content SHA-256 and size, chain algorithm, chain start and end, generator, correlation, and an HMAC-SHA256 `seal` under a key derived from the current cookie secret with its `key_id`) and `next_cursor` (signed, 15 minutes, bound to tenant, principal, grants, window and purpose; the chain and sequence continue across pages). Each page is a command: tenant advisory lock, `authorize(…, purpose=…)` — a TENANT-scope grant without a purpose or with the stated purpose — operation receipt (exact retry returns the same page; a changed payload conflicts) and an AuditEvent of its own (`action_type` `create_audit_export`, `specification_ref` `VF-AUD-001/<purpose>`, the request's correlation id) in the same transaction. Only the projected audit columns and the revision digest are read: no payload, secret, sealed value or address can appear. `impact_api.audit_export.verify_content` and `verify_seal` verify a page. `store.authorize` gains an optional `purpose` argument (a purpose-required operation still fails closed without one; behaviour for every existing caller is unchanged).

**UI.** An "Audit export" panel under Administration → Members (`apps/web/src/AuditExport.tsx`), shown with `audit.export`: dates, purpose, reason, export, page summary with digest, chain end and seal key, download of the `.jsonl` and the manifest built in the browser, next page. A retry reuses its operation id.

## Limits

- Rotation covers the application's three secret families and the development signing key only. Keycloak signing-key rotation is documented, not exercised; database passwords and TLS are outside the keyrings. No automatic rotation, expiry alert, in-product key register or operator screen; the kid register is a file beside the secrets.
- Sealed outbox rows are not re-encrypted on rotation; intents sealed under a retired delivery key become `DEAD RECIPIENT_UNREADABLE` (and an invitation resend reuses the first intent's sealed address, so it fails too: issue a new invitation).
- No encryption at rest by the application beyond the sealed fields; database, objects, dumps and backups depend on the host and provider (register §3). No KMS/HSM, no envelope encryption, no FIPS claim.
- Audit export: the durable record of an export is its audit event (actor, time, correlation, purpose in `specification_ref`); the window, reason and content digest are kept only in the operation receipt (7 days) — a durable `audit_export` register needs DDL (proposal below). The seal is verifiable by the platform only while its cookie key is current or in grace; it is not a public signature. Denied export attempts are not themselves recorded as audit events (no denial auditing exists in the codebase). Events without an `occurred_at` are not exported. Retention and minimisation (VF-AUD-001's 365-day metadata retention) are not implemented. Each page is ≤ 1000 events and is held in memory; no streaming or file artifact.
- Evidence is PGlite only for the live checks (serialised transactions) plus the CI container rotation step; no native run was made locally (CI runs it).

**DDL proposal (not applied; migration numbers belong to the integrator):** `impact.audit_export_register(tenant_id, export_id, principal_id, purpose, reason, window_start, window_end, page, first_sequence, event_count, content_sha256 bytea(32), chain_start/chain_end bytea(32), seal_key_id, created_at)` — insert-only, `ENABLE`/`FORCE` RLS with `tenant_fence`, SELECT/INSERT to `impact_app` only, PK `(tenant_id, export_id)` with FK to the AuditEvent registry row — so the digest and window of every export outlive the 7-day receipt.

**Risks for the integrator:**

- Another v0.25 slice may also bump the domain API; keep one 1.15.0 and regenerate contracts once. `audit_export_contracts.VERSION = "1.15.0"` must match the version that ships the route.
- `store.authorize` changed signature (keyword-only use; default unchanged). The privacy slice may also need purpose-bound authorisation — it should pass `purpose=` the same way rather than adding a second mechanism.
- Format changes are backward compatible on read (legacy CSRF tokens, cursors, sealed values, kid-less development tokens) but not forward: a server rolled back to an older build cannot open values sealed with the new header (logout hints, outbox recipients) — they fail closed (`RECIPIENT_UNREADABLE`, logout without hint). Tests elsewhere that forge cursors keep working (the legacy format is accepted while the secret is current).
- The container-stack rotation step recreates the API and worker mid-job; if a later step there depends on a session created earlier it would still work (sessions do not depend on the secret), but its CSRF token would not after the retire step.
- `qualification/test_live_idp.py` was edited (7-byte header) but not run locally (needs Java and Keycloak); CI's idp job is its check.
