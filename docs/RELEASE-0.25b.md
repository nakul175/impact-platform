## Delivered

**Data-subject requests for a member of the tenant.** No participant records exist in this build, so the subject of a case is a membership of this tenant. The personal data the tenant holds about a member was inventoried in the schema and code: the member profile (`member_profile.display_name`, `email_mask`), the invitations addressed to the member (the `member_invitation` register row with `intended_email_hash` and `intended_subject`, and every `EntitlementApproval` revision payload carrying `email_mask`), the delivery intents that reference those invitations or the member's notices (`outbox_delivery.recipient_sealed`, the AES-GCM sealed address), the member's uploads (`upload_session.filename`), and — when the privacy officer names them as the member's personal data — evidence objects the member created (revision payloads, `evidence_current` file fields, object-store bytes) and import batches the member created (raw `content`, staged `preview`, `file_name`, revision payloads). Grants, role assignments, notices, authored-record metadata and audit events are included in an access export; they carry identifiers only and are kept on erasure.

Routes (all explicit in `main.py`, before the generic handlers): `GET|POST /privacy-cases`, `GET|PATCH /privacy-cases/{id}`, `GET /privacy-cases/{id}/plan`, `POST /privacy-cases/{id}/actions/approve|execute`, `GET /privacy-cases/{id}/export`.

- **Purpose-bound.** Every case operation is purpose-required. The request names its purpose (`data.purpose` on commands, `?purpose=` on reads; closed set `DATA_SUBJECT_REQUEST`) and needs a TENANT-scope grant for the capability whose `purpose` is exactly that value; a purpose-less grant never authorises a privacy operation, and the general `authorize()` still refuses every purpose-required operation. `/me/access` lists purpose-bound grants separately as `purpose_capabilities`. Missing purpose → 403 `PURPOSE_REQUIRED`; no matching grant → 403 on the collection, 404 on an item.
- **Intake** (`privacy-cases.draft.create/edit`, PRIVACY and TENANT_ADMIN): request type ACCESS or ERASURE, subject membership, reason, verification note, optional deadline and handling authority; ERASURE may name up to 50 evidence objects and 50 finished (Committed/Cancelled) import batches, each refused unless created or owned by the subject's principal (`NOT_SUBJECT_DATA`). A subject outside the tenant is refused (`SUBJECT_NOT_A_MEMBER`).
- **Plan.** `GET .../plan` returns the per-store plan the case would execute now and its SHA-256 (ACCESS: the export scope only). Stores: `MEMBER_PROFILE`/REDACT, `INVITATION_REGISTER`/REDACT, `DATABASE`/DELETE (revision payloads), `PROJECTION`/REDACT, `OUTBOX`/SUPERSEDE, `OBJECT_STORE`/DELETE. An object under an active `retention_hold` is `HELD` (`RETENTION_HOLD`, with the hold's review date); evidence bytes another available evidence revision still uses are `HELD` (`SHARED_CONTENT`). A plan above 2,000 entries is refused (`PRIVACY_PLAN_TOO_LARGE`).
- **Independent approval** (`privacy.approve`, PRIVACY, 300 s fresh assurance): the approver must be a natural person other than every author of the case and other than the subject (`INDEPENDENCE_REQUIRED`); the approver confirms the plan SHA-256 they reviewed and a changed plan is refused (409 `PLAN_CHANGED`). Erasure additionally requires that the member is no longer Active or Suspended (`SUBJECT_STILL_ACTIVE`; offboard first) and does not hold custody (`SUBJECT_HOLDS_CUSTODY`). Approval writes the plan into `privacy_store_action` (APPROVED or HELD, plan hash on every row).
- **Execute — access** (`privacy.execute`, PRIVACY, 300 s): the plan hash is re-computed and must equal the approved one; one export package (`impact-data-subject-export-v1`, canonical JSON, at most 5 MiB, sections `subject`, `invitations`, `grants`, `role_assignments`, `notifications`, `uploads`, `authored_records`, `audit_events`, each at most 1,000 items with `count`, `complete` and a SHA-256 in the manifest, plus stated limits) is stored once with its SHA-256 and a 7-day expiry. Other people are excluded by construction: no inviter, issuer or other principal is copied; authored records are identifiers only.
- **Download** (`privacy.export`, PRIVACY, purpose, 300 s): `GET .../export?purpose=…` returns the package as a JSON attachment (ETag = SHA-256, sandbox CSP), records `privacy_export_access` (insert-only) and an audit event; an expired package answers 404 `EXPORT_EXPIRED`.
- **Execute — erasure:** one transaction re-computes and compares the plan, marks each non-held action EXECUTING, then: member profile → display name `Erased member`, mask cleared; each invitation → a tombstone revision (`email_mask` `[erased]`, `erased_by_case`; a pending one becomes Revoked) followed by removal of every earlier revision payload, and the register row's e-mail hash replaced by a random value and `intended_subject` cleared; open delivery intents of the invitations and of the member's notices → SUPERSEDED `SUBJECT_ERASED` with the lease generation advanced, and every sealed address of those intents overwritten with random bytes (`recipient_redacted_at`); named evidence → upload file names cleared, `evidence_current` file fields cleared, every revision payload removed; named import batches → raw content, preview and file name cleared, every revision payload removed. Revision payloads are removed only by the SECURITY DEFINER `impact.privacy_remove_revisions`, under the `revision_removal_guard` trigger, which still requires the privacy case context, an EXECUTING DATABASE/DELETE action, a `deletion_ledger` row (written first by the definer) and no active hold. After the commit, evidence bytes are deleted from the object store (no external call inside a transaction); a second transaction records each OBJECT_STORE action COMPLETED or FAILED with an error class, sets `file_blob.purged_at`/`purge_case_id`, writes the final case revision (`Completed`, or `PartiallyCompleted` when anything is held or failed, with the held items and their review dates in the manifest) and an audit event `privacy.object_store_purge`. `execute` on a PartiallyCompleted/Executing erasure retries only the failed or pending object-store deletions (`NOTHING_TO_RETRY` otherwise). A purged blob can back no new evidence (`UPLOAD_CONTENT_ERASED`) and is never served.
- **What erasure keeps:** the subject's principal and membership identifiers (pseudonymous keys used by audit, grants, review independence and attribution), audit events, the case's own revisions and ledger, and every observation, calculated result, snapshot and report: approved official numbers are never altered (`test_erasure_reaches_every_store…` compares every CalculatedResult, Snapshot and Observation revision before and after).

**Retention sweep (job class RETENTION_SWEEP).** During its per-tenant scan the worker calls the definer `impact.worker_schedule_retention`, which queues one sweep per Active tenant when none is open and none completed within `retention_seconds` (default 86,400; 60 s–31 days). The sweep is claimed like a REPORT_EXPORT (one per batch, `lease_generation + 1`, 60 s lease on database time, one more attempt) and executed in one transaction that renews the lease (only while it is live), applies the schedule, writes one insert-only `retention_proof` row per data class (action, retention days, cutoff, affected count, SHA-256 of the sorted affected keys, worker, lease generation) and records Succeeded — every update fenced on owner and generation, so a stale holder's sweep rolls back and leaves neither deletions nor proof. Failures back off and become Failed `SWEEP_FAILED` at the attempt limit; an expired lease at the limit is Failed `LEASE_EXPIRED`. Every cutoff is the database clock (the definers ignore any cutoff a caller could supply). The fixed schedule (`impact_api/retention.py`, `GET /retention-schedule`):

| Data class | Store | Rule | Action |
|---|---|---|---|
| OPERATION_RECEIPT | `operation_receipt` | past `expires_at` (7 days, the API's idempotency window) | DELETE via definer `retention_purge_receipts` |
| UPLOAD_SESSION | `upload_session` | still OPEN past its 24-hour window | EXPIRE via definer `retention_expire_uploads` |
| PRIVACY_EXPORT_PACKAGE | `privacy_export_package` | 7 days after production | DELETE |
| OUTBOX_RECIPIENT | `outbox_delivery.recipient_sealed` | 30 days after SENT/DEAD/SUPERSEDED | REDACT (random bytes) |

`GET /retention-proofs` (`retention.read`, PRIVACY and TENANT_ADMIN) lists the latest 100 proof rows.

**UI.** A "Data-subject requests" section under People & access (`apps/web/src/Privacy.tsx`), shown only to holders of a `DATA_SUBJECT_REQUEST` grant or `retention.read`: list, new request, plan review with "Approve this plan", execute, export download, and the latest retention proof rows. No nav entry was added (the sidebar is unchanged). No browser check covers it.

## Limits

- Subjects are members only: no participant records, household members or external persons exist. The platform identity (sign-in account, `identity_profile`, `web_session`, provider account) is outside the tenant and is neither exported nor erased; control-plane recovery-contact rows (display name, e-mail mask of a nominee) are not reached. Free-text fields other members wrote (review comments, `admin_reason`, observation notes, report narrative) are not searched for the member's name.
- Evidence and import batches are erased only when the privacy officer names them; the platform does not detect personal content. Erased revision rows keep their metadata and `payload_sha256` (a hash of the removed content). Evidence citations (`evidence_attachment` rows) remain as identifiers and are omitted from listings.
- Backups: an erased value stays in every `pg_dump` taken before the erasure (and an export package in dumps taken during its 7 days) until those dumps expire (7 daily/4 weekly); the object volume is not backed up at all. No deletion replay on restore exists (FR-PRV-006, TH27 untested).
- Holds are honoured and reported but there is no API to place or release a hold (tests insert `retention_hold` rows directly); a held item is not erased later by the same case — a new case is needed after release. No rejection, on-hold or deadline handling of cases; no response-deadline policy; no subject self-service.
- Execution is synchronous inside the request (bounded: 2,000 plan entries, 8 s statement timeout); a worker-executed privacy job does not exist. An email intent whose lease holder is mid-send when the case supersedes it may still be delivered once (the stale outcome is refused).
- Retention: one fixed schedule for every tenant, no tenant-approved retention policy objects (VF-PRV-002 asks for approved record and evidence policies before collection: not delivered), no diagnostic-log or AI-content classes (no such stores exist), `oidc_logout_token` stays purged by the back-channel handler, bytes an expired OPEN upload received stay in the object store (the worker has no object-store access), operation receipts are deleted at most 5,000 per class per sweep. No delete of expired export artifacts (`report_export_artifact`).
- Evidence: PGlite for every test; natively on PostgreSQL 16.13 for the files listed below (14 + worker/evidence regressions). No browser check; no concurrency test of two erasures or of a sweep racing an erasure.
