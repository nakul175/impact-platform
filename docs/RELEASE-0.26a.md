# v0.26a — Usable staging

Build 0.25.0 → 0.26.0; schema 27 → 28 (migration `0028_usable_staging.sql`); domain API 1.15.0 → 1.16.0 (197 → 207 implemented operations; policy rows 328 → 337; capabilities 226, with `reference-data.manage` added and the design-only `report-templates.draft.create` gone with the design row its path replaced; delegable capabilities 116 → 117; fresh-assurance operations 44 → 53; purpose-required operations 19, unchanged); platform API 1.6.0 → 1.7.0 (35 → 42 operations). Release 1 remains in progress; nothing is accepted (ledger: see "Requirement status").

This increment removes the four blockers to user acceptance on the hosted service that `docs/current/RELEASE-1-ACCEPTANCE-GAPS.md` §1 listed as A1–A4, without weakening any independence rule: every review that needed a different natural person still does, no synthetic or login-less approver exists, and no waiver was added. A5 (imports and period close) is not addressed here.

## Delivered

### A1 — reference data for a new tenant

Six governed tenant-administration commands (the `administration_contracts.COMMANDS` pattern: capability `reference-data.manage` at TENANT scope with a purpose-less grant, OWNER and TENANT_ADMIN templates, authentication within 300 seconds, a stated reason, an audit and an outbox event per record written, an operation receipt; exact retry returns the receipt, a changed payload under the same operation ID is `CONFLICT_OPERATION`, a stale `expected_revision` is `CONFLICT_VERSION`):

| Route | Operation | Writes |
|---|---|---|
| `POST /reporting-calendars` | `create_reporting_calendar` | an Active `ReportingCalendar` (title, IANA zone, MONTHLY/QUARTERLY/ANNUAL, first and last year, 1–5 years) and its Open `Period`s: contiguous, non-overlapping, local midnight of the first day of each period in the calendar's zone held as UTC instants with an exclusive end, codes `2026-Q1` / `2026-01` / `2026` |
| `POST /reporting-calendars/{id}/actions/extend` | `extend_reporting_calendar` | 1–5 further years (a new calendar revision; at most 20 years in all); a fixture or earlier calendar without first/last year is refused (`CALENDAR_NOT_EXTENSIBLE`) |
| `POST /workflow-templates` | `create_workflow_template` | an Active single-stage template `{independent: true, required_approvals: 1}` — the only review shape this build executes |
| `POST /report-templates` | `create_report_template` | an Active report template (1–20 sections with codes, headings, required flag and narrative limit; no numeric binding is pre-set; duplicate section codes refused) |
| `POST /geographies` | `create_geography` | an Active geography (title, code; a duplicate active code refused) |
| `POST /reference-defaults` | `apply_reference_defaults` | the standard set below; refused once applied (`REFERENCE_DEFAULTS_APPLIED`) |

**The standard set** (`impact_api/reference_contracts.py` `DEFAULTS`, deterministic object identifiers derived from the tenant): a quarterly calendar "Standard quarterly calendar" in the tenant's reporting zone covering the current and the next calendar year of that zone at the moment it is applied (8 Open periods); the review template "Standard independent review" (one independent approval); the report template "Standard results report" (sections Summary and Results required, Data quality and caveats optional, language `en`); and the geography "Organisation-wide" (code ORG) unless an active ORG geography exists. One click under **People & access → Reference data → Set up the standard reference data**.

*Why not at activation itself:* activation is a control-plane command on the `impact_platform` role, which stays inside the restrictive object-type lists of migrations 0013/0014 (CLAUDE.md rule 20): the control plane never writes business reference records. The set is applied through the normal governed tenant-administration path by the tenant's own administrator, as the first step after initial access, and the start page and Deployment guide name it as that step.

### A2 — onboarding profile `initial-access-v2`

`apps/api/impact_api/bootstrap_profile.json` is now generated by `scripts/build_access_profile.py` from the access policy (a unit test fails when it is stale): each role bundle holds exactly the capabilities of the implemented, purpose-less operations whose policy row names its role template. Roles: TENANT_ADMIN (29, now including `reference-data.manage`, `grants.read`, `retention.read`), MEL_ADMIN (69), AUTHOR (74), REVIEWER (37), PROGRAMME_MANAGER (53), DATA_STEWARD (35), ENUMERATOR (9), ANALYST (23), PRIVACY (8, the purpose-less part only), AUDIT_READER (3; the policy's tenant OPERATOR template renamed so it is never confused with a platform operator) and EXTERNAL (21). Together they cover all 117 delegable capabilities of implemented operations; no role carries a purpose-required capability. The seven purpose-required capabilities (`audit.export` and the six privacy-case capabilities) are listed separately as `purpose_bound`: migration 0028 replaces `impact.apply_initial_authority` so the reviewed delegation ceiling also covers them (every other condition unchanged; a v1 manifest has no such list and is applied exactly as before), and they can be held only as purpose-bound grants issued through A4. Approval capabilities are ordinary capabilities: whoever holds one still cannot approve anything they authored (natural-person independence is enforced per action, unchanged).

New tenants use v2. A v1 request still pending at deployment is refused at acceptance or approval (`ACCESS_PROFILE_CHANGED`, the profile hash it pinned no longer matches); cancel it and propose again. **Existing tenants that already applied v1 keep their v1 ceiling**: no upgrade path is built in this increment (staging has no applied tenant; a reviewed owner-proposes / independent-operator-approves widening, like authority renewal, is the recorded follow-up).

### A4 — reviewed purpose-bound grants

Tenant-administration route `purpose-grants` (`administration.py` `purpose_grant`):

- `POST /purpose-grants` (`request_purpose_grant`, `grant.request`): one member, one capability, one purpose, a scope, an expiry and a reason. Refused for a capability that is not the capability of an implemented purpose-required operation (`NON_DELEGABLE_CAPABILITY` — purpose-less capabilities travel in role bundles), for a purpose that operation does not accept (`PURPOSE_NOT_PERMITTED`: privacy capabilities `DATA_SUBJECT_REQUEST`; the audit export its four purposes), for a non-TENANT scope (`PURPOSE_GRANT_REQUIRES_TENANT_SCOPE`; purpose-bound authorisation reads TENANT-scope grants only), beyond 90 days or the member's own expiry, beyond the requester's delegation ceiling (`DELEGATION_NOT_PERMITTED`), for the tenant owner (`LAST_OWNER_PROTECTED`, as for every access change) and while the member already holds that capability for that purpose (`PURPOSE_GRANT_EXISTS`).
- `POST /purpose-grants/{id}/actions/approve|reject` (`grant.approve`): only by a natural person different from the requester and from the member (`INDEPENDENCE_REQUIRED`); approval rechecks the membership revision, the requester's continuing `grant.request` and both administrators' ceilings, then writes one `Grant` with the `purpose` set, issued by the approver, and advances the member's subject epoch.
- `GET /purpose-grants` (`access-requests.read`) lists the requests and their outcome (`grant_id`).

All three commands need authentication within 300 seconds and are audited. A tenant onboarded with v2 has two administrators; the second administrator requests a privacy grant for themself and the owner approves it (the owner's own access is never changed this way).

### A3 — governed operator onboarding and sign-in accounts, no console

Control-plane operations (platform API 1.7.0, `impact_api/operators.py`, `operator_contracts.py`), identity-authorised like the rest of `/v1/platform`, each committing a `platform_event` (tenant-less for nominations and operator-created accounts — migration 0028 lets `tenant_id` be NULL for exactly these actions) and a `platform_receipt` together, after fresh MFA:

- `GET /v1/platform/operators`: for an operator, the operators, the latest 100 nominations, the registered people of this issuer (name, masked address, signed in, operator) and the accounts created here; for anyone else, only the nominations addressed to their verified address and the accounts they created.
- `POST /v1/platform/operator-nominations` (operator): an e-mail address (stored as SHA-256 and a mask only), an operator expiry no later than the nominator's own and within 365 days, a reason; the nomination is open 7 days. Nominating oneself is refused (`SELF_NOMINATION`), as is an address of the nominator's natural person (`INDEPENDENCE_REQUIRED`) or of a current operator (`ALREADY_OPERATOR`); one open nomination per address (`NOMINATION_PENDING`).
- `POST /v1/platform/operator-nominations/{id}/actions/accept|decline` (the person signed in with that verified address) and `cancel` (any operator). Acceptance runs the SECURITY DEFINER `impact.accept_operator_nomination`, the only run-time writer of `platform_operator`, which rechecks everything: open and unexpired, the nominating operator still active, the actor's verified address, a natural person different from the nominating operator and from every active operator. A trigger refuses an acceptance recorded any other way. The nominating operator cannot accept on the nominee's behalf (the nomination is not addressed to them: 404).
- `POST /v1/platform/accounts` (create a sign-in): an operator for any address (optionally linked to an open nomination for that address), or the current owner of an Active tenant for an address with a pending invitation of that tenant (`INVITATION_REQUIRED` otherwise; the definer `tenant_pending_invitation` answers yes or no only); never for one's own address (`SELF_ACCOUNT`). The account is created at the identity provider with exactly the logic of `deploy/add-user.sh` (`impact_api/provider_admin.py`, now shared with `deploy/keycloak_admin.py`): e-mail as user name, e-mail marked verified, a temporary password, required actions UPDATE_PASSWORD and CONFIGURE_TOTP. It is registered as a platform identity without authority by the definer `register_provider_account_identity` (only for an active qualification's issuer). The provider call happens outside any transaction: authorisation and replay first, then the call, then a second transaction that rechecks the authority and records it.
- `POST /v1/platform/accounts/{id}/actions/reissue`: a new one-time password, only while the person has not yet chosen their own (`ACCOUNT_IN_USE` afterwards), by an operator or the tenant's current owner, with the address typed again (`EMAIL_MISMATCH`).

**The one-time password** (five groups of four unambiguous characters) is in the live response only. It is never stored, logged, written to the receipt or the event (both hold the account record with `temporary_password: null`), and an exact retry returns the receipt without it. The UI shows it once with copy buttons and the instruction to hand it over in person or by phone. An existing account at the provider is registered without any password change.

**Staging wiring:** `deploy/update.sh` generates `IMPACT_PROVISIONER_SECRET` once and runs `deploy/keycloak_admin.py provisioner`, which ensures the confidential client `impact-provisioner` in the `impact` realm: client credentials only (no browser, password or implicit flow), its service account holding exactly the realm-management roles manage-users, view-users and query-users (any other role found is removed). The API reaches Keycloak's admin API on the internal network (`IMPACT_PROVIDER_ADMIN=keycloak`, `http://keycloak:8080`, `deploy/compose.yaml`) with that client; it never holds the master-realm administrator. Locally, `make dev` and the PGlite suites use the development backend (`provider_admin: development`): created accounts go to the development users file and sign in on the development login page; the first sign-in consumes the temporary flag.

## Limits

- **A first organisation still needs three different people** — by the unchanged rules, not by this build: the operator who requests the organisation, its owner, and an operator who is neither of them to activate it (the same independent operator also approves the recovery contact and initial access). With the deployment owner as requesting operator, recovery contact and second administrator, that is one colleague as second operator and one as organisation owner (DEPLOYMENT-GUIDE §4).
- **Natural persons are asserted, not proven.** Each provider account is its own natural person. An operator who creates an account sees its one-time password; the independence of that account rests on handing it over and on the person choosing their own password and authenticator — the same trust as `add-user.sh` (and the reason the directory flags "sign-in created by the nominating operator" and the acceptance event records it). The platform cannot detect one human holding two provider accounts.
- No e-mail provider: nothing is sent; the one-time password and invitation links are handed over by people.
- The provisioner service account can manage every user of the realm (Keycloak's manage-users), including resetting the deployment owner's credentials; its secret is in `secrets.env` (0600) and the API environment only. It is not rotated by `deploy/rotate-secrets.sh` (re-running `update.sh` after replacing the value in `secrets.env` re-aligns the client).
- Operator authority still expires after its stated term and is not renewable through the UI (a new nomination by another operator is the path); deactivating an operator is not in the UI.
- Existing v1 tenants keep their v1 ceiling (no reviewed upgrade path yet); pending v1 initial-access requests must be re-proposed.
- Calendars are created in whole calendar years; fiscal years starting in another month, custom periods and calendar retirement are not offered. Report templates carry no numeric bindings; bindings are chosen per report package as before.
- TENANT_ADMIN holds `reference-data.manage` but not the reads of calendars, periods and templates: the Reference data panel reports what it created; programme managers (MEL_ADMIN, AUTHOR, REVIEWER, PROGRAMME_MANAGER) see the records in Measurement setup.
- A5 (imports making a period unclosable) is unchanged.
