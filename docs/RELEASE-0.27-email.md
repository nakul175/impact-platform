# v0.27 — Email readiness: qualified SMTP path, provider-ready configuration, owner decision pack

Branch `release/0.27-email-readiness` from `main` at 25a8dca (build 0.26.0; schema 28; domain API 1.16.0 and platform API 1.7.0 unchanged; no migration, no contract change, no version bump — the integrator bumps). The ledger is not moved by this slice; proposals are in "Integration notes". Real email still depends on an owner decision (the provider and the sending domain); this increment makes switching it on a configuration step and documents that step for a non-engineer.

## Delivered

**The STARTTLS and AUTH path is qualified.** Until now the worker's `SmtpAdapter` had only ever spoken plain SMTP to a loopback sink: STARTTLS with certificate verification and AUTH were written but never exercised (CLAUDE.md §1, §11). `qualification/smtp_sink.py` can now behave like a provider's submission port: it advertises and performs STARTTLS with a certificate generated per run (`make_certificate`, an EC P-256 self-signed certificate with DNS and IP subject alternative names, written only under the test's temporary directory; `*.pem`/`*.key` are git-ignored anyway), advertises AUTH PLAIN and LOGIN and checks credentials, answers scripted authentication refusals, can advertise STARTTLS without honouring it, and records every verb with whether it arrived under TLS. The adapter is unchanged in behaviour for the loopback capture and gains two options: `smtp_ca_file` (an extra PEM trust anchor passed to `ssl.create_default_context(cafile=...)`, for a private relay; the system store is used when empty) and `smtp_starttls` (`auto`, the default and previous behaviour — mandatory upgrade with verification for every non-loopback host, plain SMTP to loopback; `required` — mandatory for every host, loopback included). The matrix executed against the in-process TLS server, with the provider's host name resolved to it so that every non-loopback rule applies:

The adapter never falls back to clear text: a failed upgrade raises and the connection is closed; the sink's `commands_in_clear()` is empty in every negative case. `WorkerSettings` also refuses a username without a password (`SMTP_CREDENTIALS_INCOMPLETE`; a password without a username is inert, AUTH is only attempted with a username), an unreadable CA file (`SMTP_CA_FILE_UNREADABLE`) and an unknown STARTTLS mode (`INVALID_SMTP_STARTTLS`); the password stays out of `repr`.

**Send rate limits, applied at claim time.** `apps/api/impact_api/mail_rate.py` adds `EmailRateLimiter`: two sliding windows of one length (`email_rate_window_seconds`, default 60), a global one (`email_rate_limit`) and one per tenant (`email_tenant_rate_limit`); 0 means no limit (the default, so nothing changes for a deployment that sets nothing). The worker consults it in `Worker.claim`: when the window still admits at least `batch_size` emails the claim statement is the one of v0.16, byte for byte; otherwise in-app rows are claimed first (never limited) and EMAIL rows only up to the allowance, in a second statement with the same predicate and ordering. Rows left behind stay PENDING and due with their `attempts` and `next_attempt_at` untouched, so **rate limiting can never make a delivery DEAD and never spends one of its six attempts**; they are claimed on a later iteration (`test_email_readiness.py::test_email_rate_limit_defers_claims_without_spending_attempts_and_spares_in_app`: three invitations under a limit of two, the third waits with attempts 0 and no error class, in-app notices still claimed, the window reopens after 61 s on the database clock, a per-tenant limit of one, and every intent sent with attempts 1 once no limit applies). Claims are counted, not successful sends, because a refused submission still counts toward a provider's quota. The windows live in the worker process (no table, no migration) and use the database time already fetched for the claim; with more than one worker each process has its own allowance, so the provider limit is divided between them. Deferred counts are logged (`delivery claims deferred by the email rate limit tenant=… deferred=…`) and kept on `Worker.email_limiter.deferred`; the heartbeat and `empty_summary()` are unchanged.

**Provider-ready configuration.** `deploy/compose.yaml` passes `IMPACT_SMTP_STARTTLS`, `IMPACT_SMTP_CA_FILE`, `IMPACT_EMAIL_RATE_LIMIT`, `IMPACT_EMAIL_TENANT_RATE_LIMIT` and `IMPACT_EMAIL_RATE_WINDOW_SECONDS` to the worker from `SMTP_STARTTLS`, `SMTP_CA_FILE`, `EMAIL_RATE_LIMIT`, `EMAIL_TENANT_RATE_LIMIT`, `EMAIL_RATE_WINDOW_SECONDS` (defaults `auto`, empty, 0, 0, 60), and `deploy/update.sh` copies those keys from `config.env` beside the existing `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`. `SMTP_PASSWORD` belongs in `secrets.env`: every `KEY=value` line of that file already reaches `compose.env`, and every value of it is scrubbed from the deployment log and the status page, which `config.env` is not. No value is committed anywhere. The worker shares the `mailsink` container's network namespace, which is on the `edge` network (not `internal`), so a provider is reachable without a wiring change; the mail check below proves the route. `IMPACT_SMTP_CA_FILE` is passed through but nothing mounts a file for it yet (a public provider needs none).

**`deploy/mail-check.sh <address>` and `deploy/mail_check.py`.** The owner's console script runs `deploy/mail_check.py` inside the worker's container (`compose run --rm -T -v <repo>/deploy/mail_check.py:/app/deploy/mail_check.py:ro worker …`, so the Dockerfile is untouched and the script always matches the checked-out revision) with exactly the worker's SMTP environment and network. The script (standard library only) applies the adapter's rules — STARTTLS with verification required for any non-loopback host or under `required`, no clear-text fallback, credentials only after the upgrade — sends one plain message ("Impact Platform email check", `Auto-Submitted`, a `Message-ID` on the public host) and prints the SMTP conversation captured from `smtplib`'s debug channel with every secret removed: the argument of any `AUTH` command and every client line of an AUTH exchange become `[redacted]`, and the password, the username and their base64 forms (bare, and as the PLAIN `\0user\0pass` string) are removed wherever they would appear. The last line is one JSON object (`ok`, `reason`, `to`, `host`, `port`, `tls`, `tls_version`, `auth`, `message_id`); exit 0 accepted, 1 refused (`SMTP_AUTHENTICATION`, `STARTTLS_UNAVAILABLE`, `TLS_FAILURE`, `RECIPIENT_REFUSED`, `SMTP_PERMANENT_REJECTION`, `SMTP_TRANSIENT_REJECTION`, `SMTP_CONNECTION`), 2 configuration (`INVALID_ADDRESS`, `SMTP_CREDENTIALS_INCOMPLETE`, `INVALID_SMTP_STARTTLS`, `INVALID_SMTP_PORT`, `SMTP_CA_FILE_UNREADABLE`, `INVALID_SMTP_FROM`). The wrapper validates the address, requires root and `compose.env`, and appends one line (address and outcome, never the transcript) to `state/admin-actions.log`. Unit tests run the script against the TLS sink for PLAIN and LOGIN, a wrong password, a provider without STARTTLS, an untrusted certificate, a closed port and each configuration refusal, and assert that no form of the credentials appears in the output.

**Owner decision pack.** `docs/current/EMAIL-PROVIDER-DECISION.md`: Amazon SES (Mumbai region), Postmark and Brevo compared on cost at our volume, setup effort, SMTP details, bounce information and data location, with the provider pages read on 2 October 2026 linked and every unconfirmed fact marked; the four DNS records (SPF, DKIM, DMARC, Return-Path) with example values and the order of steps; the fifteen-minute switch-over on the droplet; what stays unsolved (bounce webhooks, inbound, per-process limits, reputation, Keycloak's separate "Forgot password" SMTP setting). Bottom line: Postmark first (least setup, $0 until more than 100 emails a month, then $15), SES in Mumbai if one AWS bill is wanted, Brevo as the free fallback with a logo in every email — and nothing can be switched on before the owner provides a sending subdomain he controls.

**Bounce handling, minimum.** SMTP-time permanent failures already map to the DEAD classes (`RECIPIENT_REFUSED` for a refused recipient, `SMTP_PERMANENT_REJECTION` for any other 5xx; both now also qualified over TLS and AUTH); `SMTP_AUTHENTICATION` and `SMTP_SENDER_REJECTED` stay retried because they are the operator's to fix. Everything a provider learns after accepting the message (hard bounce, complaint, suppression) is invisible to the platform. Design for provider bounce webhooks, **not built**:

- One control-plane route per provider family, `POST /v1/platform/bounces/{provider}` (Postmark JSON, SES through SNS with signature verification, Brevo JSON), authenticated by a per-route shared secret from `secrets.env` carried in a header or basic auth (never a query string), body bounded by `bounded_body` like the back-channel logout, answered 204 and processed asynchronously.
- The handler finds the delivery by `Message-ID` (`<event_id@host>`; the provider echoes it, or the `X-Impact-Delivery` header) and writes an insert-only `delivery_feedback` row (tenant, event, provider, kind HARD_BOUNCE / SOFT_BOUNCE / COMPLAINT / SUPPRESSED, provider reference, received_at, SHA-256 of the payload; no address, no body) under RLS, through a SECURITY DEFINER because the platform role holds no tenant tables; a hard bounce or complaint also sets `outbox_delivery.state='DEAD'` with `last_error_class='BOUNCED'`/`'COMPLAINED'` only from `SENT`, fenced on `event_id`, and raises `DELIVERIES_DEAD`.
- A per-tenant **suppression** check at intent creation (`delivery.enqueue`): an address whose hash has a hard bounce or complaint within 90 days gets no new EMAIL intent; the invitation or notice is recorded as `SUPPRESSED` and the inviter sees it in the Work Center. Keyed by `email_hash`, never the clear address.
- Replay protection by provider reference (insert-once), one migration (`delivery_feedback`, grants to `impact_platform` through a definer), a `feedback` panel in the Workers console, a unit test per provider payload sample and a live test with the synthetic sink posting feedback for its own messages.
- Not in scope even then: inbound mail, list-unsubscribe (no list mail exists), and reputation monitoring, which stays on the provider's dashboard.

## Limits

- No real provider was contacted: every TLS and AUTH case runs against the in-process server with a per-run self-signed certificate. STARTTLS, verification, PLAIN and LOGIN are now exercised; CRAM-MD5, OAuth2 (XOAUTH2), implicit TLS on port 465, provider-specific headers (Postmark's `X-PM-Message-Stream`, SES configuration sets) and IPv6 are not.
- `smtplib.login` tries the advertised mechanisms in turn (CRAM-MD5, PLAIN, LOGIN) and raises only when the last one is refused, so a provider that offers PLAIN and LOGIN sees two failed AUTH commands per refused attempt; the worker's outcome is one `SMTP_AUTHENTICATION` retry either way.
- Rate limits are per worker process and count claims; a provider's own throttling (`421`/`450`/`452`) is still a retried `SMTP_TRANSIENT_REJECTION` with the normal backoff, which does count an attempt.
- `mail-check.sh` sends through the worker's environment; a provider that rejects the From domain or the recipient shows up in the transcript, but DKIM/SPF results are only visible in the received message's headers. The script was unit-tested against the sink and shell-checked for arguments and strictness; it was not run against a live Compose stack in this session (CI's `container-stack` does not yet call it — proposed below).
- Changing `config.env` alone does not restart the worker (update.sh recreates containers only for a new commit): the decision pack gives the `compose up -d worker` command.
- Keycloak's own SMTP setting ("Forgot password") is not configured by `update.sh`; manual step documented.
- Bounce webhooks, suppression, inbound: designed, not built. `IMPACT_SMTP_CA_FILE` has no mount.
