## Delivered

Build 0.26.0 collected responses on one undeclared language, with no notion of who was expected to report what, and a returned form observation could not be corrected because the `FORM` namespace is reserved. This increment adds language versions inside the reviewed and published Form revision, rounds and assignments with coverage per round, and a correction path for returned work. Every independence, authorisation, immutability and audit rule is unchanged.

**Language versions (FR-FRM-004).** A form declares its `default_language` (the language of the field definitions themselves; a BCP-47 code such as `en`, `hi` or `pt-BR`) and `translation_versions`, each a language code, an optional display name and texts keyed by the stable field codes: a `label`, optional `help` and choice labels keyed by the stable choice codes. Translations only add text: an unknown field or choice code is refused (`FORM_TRANSLATION_INVALID`), as is a translation without a declared default language, a language listed twice or the default language listed as a translation (`FORM_LANGUAGE_INVALID`). Completeness is checked where the version is checked — submission for review, approval and publication: every field label and every active choice label must exist in each declared language (`FORM_TRANSLATION_INCOMPLETE`); help text is optional in every language. `GET forms/{id}/completeness` (`forms.read`) lists, for the head revision, each language with its gaps (field code and, for a choice label, the choice code), so a translator sees what is missing before review. The reviewer sees the languages in the review candidate because they are part of the Form revision, and the published version carries them unchanged; revising a published form starts a new draft and changes nothing collection sees until a successor publishes. A submission records the `language` presented to the respondent, which must be the version's default language or one of its translations (`FORM_LANGUAGE_NOT_AVAILABLE`); answers carry the stable codes whatever the language, so the same choice submitted in English and in Hindi maps to one response code (FT-FRM-004). The fill-in dialog offers a language switch when the version declares languages and shows the translated labels and choice labels with the form's own text as the explicit fallback; the designer edits the default language and the language versions (one text per question and per choice).

**Collection rounds and assignments (FR-FRM-005).** A supervisor (`collection-rounds.draft.create`/`.draft.edit`: MEL_ADMIN, PROGRAMME_MANAGER) defines a `CollectionRound` on the route `collection-rounds`: the form, a published `form_version` of that form (`FORM_VERSION_NOT_PUBLISHED` otherwise), a `period_id`, a title, a `due_at` and the `expected_units` (unit keys, at most 500, unique). Form, version and period are pinned at creation (`ROUND_IMMUTABLE`); title, due time and expected units may change, except that a unit with an assignment cannot be dropped (`ROUND_UNIT_ASSIGNED`). An `Assignment` (the design route `assignments`, now implemented) is one stable task per round and unit: `round_id`, `form_version` (must be the round's, `ASSIGNMENT_FORM_VERSION_MISMATCH`), `assignee_id` (an active member who holds `submission.submit` at TENANT scope, `ASSIGNEE_INELIGIBLE`), `unit_key` (one of the round's expected units, `ASSIGNMENT_UNIT_NOT_EXPECTED`; one assignment per round and unit, `ASSIGNMENT_UNIT_TAKEN`) and `due_at`. Round, version, unit and assignee are immutable through patch (`ASSIGNMENT_IMMUTABLE`; only the due time moves); the assignee changes only through `action_assignments_reassign` (`assignment.reassign`, PROGRAMME_MANAGER), which writes a new revision with the new assignee, `previous_assignee_id` and the `reason` — the revision chain is the history, the task identity stays. A response names its `assignment_id`: the unit key comes from the assignment (a different one is `ASSIGNMENT_UNIT_MISMATCH`), only the current holder may create or submit it (`POLICY_DENIED`, reason `ASSIGNMENT_NOT_HELD`), and submitting completes the assignment in the same transaction (lifecycle `Completed`, its own audit event), after which nobody can respond to it again and it cannot be reassigned (`ASSIGNMENT_COMPLETED`) — the old holder of a reassigned task can never produce a second eligible completed visit (FT-FRM-005). An assignment is work, never authority: it grants nothing and the assignee cannot approve the observations their response produced (`INDEPENDENCE_REQUIRED`). My work: `GET assignments` lists, for a member without `assignments.draft.create` at TENANT scope, only the assignments they hold; a supervisor lists every assignment their read scope admits. `GET collection-rounds/{id}/coverage` (`collection-rounds.read`) gives, per expected unit, the assignment, its holder and state and whether a Submitted (never a quarantined) response was received, and the counts: expected, assigned, received, missing, unassigned and `coverage_percent` = Σreceived / Σexpected rounded half-up to two places; a round that expects no unit is `NOT_APPLICABLE`, never 100 %.

**Correction of returned work (FR-FRM-006).** `POST submissions/{id}/actions/correct` (`submission.correct`, AUTHOR and ENUMERATOR; the same additional capabilities as submit when the version binds indicators) takes the full corrected answer set, a reason and the workflow version. It applies to a Submitted response on the current published version whose produced observations have all been returned by their reviewer (`CORRECTION_REQUIRES_SUBMITTED_RESPONSE`, `CORRECTION_REQUIRES_RETURNED_WORK`, `FORM_VERSION_SUPERSEDED`); the corrected answers are validated against the pinned version exactly as a submission is (a hidden answer is still `ANSWER_NOT_RELEVANT`). The submission gets a new Submitted revision carrying `correction_of_revision` (the revision it supersedes) and `correction_reason`; each returned observation gets a new Draft revision with the corrected content under its existing identity and source key — the returned revision is kept, nothing is edited — and is submitted into a new independent review in the same transaction. The corrector is written as a natural author of the submission and of each corrected observation, so the corrector can never approve the correction. Receipts, replay (same operation identifier and payload) and stale revisions behave as for every command.

## Limits

- Languages: no separate approval per language version (the whole version is approved once, with its languages; FR-FRM-004's "review approves a language version separately" is not implemented), no machine-proposed translations, no consent-text class (every label is treated alike), no translation of the form title or of answer-status labels, no right-to-left layout work; the client's fallback is the form's own text, shown as such.
- Rounds: no sampling frame, visits or sample replacement; a round has no lifecycle beyond its draft revisions (it is in force from creation); the period is not checked against the form's programme calendar; a response can still be submitted without an assignment (unplanned, as before); a quarantined response leaves its assignment open; collection plans and round coverage are separate views (a plan counts source keys, a round counts assignments). No worker involvement, no reminders for due assignments.
- Correction: only when every produced observation is Returned (a response with one approved and one returned observation cannot be corrected: `CORRECTION_REQUIRES_RETURNED_WORK`); not for quarantined or superseded-version responses; the whole answer set is resubmitted; no local draft of a correction.
- UI: the designer and fill-in dialog cover languages (`forms-browser` now designs a form with a default language and a complete Hindi version, checks the completeness read, switches the fill-in dialog to Hindi and finds the presented language on the submission); rounds, assignments, My work and coverage are API-only in this increment (no screen, no browser check).
- Evidence on this branch (2 October 2026, shared sandbox, one heavy run at a time): focused PGlite runs of `qualification/test_forms_rounds.py` (4 passed) and `qualification/test_forms.py` (24 passed, 1 native-only skipped, unchanged), `test_version_unit.py` and `test_usable_staging_unit.py` (16 passed), `make lint`, the web build (`tsc --noEmit && vite build`) and the `forms-browser` group (4 checks, Chromium 153) clean; no full PGlite, native, other browser or live-provider run was made here — CI runs them on the pull request. `docs/evidence/` is unchanged.
