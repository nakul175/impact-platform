## Delivered

**The problem (A5).** Period close refuses while any observation of a programme indicator in the period is not named by the approved collection plan (`UNPLANNED_VALUES`, `period_governance.py`). Since v0.21 an imported value's source key was `<batch id>/<unit key>/<indicator id>`: the batch identifier is minted when the batch is created, so no plan could name the key in advance, and every import into a planned indicator left the period unclosable until the values were resolved by hand. `docs/current/RELEASE-1-ACCEPTANCE-GAPS.md` §1 A5 also recorded as unverified whether a reviewed plan change naming the exact imported keys clears the blocker.

**Plannable source identity.** An imported value's source key is now `<unit key>/<indicator id>/<period id>` (`imports.source_key()`), in the reserved namespace `IMPORT`. Each part is known before the file exists — the planner knows the unit, the indicator instance and the period the plan is for — so an obligation `{"source_namespace": "IMPORT", "source_key": "<unit>/<indicator>/<period>"}` can be approved in advance, and `coverage()` then matches the imported observation exactly as it matches a manual or form observation: an approved imported value is APPROVED coverage, never an unplanned one. The period is part of the key because a source key is unique in a tenant for ever (`source_key_registry`): the same unit and indicator imported again in a later period is a new identity and never collides (the form convention `<unit>/<indicator>` has no period and cannot be reused across periods; imports keep that property). Which batch produced a value is recorded where it was already recorded — `source_version` on the observation is the committed batch revision, and `import_unit_register` holds the batch id, revision and row number per unit, indicator and period — never in the key. `import_unit_register`'s primary key (tenant, indicator, period, unit key) and the duplicate rules (`DUPLICATE_UNIT_PERIOD`, `DUPLICATE_IN_BATCH`, `DUPLICATE_SOURCE_KEY` against form observations) are unchanged.

**The preview tells the planner and the importer.** Every staged value in the preview now carries its `source_key`. When the previewer can read the indicator's approved collection plan for the period, each value also carries `planned: true|false` (whether that plan names the key), the preview counts gain `unplanned` (accepted values no approved plan names) and `plan_check.evaluated_indicators` lists the indicators whose plan was compared. When there is no approved plan or the caller cannot read it, no value is marked either way and the indicator is absent from `evaluated_indicators` — the preview never guesses. The flags are part of the preview and therefore of the preview hash: a plan amendment approved between preview and commit makes the batch `PREVIEW_STALE`, as any other change the outcome depends on does, and the batch is previewed again.

**Close counts imported, approved values as planned; truly unplanned values still block.** No change was needed in `period_governance.py` or `measurement.py`: the close preview, coverage, the dashboards' open-period coverage and the close snapshot's obligation coverage all run over (namespace, source key) pairs, and the imported pairs now match. An imported value no plan names still blocks close with `UNPLANNED_VALUES` until an independently approved plan amendment (`measurement-changes`, target kind CollectionPlan) names its exact key — which `validate_plan` admits because the existing observation belongs to the same indicator with its event inside the period — or the value is resolved. Both outcomes are tested (below).

**UI.** The import preview shows "(planned)" or "(unplanned)" beside each value's interpretation, the value's source key in that cell's tooltip, and a note when accepted values are unplanned, stating that they commit and are reviewed as usual but that the period cannot close until a reviewed plan names each key. The collection-plan editor's guidance names the import key convention (`Configuration.tsx`, one sentence).

**Compatibility.** A batch previewed by an earlier build and committed on this one fails `PREVIEW_STALE` (the recomputed preview now carries keys and flags) and is previewed again; nothing is written by the failed commit. Observations committed by earlier builds keep their `<batch id>/…` keys: they remain unplanned for close exactly as before, and a plan amendment can name those keys too (they exist for the same indicator inside the period). No data migration.

## Contract and persistence

Domain API (regenerated with `scripts/build_contracts.py` and `scripts/export_implemented_api.py`; the integrator re-runs both): the staged preview's observation schema gains `source_key` (string, ≤200) and `planned` (boolean, optional); `counts` gains the optional integer `unplanned`; the preview gains the closed object `plan_check` (`evaluated_indicators`, ≤20 UUIDs). Required fields are unchanged, so batches stored by earlier builds still validate on read. Policy: the `state_guard` texts of `action_imports_preview` and `action_imports_commit` describe the key and the planned flag; capabilities, role templates, assurance and purpose rules are unchanged, so `bootstrap_profile.json` (`initial-access-v2`) is unaffected (`test_usable_staging_unit.py` passes).

Persistence: no migration. `import_unit_register` is unchanged. The observation payload's `source_key` is a free string (≤2000) and an obligation's `source_key` allows 200 characters, which holds the longest key (100-character unit key + two UUIDs + separators = 174).

## Not delivered: asynchronous import commit (slice (b))

The brief asked for a worker job class `IMPORT_COMMIT` for batches above a threshold. It is **not built**, and no part of it is in this branch, for a reason that is architectural rather than a matter of time alone: a commit is the governed write path — `forms.record` → `store.write`, `Service.submit`, the review workflow, `workflow_author`, `object_natural_author`, `source_key_registry`, audit and outbox events, `import_unit_register` — executed **as the committing principal** with that person's grants, natural-person authorship and audit identity. The worker runs on `impact_worker_login`, which migrations 0025/0026 narrowed to exactly the tables the dispatcher, exports and retention sweeps touch, and `IMPACT_REQUIRE_UNPRIVILEGED_DB` requires a worker connection to be a member of exactly `impact_worker`. Executing a commit there would mean either granting the worker INSERT/UPDATE on the object registry, revisions, the observation partitions, workflows, authorship and review tables for every tenant (a second application role in all but name, reversing the 0025/0026 narrowing and §4 rule 20's spirit) or reconstructing a principal context without an authenticated identity (`store.context` requires one). Neither is a safe two-hour change with CI-only native evidence, and the synchronous path still works for every batch within the bounds (≤500 rows, about 29 ms per produced observation, 14.4 s for a 500-row batch in the sandbox run — unchanged by this slice: the cost is the governed write itself, and an asynchronous path moves it off the request path without making it cheaper). The design that keeps the write on an application-role process is in "Integration notes".

## Limits

- The key convention is only as discoverable as the UI makes it: a planner types `<unit>/<indicator id>/<period id>` into the obligation's source key field (the editor says so; the import preview shows each value's key for copying). No picker generates the keys from a unit list; no plan is generated from an import preview.
- `planned` is evaluated with the previewer's own access: an importer without `collection-plans.read` sees no flags, and a committer with different plan access than the previewer gets `PREVIEW_STALE` (the recomputed preview differs); preview again as the committer.
- A unit imported again in a later period is a new key by construction (the period id is in it); tested on a monthly calendar created through the v0.26a reference-data command (`test_a_unit_imports_again_in_a_later_period_without_colliding`), not on the fixture calendar, which has one period.
- Observations committed by earlier builds keep their batch-prefixed keys.
- Collection plans still cannot be amended to *remove* an obligation without exclusion evidence (`OBLIGATION_REMOVAL_REQUIRES_EXCLUSION`, unchanged), and an import into an indicator with no approved plan is impossible as before (an indicator activates only with an approved plan).
- No asynchronous commit (above). The `import-browser` group now asserts the "(unplanned)" marker and the unplanned note on the preview and finds committed observations in Measurement by the new key (its earlier locator used the batch-prefixed key and failed on the first CI run of this branch); no browser check covers a planned import end to end through close.

**Design for the asynchronous commit (not built; for the next slice or an owner decision).** Keep the governed write on an application-role process: (1) `action_imports_commit` above a threshold (proposed 50 rows, read from one constant in `import_contracts.py`) performs today's authorisation, preview recomputation, hash and warning checks, then writes the batch as `Queued` with a `commit_request` in the payload (committer principal, workflow version, preview hash, accepted warnings) plus one `impact.job` of class `IMPORT_COMMIT` and an `import_commit` row (lease owner/generation/expiry, attempts, `next_attempt_at`, `last_error_class`, `completed_at`), all in the request transaction — intent, not proof; small batches stay synchronous and answer exactly as today. (2) An **import executor** process — the API image started as `python -m impact_api.import_executor`, on a new provisioned login that is a member of exactly `impact_app` (not `impact_worker`), with its own `IMPACT_REQUIRE_UNPRIVILEGED_DB` topology rule — claims due jobs per Active tenant under the tenant advisory lock (`FOR UPDATE SKIP LOCKED`, `lease_generation+1`, 60 s lease on `statement_timestamp()`), rebuilds the committer's `Context` from `tenant_principal` and the current grants (the identity fields the context needs are the principal's; `auth_time` is irrelevant because the fresh-assurance check already ran at request time and the commit operation needs none), re-runs `Imports.commit` with `stage()` recomputed (a changed outcome fails the job `PREVIEW_STALE` rather than committing a different batch), and records the fenced outcome in the same transaction as the writes: `Committed` + register rows, or `Failed` with a closed error class (`PREVIEW_STALE`, `IMPORT_ATOMIC_REJECTED`, `WARNINGS_NOT_ACCEPTED`, `SOURCE_KEY_CONFLICT`, `AUTHORITY_CHANGED` when the committer's grants no longer cover the commit, `LEASE_EXPIRED`, `COMMIT_DEFECT`), every UPDATE fenced on owner and generation; a stale holder's whole transaction rolls back, so atomicity holds. Because the write is one transaction under the tenant lock, two executors can never commit one batch twice (the second's fenced claim or outcome matches no row), and a 500-row batch still holds the tenant lock for its ~14 s — the cost moves off the request, it does not shrink; a per-row chunked commit would break the all-or-nothing rule and is not proposed. (3) Cancellation before start through the existing `cancel_jobs` pass (`cancellation_requested_at` → `Cancelled`, `job_item 'cancellation' CANCELLED_BEFORE_START`; a started commit is never cancelled). (4) Migration: `import_commit` (forced RLS, `tenant_fence`; app SELECT/INSERT/UPDATE; nothing for `impact_worker` or the control plane), a `job_class` CHECK extension if one exists, and the executor login's provisioning in `scripts/provision_logins.py` and `deploy/prepare_database.py`. (5) UI: batch states `Queued`/`Running`/`Committed`/`Failed` with the error class and a refresh button; the operators' Workers panel gains the executor's heartbeat. If the owner prefers widening `impact_worker` instead, the explicit grant list derived from the commit's code path is: SELECT/INSERT/UPDATE on `object_registry`, `import_job_current`, `observation_current` (the parent; partitions follow for DML through the parent), `workflow_current`, `source_key_registry`; SELECT/INSERT on `workflow_author`, `object_natural_author`, `review_decision`, `import_unit_register`, `task_current`, `notification_current`, `audit_event_current`, `outbox_event`, `object_revision`, `operation_receipt`; SELECT on `tenant_root`, `tenant_principal`, `membership_current`, `grant_current`, `group_entitlement`, `scope_definition`, `scope_member`, `collection_plan_binding`, `indicator_instance_current`, `programme_current`, `period_current`, `programme_period_state`, `workflow_template_current`, `result_binding`, `restatement_source_permission` — and `test_worker.py`'s kept/revoked sets must change with it. That widening is the reason this slice recommends the executor process instead.
