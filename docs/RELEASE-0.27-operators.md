## Delivered

### Operator renewal and deactivation

A platform operator's role has an expiry (`platform_operator.expires_at`, at most 365 days at nomination). Until this build nothing could extend it and nothing could end it except a direct database change. Two governed control-plane operations now exist, each made by a **different active operator** than the subject, with authentication within the previous 300 seconds and the configured assurance, a reason, and the exact operator revision:

- `POST /v1/platform/operators/{identity_id}/actions/renew` (`renew_platform_operator`; body `{operation_id, expected_revision, data: {expires_at, reason}}`): moves the subject's expiry later — strictly after the current expiry and at most 365 days from now (`OPERATOR_EXPIRY_BOUNDS` otherwise). Only active, unexpired authority is renewed: a deactivated operator answers `409 OPERATOR_DEACTIVATED`, an expired one `409 OPERATOR_EXPIRED` (expired authority is re-established only by a new nomination and acceptance, as for tenant authority in v0.13). The origin of the authority (`authority_reference`) is kept; the renewal is recorded in the register, not by rewriting it.
- `POST /v1/platform/operators/{identity_id}/actions/deactivate` (`deactivate_platform_operator`; body `{operation_id, expected_revision, data: {reason}}`): sets `active=false`. Authority ends at once: `lock_platform_operator` is evaluated on every control-plane command, so the person's next request is that of a non-operator (`PLATFORM_OPERATOR_REQUIRED`, or 404 where operators alone see a resource), the operator directory no longer lists anything to them, and nominations they made can no longer be accepted (the definer `accept_operator_nomination` requires the nominating operator to still be active).

Rules, all rechecked inside the SECURITY DEFINER `impact.apply_operator_change` (migration 0029), which is the only run-time writer of `platform_operator` besides `accept_operator_nomination` (the platform role still holds no UPDATE on the table):

- **Never oneself**: the subject as actor is refused (`403 INDEPENDENCE_REQUIRED`), and so is any other identity of the subject's natural person (aliases and second logins create no independence).
- **By an active operator only**: a non-operator never learns whether the subject exists (`404 RESOURCE_UNAVAILABLE`); an unknown subject is the same 404.
- **The last active operator is never deactivated**: the actor must be another active, unexpired operator, which already guarantees one remains; the definer counts the others again before writing (`LAST_OPERATOR` in the application check; unreachable through the API, kept as defence in depth).
- **Exact revision**: `platform_operator` now carries `revision_id` (and `updated_at`), refreshed by the guard trigger `guard_platform_operator` on every update (the identity is immutable); a stale `expected_revision` is `409 CONFLICT_VERSION`, including after a direct maintenance update.
- **Receipts and events**: `platform_receipt` (exact retry returns the receipt; the same operation ID with another payload is `CONFLICT_VERSION OPERATION_REUSE`) and a tenant-less `platform_event` (`operator-renew` / `operator-deactivate`; the CHECK `platform_event_tenant_scope` is widened to admit them) commit with the change. Every applied change is one row of the insert-only register `platform_operator_change` (subject, action, actor, the actor's assurance instant, reason, previous and new revision, expiry and active flag); the platform role reads it and cannot insert, update or delete it.

The operator directory (`GET /v1/platform/operators`) gains `revision_id`, `state` (`Active` / `Expired` / `Deactivated`) and `updated_at` per operator and a `changes` list (the last 100 register rows with the actor's display name). The Operators panel of the tenant-lifecycle console shows each operator's state, offers **Renew operator role** (date and reason) and **Deactivate** (reason) on every active operator other than the viewer, and lists the operator changes. Hidden buttons are not security: the server refuses self-service whatever the client shows.

### Provisioner client secret rotation

`scripts/rotate_secrets.py` gains the family `provisioner`: the secret of the confidential Keycloak client `impact-provisioner` that the API uses to create sign-in accounts (`IMPACT_PROVISIONER_SECRET` in `secrets.env`, `IMPACT_PROVIDER_ADMIN_CLIENT_SECRET` in the api container). Unlike the keyring families it is one value on each side, so it has **no grace list**: `rotate --family provisioner` (env-file mode only; `--family all` includes it) writes a new 96-hex-character value atomically to `secrets.env` and, with `--sync-to`, `compose.env`, records the kids in `secrets.env.keys.json` (the old kid is marked retired at once), prints kids only, and reports `restart_required: ["api"]` and `provider_realign: ["provisioner"]`. `retire --family provisioner` is refused (`--family all` skips it); `--dry-run` writes nothing.

`deploy/rotate-secrets.sh` acts on `provider_realign`: after the files are written it runs `deploy/keycloak_admin.py rotate-provisioner` inside the `idp-admin` job (which reads the new value from `compose.env`; the function sets the client secret through the admin REST API, verifies it was applied, is idempotent and never prints it), then recreates the api. The files are the source of truth: should the re-alignment fail (the script dies with that message), the next `deploy/update.sh` run re-aligns the provider itself in its "account provisioning client" step, and account creation answers `503 PROVIDER_ADMIN_UNAVAILABLE` until then. The CI container stack now expects the provisioner family in the rotation status with no grace key, and after `rotate --family all` checks that a second `rotate-provisioner` reports `changed: false` (the provider holds the rotated value) before the smoke run.

## Contract and persistence

| Method | Path | Purpose |
|---|---|---|
| POST | /v1/platform/operators/{identity_id}/actions/renew | Another active operator moves an operator's expiry later (≤ 365 days) |
| POST | /v1/platform/operators/{identity_id}/actions/deactivate | Another active operator ends an operator's authority at once |

`GET /v1/platform/operators` (unchanged path) answers the widened `DIRECTORY` schema (`operators[].revision_id/state/updated_at`, `changes[]`). Both commands validate closed schemas (`RENEW`, the shared `ACTION`), require fresh assurance, serialise on the platform-wide onboarding advisory lock (one operator change at a time) and follow the v0.12 skeleton (identity authorisation, replay check, expected revision, definer, event, receipt).

Migration `0029_operator_lifecycle.sql` (SHA-256 `de05d78b232cfea0ec5f75479f2f374fbfd8196c0df5a4694d871b73e68d4d41`, appended to the register and the executable definitions in `docs/current/CURRENT-DATA-DICTIONARY.md`): `ALTER TABLE platform_operator ADD revision_id, updated_at` (defaults, so `bootstrap_operator.py`, `bootstrap_platform.py` and the positional fixture inserts of the suites are unchanged), trigger `platform_operator_guard`, the widened `platform_event_tenant_scope` CHECK (dropped and re-added with two more actions), table `platform_operator_change` (SELECT to `impact_platform` only), function `apply_operator_change(uuid,uuid,uuid,text,uuid,timestamptz,timestamptz,text)` (SECURITY DEFINER, fixed search path, EXECUTE to `impact_platform` only, REVOKE FROM PUBLIC). No role, RLS policy or grant on an existing table changes; `impact_app`, `impact_identity` and `impact_worker` reach none of it.

## Limits

- Renewal is for active, unexpired authority only; an expired or deactivated operator is re-established only by a new nomination and acceptance (which `accept_operator_nomination` applies with `ON CONFLICT DO UPDATE`; the guard trigger refreshes the revision then too). There is no reactivation action and no expiry reminder for operators.
- The register `platform_operator_change` records applied changes only; refused attempts are not audited (as for every denial in this build).
- The "last active operator" rule is enforced by construction (the actor is another active operator) and by the definer's count; it has no API-level test because it cannot be reached through the API.
- The browser check (`operators-browser`) extends the v0.26a click-path with a renewal and a deactivation of the newly accepted operator by the nominating operator (4 checks, was 3); the evidence file `docs/evidence/operators-browser-tests.json` is not republished by this slice (CI's `make browser` records it).
- The provisioner family has no grace: between the file write and the api recreate (seconds), a running api still holds the old secret and account creation fails with `PROVIDER_ADMIN_UNAVAILABLE`; nothing else is affected. The master Keycloak administrator password (`KEYCLOAK_ADMIN_PASSWORD`) and the database login passwords stay outside `rotate_secrets.py`, as before.

## Deferred: ceiling widening (`initial-access-v1` → v2)

Not built in this slice; recorded so the next slice starts from a design rather than a blank page. Tenants that applied `initial-access-v1` keep their 75-capability ceiling and the v1 role bundles (`RELEASE-0.26a.md` A2). The reviewed widening should mirror v0.13 exactly:

- **Table** `tenant_access_upgrade` (one pending per tenant through a partial unique index): `request_id`, `tenant_id`, `revision_id`, `state` Requested → Accepted → Applied | Rejected | Cancelled, `bootstrap_request_id`, `owner_identity_id`, `second_identity_id`, `tenant_revision`, `owner_revision`, the pinned `current_manifest` (both administrators' ceilings as `authority_renewal.holding` assembles them) and `authority_hash`, the target `profile_hash` (`bootstrap_profile.json` `PROFILE_HASH`) and `target_manifest` (the v2 roles and `purpose_bound` list), `review_expires_at` (≤ 7 days), `owner_auth_time`, `second_auth_time`, `approved_by`, `applied_at`, `reason`; grants to `impact_platform` only.
- **Flow**: `POST /v1/platform/tenants/{id}/access-upgrade` by the current owner (pins the current ceiling hash and the profile hash; refused when the tenant already holds the profile, when a renewal or upgrade is pending, when readiness fails); `accept` by the exact second administrator; `approve` by an operator who is a different natural person from both; `reject` / `cancel` as in v0.13. Every step: fresh assurance, Active tenant, `platform_event` + `platform_receipt`.
- **Approval** rechecks `recheck()` of v0.13 (context revisions, deadlines, readiness, byte-identical recomputed manifest — anything revoked after the proposal fails with `AUTHORITY_CHANGED`, anything revoked before is absent and stays absent) and then, in the application transaction as the operator's provenance principal: a new revision of each managed `RoleTemplate` (`managed_by = impact-access-v1`) with the v2 capabilities, new managed templates for the v2 role names a v1 tenant lacks (AUDIT_READER, PRIVACY …), new `Grant`s for the TENANT_ADMIN delta of both administrators and the matching `member_role_assignment` rows, subject and policy epochs advanced.
- **Definer** `impact.apply_access_upgrade(request_id)` mirrors `apply_initial_authority`: the only writer of the new `grant_authority` rows (the capability delta of `roles` ∪ `purpose_bound` for both principals, expiring with the existing ceiling), rechecking state, deadlines, Active tenant, `lock_platform_operator(approved_by)`, natural-person independence of the approver from both administrators and the bootstrap marker; `impact_app` can never widen a ceiling (rule 20).
- **Tests** per v0.13 (`test_authority_renewal.py`): positive three-party flow on a v1 fixture tenant (apply v1 through the existing bootstrap with the v1 profile pinned in the test), revocation after the proposal → `AUTHORITY_CHANGED`, same-person approver refused, stale/replay/conflict, a native fence that `impact_platform` cannot insert `grant_authority` directly, a browser check in the Authority panel.
