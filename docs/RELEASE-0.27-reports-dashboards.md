# v0.27 — Charts in reports, dashboard drill-down and portfolio view

Build number, domain API version and ledger counts are set by the integrator (this branch does not bump version literals; `dashboard_contracts.VERSION` and `export_contracts` keep their `x-contract-version` tags). Schema 28: **no migration** — the chart declaration lives inside the report section (`report_current.sections` is already jsonb) and both new reads are pure read models. Domain API +2 read operations (207 → 209 on this branch); control-plane API unchanged. Ledger: **nothing is accepted**; the proposed movements are in "Integration notes". Built on `main` at 25a8dca (build 0.26.0) on branch `release/0.27-reports-dashboards`, 2 October 2026.

## Delivered

**1. Charts in frozen report packages (FR-RPT-005, FR-RPT-003; `report_charts.py`).** A report section may declare `charts`: each chart (`chart_code`, `title`, `kind: BAR`, 1–12 `series`) names bars by the section's own numeric binding codes, so every bar is an OFFICIAL result revision of the locked snapshot that reconciliation already checks, and each bar may pin `target_revision`, the approved Target revision the snapshot locked (`snapshot.target_versions`) for the same indicator and period (official versus target). Reconciliation (`Reporting._reconcile_charts`, run at create, submit and approval exactly like the numeric bindings) refuses: a bar that is not one of the section's bindings (`UNKNOWN_CHART_BINDING`), a target the snapshot did not pin (`TARGET_NOT_IN_SNAPSHOT`), a pinned target of another indicator or period or a baseline (`CHART_TARGET_MISMATCH`, checked through `result_binding` and the Target payload), bars of differing unit or display places in one chart (`INCOMPATIBLE_MEASURE` / `CHART_MIXED_MEASURES`), duplicate chart codes and more than ten charts per section. The reconciliation digest of a package with charts includes them (`charts` entries with the exact result and target revisions), so a frozen package with charts cannot have its charts changed; chart-less packages keep the digest they were frozen with.

Rendering is deterministic and never recomputes a number: bar heights are proportions of the stored decimal values quantised to whole pixels with `Decimal` arithmetic, labels are the stored `displayed_value` strings, a value that is not PRESENT draws no bar (the state is written where the bar would be, never a zero-height bar), a missing target is "not set", a negative value hangs below the explicit zero axis. The HTML artifact gets an inline SVG `<figure>` (`role="img"`, `<title>`, a `<desc>` naming every value, legend, unit) followed by a "Chart data" table with the same values; the figure's styles sit inside `REPORT_STYLE`, so the artifact CSP is unchanged in shape and the hash is recomputed. The PDF gets the same chart as a reportlab vector drawing (`reportlab.graphics.shapes`, Helvetica only, inside the invariant document) plus the data table; XLSX gets a "Charts" sheet (note, one titled block per chart, text cells only) and DOCX a note and a table per chart — no picture, as the brief allowed when a native chart is not cheap and deterministic. The worker's `export_model` reads chart targets as Target revisions through `object_revision` (the only table it needs; a target outside the snapshot's pins fails the job `RESULT_NOT_OFFICIAL`), so the worker login needs no new grant. Two renders of the same package are byte-identical in every format (extended determinism test).

Not built: template-level chart declarations (report templates have no authoring route in this build — they come from the seed or the closed `reference-data/report-templates` command owned by the v0.26a slice — so the declaration lives in the reviewed, frozen report; a template may later carry `required_chart_codes` the same way it carries `required_binding_codes`); trend charts across periods (a snapshot locks one period; a trend would need several snapshots and is a dashboard, not a frozen package).

**2. Dashboard drill-down (FR-ANA-002 subset).** `GET /v1/tenants/{t}/indicator-instances/{id}/dashboard-sources?period_id=…&limit&cursor` (`indicator_dashboard_sources`, `dashboards.read`): the period's source observations of one indicator instance as the reader may see them (`observations.read` as the listing predicate, RESTRICTED and restricted revisions excluded), keyset on the observation identifier, signed cursor bound to tenant, principal, grants, route, instance and period, at most 100 per page, no total. Each row: namespace and key, event time, value state, stored value and its display (from the pinned definition's places), numerator/denominator, approval state, lifecycle state, and its disposition in the value the card shows — INCLUDED or EXCLUDED with the reason from `lineage_edge` of that result revision, `NOT_IN_RESULT` for a row that was not an input (approved after the calculation), `null` when no value exists — plus `changed_since_calculation` when the row's head revision differs from the one the calculation read. `value` names the shown result (OFFICIAL from this programme's snapshot when one exists, else the latest provisional, as the card). `source_check` is `COMPLETE` when the reader can read every source row of the period and `PARTIAL` otherwise: withheld rows are absent and never counted (FR-ANA-002: filtering cannot reveal hidden source counts; the card's coverage already says UNAVAILABLE in that case). Another tenant, a missing or wrong-kind identifier → 404; no `dashboards.read` → 403; a tampered or foreign cursor → 400 `INVALID_CURSOR`. UI: a "Show sources" button on every dashboard card opens a "Source observations" table with the disposition column and a status line that says whether the set is complete.

**3. Portfolio view (aggregation across programmes).** `GET /v1/tenants/{t}/indicator-definitions/{id}/portfolio?period_id=…&limit&cursor` (`indicator_definition_portfolio`, `dashboards.read`): for one indicator definition and one period, every instance of that definition in the tenant the reader may see (`indicator-instances.read` predicate; at most 500 instances are considered), one row per programme instance (keyset on the instance identifier, signed cursor, 100 per page) with the programme's period state, its latest locked snapshot for the period, the OFFICIAL value from *that programme's* snapshot only (under the instance's pinned definition revision, exactly as the programme dashboard) and the coverage block. `versions` groups the instances by definition revision and carries one `pooled` block per revision: SUM and COUNT sum the stored official values; POOLED_RATIO sums the stored numerators and denominators (51/110 + 8/10 → 59/120 = 49.17, never the mean of 46.36 and 80.00; a zero denominator is UNDEFINED, never 0); MEAN, MEDIAN, MIN, MAX and LAST_VALID are `NOT_APPLICABLE` / `NOT_POOLABLE`. A total is withheld (`value_state` MISSING with a reason) when the reader cannot see every instance of the definition (`scope: PARTIAL`, `SCOPE_PARTIAL` — a subset is never presented as the whole, FSD §32.1), when any visible instance lacks an official PRESENT value for the period (`OFFICIAL_VALUES_INCOMPLETE`, with `contributing_count` of `instance_count`), or when components are missing. No pooling across definition revisions (FR-IND-009: no portfolio pool across versions). UI: the Dashboards area gains a "Programme dashboard | Portfolio" tab list (`setup-tabs`, keyboard-navigable); the Portfolio tab (`Portfolio.tsx`) has definition and period pickers, the pooled total per version with its method and contributing count, and a programme table (official value with components, coverage, snapshot).

## Contract and persistence

`export_contracts.py` adds the closed schemas `ReportChart` and `ReportChartSeries` and the optional `charts` array on `ReportSection` (so `ReportData` and `ReportDraftData` accept it; earlier payloads validate unchanged). `dashboard_contracts.py` adds `indicator-instances/{object_id}/dashboard-sources` and `indicator-definitions/{object_id}/portfolio` to `SPECIAL_READS` (both with a required `period_id`), the closed schemas `IndicatorDashboardSources` and `IndicatorPortfolio`, and two policy rows (`dashboards.read`, same role templates as the v0.24 reads, no purpose, no fresh assurance, not audited). Routes are explicit in `main.py` before the generic handlers. Generated `openapi.json`, `access-policy.json`, `openapi-implemented.json` and `docs/API-INVENTORY.md` are regenerated (209 domain operations). No migration, table, index, grant, role or worker-grant change; `event.schema.json` unchanged.

## Limits

- Charts: one kind (bars of official values, optionally beside the pinned target); no trend across periods, no stacked, line or pie charts, no disaggregation breakdown bars, no colour-blind-safe palette audit beyond two fills plus text labels; the PDF chart uses Helvetica (Windows-1252 only, like the rest of the PDF); XLSX and DOCX carry tables, not pictures; the CSV artifact is unchanged (bound values only); a report created before this build cannot gain a chart without a new report revision (as any other content change).
- Drill-down: one period at a time, the period's source rows only (no hierarchy levels, partner slices, saved views or filter widgets of FR-ANA-002); dispositions come from `lineage_edge` of the shown result, so a result produced before lineage edges existed shows `NOT_IN_RESULT`; reading `complete` costs the same 10,000-row bound as the card.
- Portfolio: one definition per read (no tenant-wide listing of definitions with instances — the UI iterates the definitions list); at most 500 instances per definition (beyond that `scope` is PARTIAL); pooled totals need a complete, fully official set, which in practice means every programme has closed the period; no comparability review, ranking, coverage thresholds or mixed-version flags of FR-ANA-007 beyond grouping by revision; per-instance cards run the same per-card queries as the programme dashboard (bounded, not fast; no timing measured).
- UI: the Portfolio view is a tab inside Dashboards rather than a sidebar entry (deliberately no `main.tsx` edit: nine parallel branches touch that file); no browser check of the drill-down's PARTIAL case.
- Evidence is PGlite only on this branch (serialised transactions); native, full-suite and the remaining browser groups run in CI.
