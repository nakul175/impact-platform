## Delivered

**Denial auditing (FR-SEC-007, FSD §35 denied operations).** `store.authorize` has one hook, `denied()`, at its five refusal points (POLICY_DENIED, hidden RESOURCE_UNAVAILABLE, PURPOSE_REQUIRED, MFA_ASSURANCE_REQUIRED, FRESH_AUTHENTICATION_REQUIRED): the raised `DomainError` carries tenant, principal, operation, capability, the client-supplied selector, status, code and reason. The refusal itself is unchanged. Because the refused transaction rolls back, `main.py`'s `DomainError` handler records the denial afterwards in a transaction of its own (`security_events.record`) through the SECURITY DEFINER `impact.record_access_denial`; `impact_app` holds SELECT only on `impact.access_denial`. Flood control on the database clock: repeats of the same (principal, operation, reason) inside one 300-second window collapse into one row whose `occurrences`, `last_at` and `last_correlation_id` advance (trigger `access_denial_guard` lets nothing else change); once a principal holds 50 distinct rows in a window, every further distinct denial counts in one overflow row (`operation_id '*'`, reason `DENIAL_LIMIT`), so a scan of n operations costs at most 51 rows per window. Recording never changes the response (a failure to record is logged with the correlation id). Not recorded: refusals before authorisation (unknown tenant, no membership, invalid token) and 404s raised by `store.load` outside `authorize`. Read: `GET /v1/tenants/{t}/access-denials?limit&since` (`access-denials.read`, OWNER and TENANT_ADMIN; newest first, at most 200). UI: an "Access denied" table under People & access (`Privacy.tsx`, shown with the capability).

**Denials in the audit export, and the durable export register (VF-AUD-001, FR-SEC-007).** The audit export (`create_audit_export`) now reads audit events and collapsed denials as one stream ordered by occurrence: a denial line has `outcome DENIED`, `action_type` = the refused operation, the principal as actor, the selector as `object_reference`, the first correlation id, `specification_ref FR-SEC-007/<reason>`, `occurrences` = the collapsed count and null revision fields; every line carries the new `occurrences` field (null on events), so the format is `impact-audit-export-v2` and the manifest gains `denial_count`. The chain and seal are unchanged in construction; `verify_content` verifies v2 pages. Every exported page is registered in the insert-only `impact.audit_export_register` (principal, purpose, reason, window, page, first sequence, event and denial counts, content SHA-256, chain start and end, seal key id, correlation, time; keyed by the export's own AuditEvent), the DDL proposal of RELEASE-0.25a.md applied, so the digest and window of an export outlive the 7-day receipt.

**Audit retention window (VF-AUD-001 retention clause, FR-PRV-004).** A new sweep class `SECURITY_EVENT` deletes `access_denial` rows whose `last_at` is older than the tenant's audit window: 2,555 days (seven years) by default, a tenant policy may set 365–3,650 days, and the definer `retention_purge_security_events` enforces the 365-day floor itself whatever it is asked. AuditEvent records are never deleted by this build, inside or beyond the window: no removal path through the insert-only revision store exists and none was added (`test_the_audit_window_is_never_crossed_and_audit_events_are_never_swept`).

**Tenant retention policies (FR-PRV-004, VF-PRV-002).** RetentionPolicy (a 0002 registry kind) is now served on `retention-policies` (list, get, create, patch; OWNER, TENANT_ADMIN, PRIVACY) and the one transition `actions/approve` (`retention-policy.approve`; TENANT_ADMIN, PRIVACY; 300 s fresh assurance; a natural person other than every author of the draft, else `INDEPENDENCE_REQUIRED`). A proposal names one policy-able data class and a duration inside its bounds — OPERATION_RECEIPT 7–90 days (a policy can only lengthen the API's 7-day idempotency window; the definer `retention_purge_receipts(integer,integer)` treats anything below 7 as 7), PRIVACY_EXPORT_PACKAGE 1–30 days from production, OUTBOX_RECIPIENT 7–365 days, SECURITY_EVENT 365–3,650 days — with the class's own action (`RETENTION_OUT_OF_BOUNDS`, `RETENTION_ACTION_FIXED`, `DATA_CLASS_NOT_POLICY_ABLE`; UPLOAD_SESSION stays fixed). Approval writes the Approved revision and appends one row to the insert-only `retention_policy_binding`; the worker's sweep (`retention.effective`) applies the latest binding per class and the fixed schedule otherwise, and each `retention_proof` row now records the duration actually applied. An approved policy is immutable (patch → 409); a later proposal names the revision it `supersedes_revision` (must be the current Approved head: `SUPERSEDES_NOT_CURRENT`/`SUPERSEDES_NOT_APPROVED`). `GET /retention-schedule` returns the effective schedule with `source` (`DEFAULT`/`APPROVED_POLICY`) and `policy_id` per class. UI: "Retention policies" (effective schedule, proposals, propose form, approve button) under People & access.

**Retention-hold API (FR-PRV-005).** `POST /retention-holds` (`retention.hold`; PRIVACY, TENANT_ADMIN; 300 s) places a hold on one existing object of the tenant with an authority reference, a reason and a future review date; it is effective at once (the erasure plan reports the object `HELD` with the review date and the revision-removal guard refuses it, as before). `POST /retention-holds/{hold}/actions/release` (`retention.release`; 300 s) needs a natural person other than the one who placed the hold (`INDEPENDENCE_REQUIRED`), records who released it and why, and is final: trigger `retention_hold_guard` (0029) makes every column but the three release columns immutable and a released hold unchangeable, by any role. `GET /retention-holds` lists holds, active first. Both commands are receipted and audited with the hold id as the object reference (the receipt's `revision_id` pins the held object's revision at the time). Holds inserted directly before this build (no placer) may be released by any holder of the capability. UI: "Retention holds" under People & access.

## Limits

- Denials are recorded only for authorisation refusals of a member of an Active tenant; refusals at identity, tenant or membership resolution and `store.load` hides are not security events here. Recording is best effort and asynchronous to the refused transaction (a crash between the two loses the record); no alert, no per-principal lockout, no operator (cross-tenant) view. The window (300 s) and cap (50) are build constants.
- A denial row keeps accumulating while its window bucket is open, so an export of a window that ends inside an open bucket can differ from a later export of the same window by the counter of that row (every other field is stable); exports of windows closed for more than 300 s are stable. `occurrences` on every line changes the line format: v1 consumers must be updated (none exist).
- Audit retention: `SECURITY_EVENT` rows only. AuditEvent registry rows, their revisions, outbox events and the export register are never deleted; VF-AUD-001's minimisation and a reconciliation report are not delivered. The floor (365 days) is build-fixed.
- Retention policies govern four classes and a duration only (never the action, the trigger or the store); no preview of affected objects, no collection-activation gate (VF-PRV-002's "approved before collection"), no policy expiry or review date, no notification. The policy takes effect at the tenant's next sweep (at most `retention_seconds` later). A package may now be deleted before its own `expires_at` under a short policy; the download then answers `EXPORT_EXPIRED`.
- Holds: placing a hold needs only `retention.hold` at TENANT scope and confirms the object's existence (no content is returned); there is no hold expiry, reminder at `review_at`, or hold on a whole subject (one object per hold; a case's plan still shows every held object). Release independence is by natural person against the placer only (not against the subject of a case).
- Evidence is PGlite for every live check; the native fence test (`test_native_security_privacy_tables_are_fenced_for_the_application_login`) runs only under `scripts/run.py test --native` (CI). No browser check covers the three new panels. Keycloak signing-key rotation (scope item 4) was not attempted.
