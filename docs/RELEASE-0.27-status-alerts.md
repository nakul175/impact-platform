# v0.27 — User-visible status and alert delivery

Branch `release/0.27-status-alerts` from `main` at build 0.26.0 (25a8dca), 2 October 2026. **No version bump in this branch** (the integrator bumps); schema 28 unchanged (no migration; 0029 unused); domain API 1.16.0 and platform API 1.7.0 unchanged (one new support route, `GET /v1/status`, outside both generated contracts, like `/v1/runtime-manifest`); the regenerated `openapi.json` / `openapi-implemented.json` differ only in the error documentation (below). The ledger is not regenerated here; proposals are in "Integration notes". Release 1 remains in progress; nothing is accepted.

This slice is the second half of two non-functional requirements that QA 2026-10 left open: users now *see* a degraded dependency (VF-AVL-002, "users shall see the affected function, stale data and queued actions"), and critical alerts are *delivered* somewhere a person is, not only written to a status page (VF-OBS-001, "critical service failure alerts shall be generated within 5 minutes"). It also publishes an on-call rota to operators, scripts a readiness exercise with recorded evidence, and corrects the documented error-enum mismatch without changing the wire.

## Delivered

- **`GET /v1/status`** (`apps/api/impact_api/status.py`; one route in `main.py`). Every signed-in identity (bearer or cookie; anonymous 401) receives `{generated_at, state: OK|DEGRADED, poll_seconds: 60, notices[]}` where each notice is one entry of a **closed catalogue** of plain-language messages: `UPGRADE_IN_PROGRESS` (schema ledger behind the build), `DELIVERY_DELAYED` and `EXPORTS_DELAYED` (no RUNNING worker heartbeat within 120 s, the alert's window; a development or test run that never had a worker is not degraded, a staging/production deployment without one is), `EMAIL_UNAVAILABLE` (mail capture or provider container unhealthy), `EVIDENCE_UPLOADS_UNAVAILABLE` (object-store path not a directory, or under 64 MB free where the store writes — the nearest existing ancestor, since the store creates its tree on first use) and `EVIDENCE_STORAGE_LOW` (under 512 MB, or the server's `DISK_LOW` critical), plus `IDENTITY_PROVIDER_UNAVAILABLE` when the server's last check reports Keycloak unhealthy. The server's alert list (`ops_status_file`, written by `deploy/ops-check.sh`) is consulted only while its `checked_at` is under 30 minutes old; alert codes map to user functions through a fixed table (`ALERT_NOTICES`) and everything unmapped (backups, drill, queue backlog) is operator detail only. **No reason code, login, tenant, address, figure or secret reaches a notice**: notices are catalogue text; the member body has exactly four keys. Platform operators (checked through `lock_platform_operator`, as the Workers panel does) additionally receive `detail`: observed sources (`WORKER_STALE`, `OBJECT_STORE_LOW|UNAVAILABLE`, `SCHEMA_MISMATCH`, `OPERATIONS_CHECK`), worker counts, DEAD/held delivery counts (`operator_delivery_attention`, capped at 50), store free space, the server's alerts (closed code, severity, target, message; at most 50) with the check's age, and the on-call rota. The database and the identity provider are required dependencies of every authenticated request, so when they fail the route fails too (503 with `reason_code`), and the client renders those two catalogue entries itself.
- **Service-notice banner** (`apps/web/src/StatusBanner.tsx`; one line in `main.tsx` above the workspace content and one in `TenantLifecycle.tsx` for the console). Polls `/v1/status` every 60 s, doubling to at most 10 minutes while the call fails; shows nothing when `state` is OK; otherwise a `role="status"` region "Service notice:" listing the catalogue messages, amber for warnings and the error palette for a critical notice (new `--status-*` tokens in `:root`, 4.5:1). A 503 from the status call with `reason_code` `DATABASE_UNAVAILABLE` or `IDENTITY_PROVIDER_UNAVAILABLE` renders the matching catalogue text at once; a bare 503 renders "The service is temporarily unavailable"; two consecutive failed fetches render "The server cannot be reached"; a 401 renders nothing (the session handling of `main.tsx` takes over). Operators get a "Details for operators" disclosure (`aria-expanded`, `aria-controls`) with the observed sources, counts, server alert list and the on-call line.
- **Who is on call** (`deploy/on-call.example.json`, schema `impact-on-call-v1`; `status.on_call`). The server owner copies the example to `<impact home>/ops/on-call.json` (the directory the API already mounts read-only for `ops-status.json`; `IMPACT_ON_CALL_FILE` overrides the path) and fills `primary` (name, role, contact, hours), optional `secondary`, up to five `escalation` entries, `timezone`, `updated_at`, `valid_until`, `notes`. The API returns only the known keys, each bounded to 200 characters, to platform operators only; a missing, unparsable or schema-less file is reported as a closed code (`MISSING`, `INVALID`, `NOT_CONFIGURED`), and a rota past `valid_until` is flagged `expired`. The Workers panel of the tenant-lifecycle console opens with one "On call: …" line (`Workers.tsx`, `aria-label="Who is on call"`); the banner detail repeats it.
- **Alert delivery** (`deploy/ops_alerts.py notify`, called by `deploy/ops-check.sh` after every evaluation). Every alert now carries a `target` (service name, file system, or "" for the whole server) so two alerts of one code are told apart. The notifier compares the current alerts with `<impact home>/ops/alert-state.json` (0600) and emits **NEW** (unknown key, or a severity that rose), **CLEARED** (recorded key no longer present) and **REMINDER** (still active `ALERT_RENOTIFY_SECONDS` after the last successful notification; default 21,600 s) events, each listing the alerts it is about. Channels, configured in `config.env` and read by the shell into the notifier's environment (never arguments): (b) a **generic webhook** — `ALERT_WEBHOOK_URL`; JSON `{schema: impact-alert-v1, deployment, sent_at, status_url, events[], text}` where `text` is the Slack-compatible summary ("[impact <host>] 2 new alerts: CONTAINER_UNHEALTHY (worker), WORKER_STALE" with one line per alert and the status URL); with `ALERT_WEBHOOK_SECRET` (secrets.env or config.env) each POST carries `X-Impact-Signature: t=<unix>,v1=<HMAC-SHA256(secret, t + "." + body)>` (`verify_signature` is the receiver side, tolerance 300 s); 10 s timeout; failures recorded as `HTTP_<status>` or an exception class; (c) **e-mail** through the worker's SMTP settings (`SMTP_HOST/PORT/USERNAME/PASSWORD/FROM` of `config.env`/`compose.env`) to `ALERT_EMAIL_TO`, one message per check (subject = the first event's summary), STARTTLS when offered, AUTH when a username is set; a loopback host (the staging capture) is skipped with `LOOPBACK_SMTP`. A transition is consumed only when at least one configured channel accepted it (or none is configured, in which case the status page remains the only signal, as before); otherwise NEW stays NEW and CLEARED stays pending for the next check, so a channel outage delays but does not lose a transition. The state file keeps the last 100 delivery records (event kinds, codes, channel outcomes) and never a secret, address or body. `scripts/webhook_receiver.py` is a loopback receiver (verifies the signature, logs one JSON line per POST) for CI and for an owner trying a channel.
- **Readiness exercise** (`deploy/readiness-exercise.sh`, root on the server or CI; record `<impact home>/ops/readiness-exercise.json`, schema `impact-readiness-exercise-v1`). Four timed steps, each PASS/FAIL: baseline check; `compose stop worker` → the next check must raise `WORKER_STALE` and `CONTAINER_UNHEALTHY` (worker) and the notifier must hold them active (delivering NEW); `compose start worker` → repeated checks until both clear (delivering CLEARED), the time to clear recorded; a **disk simulation** against a scratch copy of the operations directory (synthetic 700 MB free file system → `DISK_LOW` → NEW labelled "<deployment> (exercise)" → healthy → CLEARED) that never touches the live status files. The live worker is stopped for one check; queued deliveries wait and are sent when it is back.
- **CI `container-stack`**: the former inline "injected failure" step now starts the loopback webhook receiver with a run-specific secret, appends `ALERT_WEBHOOK_URL`/`ALERT_WEBHOOK_SECRET` to `config.env`, runs the exercise, and asserts the record (`PASS`, both worker alerts) and the receiver log: every delivery signed and verified, a NEW and a CLEARED carrying `WORKER_STALE`, a NEW and a CLEARED carrying `DISK_LOW`, `schema impact-alert-v1`, Slack `text`, and the secret absent from every body; latencies are published as check-run notices.
- **Error-enum documentation** (`scripts/build_contracts.py`; regenerated `openapi.json` and `openapi-implemented.json`). Every dependency failure has answered `503 SERVICE_UNAVAILABLE` since v0.1 while the baseline named `DEPENDENCY_UNAVAILABLE` (CLAUDE.md §11, QA-DEGRADATION "Limits"). The wire is unchanged: the `Error.code` enum now admits `SERVICE_UNAVAILABLE` (the baseline name stays as the documented design alias), the enum carries a description naming the reason codes, and the 336 per-operation 503 descriptions read "SERVICE_UNAVAILABLE (design name DEPENDENCY_UNAVAILABLE): a required dependency failed; retryable, with reason_code when the cause is known." Response-side only; no request schema, policy row, capability or version changed; `openapi-baseline.json` is untouched.

## Contract and persistence

- Routes: `GET /v1/status` (support route; identity-authenticated; not in `openapi-implemented.json` nor `openapi-platform.json`, documented like `/v1/runtime-manifest`). No tenant table, no migration, no policy row, no capability: status is not tenant data, and the operator detail is gated by the existing platform-operator check.
- Configuration: `Settings.on_call_file` (absolute path; default `on-call.json` beside `ops_status_file`). `config.env`: `ALERT_WEBHOOK_URL`, `ALERT_WEBHOOK_SECRET` (or in `secrets.env`), `ALERT_EMAIL_TO`, `ALERT_RENOTIFY_SECONDS`; the SMTP variables are the worker's. `update.sh` is unchanged: `ops-check.sh` reads these itself.
- Files on the server: `<impact home>/ops/alert-state.json` (0600, root), `<impact home>/ops/readiness-exercise.json` (0644), `<impact home>/ops/on-call.json` (owner-written, 0644).
- `ops-status.json` / `deploy-status.json`: each alert gains `"target"`. Readers that ignore unknown fields are unaffected; `status.py` also understands files written without it.

## Limits

- **In-app notices to operators are not delivered through `WorkCenter.notify`/the outbox** (the (a) channel of the brief): a notice is a tenant object bound to a work item and a member principal, and platform operators need not be members of any tenant; building a cross-tenant notice from the host-side check needs a definer and a closed notice class. Operators do see the alert list in-app (banner detail and Workers panel), and the webhook and e-mail channels carry the same transitions. Design for the integrator: a `platform_notice` control-plane table written by a `python -m impact_api.ops_notify` step inside the API container, listed in the console, is the smallest honest version.
- The banner shows what the *server* knows: worker freshness, store space and the last 30-minute-old check. It cannot show a database or provider outage from the server side (the route fails with them); the client's own 503 handling covers that, and a cookie session that is already open keeps working through a provider outage as before. There is no per-tenant status, no "stale data" marking on individual records, and no queued-action count per user (the Work Centre shows a person's own items).
- Tenant administrators get the member view; the operator detail is for platform operators only (no capability was added for an administrator detail).
- Alert delivery runs on the host every 5 minutes with the timer: the detection-to-delivery bound is the timer plus one HTTP/SMTP call, measured in CI as one check. There is still no paging (the webhook can feed a paging service), no acknowledgement, no escalation policy, no per-recipient preference, and e-mail goes nowhere on staging (loopback capture) until an SMTP provider is configured (owner decision, unchanged).
- The disk simulation evaluates a synthetic figure; no file system is filled. The exercise stops the live worker.
- `GET /v1/status` takes `lock_platform_operator` for every signed-in caller once per poll (60 s) like the Workers panel; no latency was measured.
- Browser evidence is Chromium only, through the development sign-in, with the degraded state injected by file.
