# Internal member advice candidate for build 0.33

This slice implements advice from an existing organisation member around an exact saved AI adoption plan. The reviewed SQL is registered as migrations 0038 and0039, and explicit routes/contracts are integrated into the local candidate. The corrected focused API and actual native-login runs pass; browser and full release regression qualification remain pending. Membership eligibility does not establish employment, professional certification, availability or supplier status.

## Delivered in the candidate source

- A requester names a distinct natural person with a current membership and current scoped AI read/manage access to the saved plan. The invitation shares only its title, agreed scope, text boundary and desired outcome. The problem text is stored separately.
- The named member records an exact conflict declaration and scope acceptance. A declared conflict cannot progress to assignment. The requester explicitly assigns the current accepted declaration and consents to sharing the private brief.
- Assigned members can ask accountable questions; the requester can respond. Advice drafts contain recommendations and named action responsibilities. Requester closure pins the exact advice revision and acknowledges every current action identifier.
- The states are Open, Assigned, AwaitingInput, AdviceDraft, Closed and Cancelled. Terminal states are immutable. The adviser immediately loses case, history and receipt access; the requester retains the exact frozen record under current plan read authority.
- Every material action checks both selected current memberships, natural-person identity, plan scope, consent cutoffs and the pinned plan revision. A later plan change prevents assignment or closure; cancellation remains available to an authorised requester after plan changes or adviser expiry.
- An optional eligible-colleague selector requires current OWNER/TENANT_ADMIN authority, tenant-wide memberships.read and current plan AI read/manage. Its response contains only already-permitted display names and exact membership selectors. Ordinary AI management does not imply directory access, and eligibility is not an opt-in or availability declaration.

## Contract and persistence

`human_advice_contracts.augment()` defines thirteen closed operations under `/v1/tenants/{tenant_id}/ai-enablement/human-advice`: list, create, eligible peers, current case, revision history, exact revision and seven actions (declare-scope, assign, request-input, respond, advise, close and cancel). Writes use existing `ai.enablement.manage` with 300-second assurance; reads use existing `ai.enablement.read`. The separately permission-gated colleague selector uses manage without requesting fresh assurance. This slice adds no provider or disclosure capability.

`HumanAdviceCases` checks business access on the anchored plan and manages its own participant projection. `HumanAdviceCase` deliberately stays outside generic `contracts.ENTITIES` and `store.KINDS`: it does not receive generic case routes or exports. The existing immutable writer and audit/outbox intent are reused in the same transaction as the projection, private brief and seven-day insert-once operation receipt.

Responses use a separate closed `HumanAdvicePublicData` allowlist. Stored natural-person proofs, authentication timestamps, internal schema version and private brief digest remain server metadata, including authentication proofs nested inside declaration and assignment. Participants retain tenant-scoped principal/membership/action selectors, accountable case content and exact revision pins. The complete stored consent and salted private brief integrity checks remain unchanged.

The integrator copied the exact reviewed and scratch-qualified source from `qualification/drafts/human_advice_cases.sql` into `infrastructure/migrations/0038_human_advice_cases.sql`, SHA-256 `ace70f9e77a2636df7e0cf5f85f5ffd29de74af8efa94df6e5804077e5331e00`. The registered file is frozen; later schema fixes require an additive migration. Both new tables have tenant-qualified keys/FKs and ENABLE/FORCE RLS:

| Table | Key and purpose | Runtime privileges |
|---|---|---|
| human_advice_case_current | tenant_id/object_id; current revision, exact plan anchor, immutable requester/adviser membership/principal/natural-person pins and state | impact_app SELECT/INSERT/UPDATE under current participant policies and guards |
| human_advice_private_brief | tenant_id/object_id; bounded problem text, private random nonce and salted SHA-256 integrity digest | impact_app SELECT/INSERT; immutable brief; adviser reads start only after explicit assignment |

Transaction-local `impact.human_advice_principal` is set only after resolving the authenticated current application context. A custom GUC is writable by the database login; these RLS policies guard missing or mis-scoped application context and do not authenticate a human against a compromised application database login.

Narrow fixed-search-path owner-definer helpers enforce current participant/read scope and protect generic registry/revision, natural author, audit, operation receipt, outbox event/delivery and consumer receipt pointers. Other runtime roles cannot read those case-related rows. A participant projection is inserted before a new registry header; deferred tenant-qualified FKs and a deferred final-head consistency trigger seal the actual head and private brief at commit. There is no permissive unprojected-case creation path. Standard outbox intent has no delivery channel; the worker receives no human-advice delivery authority.

All list/history/peer cursors reuse the platform HMAC verifier with a fifteen-minute TTL. Bindings include current tenant/principal/route/authority and current visibility, including the anchor for peer lookup and exact case for history. No total counts are returned. Limits include fifty rows per page, twenty proposed actions, fifty accountable notes, one hundred currently visible requester cases and two hundred material revisions; terminal completion/cancellation remains possible at the revision limit. The colleague visibility input is bounded to five thousand eligible memberships. The requester-case count runs under current participant RLS, so unavailable or currently out-of-scope cases are excluded from this visible-case limit.
