## Delivered behaviour

The Foundations lesson can open the existing practice screen without saving or recording progress. The learner previews the invented brief from the currently loaded template edition. Cancel leaves the worksheet unchanged; applying the example is a deliberate action, with explicit replacement when existing work is present. The action replaces only the brief, preserves the learner's manually written draft and review notes byte-for-byte, and resets the self-checks. Editing the worksheet invalidates an old confirmation and the starter notice. Saving remains the existing server-authorised plan action. Reading a lesson, applying a brief or checking a worksheet does not establish competence, certification or official impact.

The saved-plan review is derived only from a successful currently authorised canonical plan read. It names the exact saved object and revision and describes known public preparation fields, with follow-up actions that open existing screens. Directory entries, unsaved drafts and save receipts cannot create a review source. Dirty edits, failed/currently refused reads, identity or workspace changes, New, and receipt-only saves clear the source. Edit then undo requires another deliberate canonical read. Delayed responses cannot restore a source after the relevant read or draft generation changes. Private advice and impact-reference fields, presence and counts are not inspected. The review records no approval or completion decision.

The cost screen distinguishes **Amounts recorded**, **Contains an unknown amount** and **Not recorded** for each entered category and offer. An explicit zero is recorded; an omitted category is neither zero nor not applicable. A blank amount remains unknown even for zero quantity. The existing exact decimal calculation, closed request body and backend arithmetic are unchanged. Results describe supplied entered lines and do not claim full ownership costs, verified prices or supplier preference. Their visible source distinguishes unsaved inputs, receipt-only local inputs and an exact opened saved revision. A change in source revision invalidates an older result even when the input values are equal.

The separate public entrypoint demonstrates five steps: choose a first use, build team skills, try a manual task, compare invented tools and prepare neutral supplier questions. It reuses the actual public lesson, comparison, procurement and practice components with visibly fictional organisations, tools and quote amounts. A permanent label explains local edits, no persistence, no sign-in and no AI connection. The adapter accepts only two exact bundled public-guidance reads; all mutations, authentication, unknown/private paths and network fallback are refused. Reload or explicit reset discards the local worksheet and lesson answer state. There are no fake saved heads, receipts, approvals or second-person actions.

## Contract and persistence

This is an interface increment on domain 1.25.0 (261 implemented operations), platform 1.10.0 (52 operations) and schema 40. The dedicated public `GET /ai-walkthrough.html` is a fixed static FileResponse, excluded from the domain/platform operation inventories; it does not authenticate, resolve a tenant or read a database. The production build has separate authenticated-app and walkthrough entries. The existing deployment copies both static entries without a new paid resource or origin.

The normal plan retains its existing five-field manual worksheet (`template_id`, `brief`, `draft`, `review_notes`, `checked_steps`), public planning inputs and ordinary immutable save/replay transaction. Starter preview, canonical read marker, review snapshot, local review view/hide state and navigation, coverage rows, calculation results and walkthrough edits are transient interface state. The [development appendage](nonprofit-ai/v1.0/DEVELOPMENT-0.35.md) records their exact boundaries. All registered migrations 0001–0040 remain unchanged; no new migration or dictionary column is introduced.

Plan reading and management retain their existing current membership and scoped capabilities. Management hints enable editing; the server remains authoritative on every actual save/read/retry. The public walkthrough's local edit control is not a tenant grant and cannot call that server flow. First-organisation custody/bootstrap still requires the existing three distinct people; the tour supplies no onboarding shortcut.

The static response uses `connect-src 'none'`, no-store caching, no-sniff and restrictive script/frame/form policies. Its JavaScript never creates, reads or uses cookies or browser persistence. A browser that already has same-origin application cookies may automatically attach those cookies to a static HTTP request; the fresh anonymous qualification context had none. This limitation does not imply a separate paid cookie-free origin.

## Limits

The frozen 0.35 interface has two concrete current limitations. Editing only the organisation brief on a fresh plan, while its plan fields remain empty, can be silently replaced when opening a saved plan: the existing dirty check omits that profile-only change. A private actual React/Chrome reproduction uses mocked requests and confirms local unsaved input loss; it does not show a server write or stored-plan loss. A narrowly reviewed fresh-profile baseline/confirmation fix and actual API/browser checks are prepared privately for 0.36, with successful synthetic evidence; they are not integrated or qualified in 0.35.

The current practice copy says historical wording is unavailable when its saved edition is Unknown or Stale. Edition compatibility does not establish exact archive availability: the existing saved-guidance view separately reports retained or unavailable content for an exact saved revision. A private conditional wording correction for 0.36 directs readers to that view only when a saved revision exists, preserving unknown/stale labels and all current-task guards. It remains unregistered and requires actual qualification. These are an interface preservation defect and a copy limitation, not a new permission or archive-policy change.

Capacity building remains self-paced preparation and manual practice. Learning programmes, independent competency assessment, provider-generated task runs, supplier onboarding, validated offers, procurement decisions, external adviser engagement and operated private retention/removal remain separate target work. The existing 0.34 privacy correction and retention limitations are unchanged. Entered-line arithmetic is not full TCO or official impact arithmetic. No AI/provider call, external message, purchase, payment, certification, automatic lesson completion or financial commitment is introduced.

The proposed public demo path is `/ai-walkthrough.html`; no hosted 0.35 link is claimed here. A usable hosted link must be checked after the exact candidate passes the remaining gates and the actual deployed commit/schema/health are observed. A private read-only post-merge verifier is prepared and reviewed as a proposal; it has not contacted hosting or executed a deployed-browser scope. The authenticated application remains the real product.

**Update, 6 October 2026:** both limitations above are fixed in [build 0.36](RELEASE-0.36-procurement-preview.md). This note is otherwise unchanged.

Earlier private prototype checks establish only prototype behaviour. Any product correction must retain the failed or superseded reports and rebind final qualification to the final served bytes.
