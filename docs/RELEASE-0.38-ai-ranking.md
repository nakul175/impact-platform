# Build 0.38 rank opportunities with the organisation's weights (US-MP-03)

9 October 2026 · Local candidate on branch `sprint-1/us-mp-03` (from `sprint-1/fr-ai-001`), committed locally only (not pushed, merged or deployed) · build 0.38.0 · domain API 1.27.0 · platform API 1.11.0 (the initial-access manifest gains the FINANCE role) · schema 42 (migration 0042) · 267 implemented domain operations (264 + 3).

The AI enablement area can now rank the opportunities that fit an organisation's brief by four scores — impact, effort, cost and readiness — weighted by the organisation's own priorities. Impact, effort and cost are versioned editorial scores; readiness is computed from the capacity gaps the existing assessment already finds. The organisation saves its weights once (a preference, not an approval); every ranking states which weights and which weights revision produced it. Nothing here is accepted: US-MP-03 is "In review" in the backlog, hosted CI has not run, and the editorial scores are a first draft that Imprana editorial and an advisor have not reviewed yet.

## Delivered behaviour

1. **Scores (1 to 5).** `apps/api/impact_api/ai_opportunity_scores.py` (new, `SCORE_VERSION` `imprana-opportunity-scores-2026-10-09.1`, `STATUS` `EDITORIAL_DRAFT_PENDING_ADVISOR_REVIEW`) holds impact (5 = largest benefit), effort (5 = most staff effort) and cost (5 = most spending) for the eight editorial use cases. It is outside `catalog()`, so the archived guidance of saved plans (`ai_content_archives.py`, `ai_content_schema_v1.json`) is unchanged. Readiness = 5 minus one for each of the use case's own capacity gaps from `assess()` (no AI practice for an AI example; data organisation below what the example needs), one for the small-team gap and, for AI-assisted examples, one for the sensitive-data review gap (never below 1). The four organisation-wide gap texts of `assess()` became named constants; its output is byte-for-byte the same.
2. **Weighted total.** Each score becomes 0–100 points with higher meaning better: impact and readiness `(score − 1) × 25`, effort and cost reversed `(5 − score) × 25`. Total = Σ weight × points / 100, between 0.00 and 100.00, computed with integers and `Decimal` (no floating point; `domain.display` rounds half-up once and the code proves no rounding was needed) and returned as a two-place decimal string. Opportunities are listed by descending total; equal totals are ordered by use-case ID; ranks are positions 1..n.
3. **Not ranked.** A use case without all three editorial scores is never in the ranked list; it is returned under `unranked` with the missing criteria and shown as "Not ranked: scores incomplete". The shipped table scores all eight use cases.
4. **Weights.** `{impact, effort, cost, readiness}`, whole numbers 0–100 that add up to exactly 100. Until an organisation saves weights, the defaults 25/25/25/25 apply, `source` is `DEFAULT` and there is no revision (a read never creates one). `PUT …/ranking-weights` stores the next immutable revision of the tenant's single `AIRankingWeights` object with `expected_revision` (null for the first save), operation ID, the tenant write lock, audit event `ai_ranking_weights.changed`, outbox intent and receipt in one transaction. It needs `ai.enablement.manage`, no independent review and no fresh sign-in.
5. **Ranking.** `POST …/ranking` with `{profile}` (the same closed six-field brief as the assessment) returns the ranked items (rank, the four scores, the weighted total, the readiness gaps), the unranked items, the weights used, `weights_source` and `weights_revision_id`, the score version and status. It is a read: nothing is stored or audited, and the assessment's own order is unchanged.
6. **Web** (`apps/web/src/AIRanking.tsx`, new; `AIEnablement.tsx`, `main.tsx`, `ai-enablement.css`). A "Rank opportunities" panel below the brief: the weights in force, a "Rank opportunities" button (enabled once the brief has a goal), a table of rank, opportunity, the four scores ("n of 5", with "higher/lower is better" in the headers) and the weighted total, the weights revision used, the editorial-draft status, and the "Not ranked: scores incomplete" section. Holders of `ai.enablement.manage` get the weights editor: four labelled number inputs, the running total ("Total: 120 of 100 (must be exactly 100)"), a client-side refusal of a wrong total or a non-whole number with `role="alert"` and `aria-invalid` (nothing is sent), "Ranking weights saved." as `role="status"`, the on-screen ranking recalculated after a save, and on 409 an alert that keeps the message and reloads the weights in force. A ranking that cites a newer revision reloads the weights shown. Unreadable saved weights show an alert, disable ranking and give managers the editor seeded with the defaults, saving against the unreadable revision (a ranking refused with `AI_RANKING_WEIGHTS_UNREADABLE` reloads the weights to show this). The table scrolls inside a focusable region on narrow screens.

## Limits

- **The editorial scores are a draft by the implementing engineer, not Imprana editorial content.** No advisor has reviewed them; `STATUS` and every ranking say so. Changing a value is a code change with a new `SCORE_VERSION`; there is no editorial screen.
- **The Operations Head reads through a new FINANCE bundle that existing tenants must still adopt.** New tenants can choose FINANCE at initial access; an existing tenant needs the reviewed access upgrade to the profile registered by 0042 before it has a managed FINANCE role template (its administrators could already grant the three read capabilities individually). FINANCE holding `ai.enablement.read` also reads the rest of AI enablement (catalogue, saved plans, policy, advice it takes part in), because capabilities are not per screen.
- A ranking is computed per request and not stored; the response names the weights and revision, but no record of who ranked what is kept. With the defaults there is no revision to name: `weights_revision_id` is null and `weights_source` is `DEFAULT`.
- There is no history route for weights; earlier revisions exist in `object_revision` and the audit log only.
- Readiness uses the self-reported brief and the gap rules of `assess()`; it is not verified capability. Totals are planning aids, never official results (rule 5).
- Weights apply to the whole organisation; there are no per-programme or per-person weights.

## Deviations from the story card

1. "The response names the weights revision used" with default weights: no revision exists until weights are saved, so the response names `DEFAULT` with the weights and a null revision; once saved (including 25/25/25/25) it names the revision.
2. "Additions to `test_ai_enablement_catalog.py`": that file is unchanged (it still passes). The "existing order still holds" checks are in `test_ai_ranking.py` (over HTTP, before and after saving weights) and `test_ai_ranking_unit.py`.
3. "An opportunity missing its cost score": the shipped table is complete, so the scenario runs the real ranking service on the real database with a replaced score table (in-process, as `test_ai_policy.py` drives the advisory gate), plus database-free tests; the browser check renders such a server response through a modified real response.
4. 0042 adds no table, grant or policy; the native `test_ai_ranking_live.py` (added after review) checks the per-tenant singleton and the fence on the application role, and the database checks of 0042 also run in `test_ai_ranking.py` on PGlite and native.
5. Stricter than the card: the client refuses a wrong total before sending; whole numbers given as `25.0` are refused by the server.
6. The review asked for the editor on a 503 `AI_RANKING_WEIGHTS_UNREADABLE`. A replacement must name the revision in force, which a 503 cannot carry, so `GET` reports unreadable weights as `source` `UNREADABLE` with their revision instead of answering 503; ranking still answers 503 (and the client then reloads the weights). `test_ai_policy_unit.py::test_migration_registers_the_generated_profile` now pins 0041's own profile hash instead of the current profile (registered by 0042; `test_access_upgrade_unit.py` checks that the current profile is registered exactly once).
