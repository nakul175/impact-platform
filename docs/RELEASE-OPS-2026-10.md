# Operations hardening (October 2026) — backups, restore drill, alerts, metrics, owner console

Operations slice on top of build 0.24.0 (branch `integration/0.21-0.24`): no build-version bump, schema 26 (no migration), domain API 1.14.0 unchanged, **platform API 1.5.0 → 1.6.0** (one operator-only read, `GET /v1/platform/metrics`). The ledger is not regenerated here; the integrator applies the proposals in "Integration notes". Nothing in this slice makes the platform production-ready: it is a single-server regime with no off-server copy of the nightly sets.

## Delivered

- **Complete backup sets** (`deploy/backup.sh`, `backup` service). Nightly at `BACKUP_HOUR_UTC` (21:00 UTC), one set per day in `/backups/daily/YYYYMMDD/`: `impact.dump` and `keycloak.dump` (`pg_dump -Fc`), `globals.sql` (`pg_dumpall --roles-only --no-role-passwords`: the roles and memberships a restore onto a fresh cluster needs; no password), `objects.tar` (the `objects` volume, mounted read-only into the backup container, taken after the dumps so every object the dumps reference is present; `.incoming-*` temporaries excluded), `SHA256SUMS` and `manifest.json` (format, set, times, commit, schema version, PostgreSQL version, each file's size and SHA-256, object count, the checks passed). The set is written in a hidden `.partial-*` directory, verified (`pg_restore --list` of both dumps, a full read of the tar, `sha256sum --check --strict`) and only then renamed into place; a same-day `--now` set replaces the earlier one only once complete. Sunday's set is hard-linked into `/backups/weekly/`; 7 daily and 4 weekly sets are kept (well inside VF-DR-003's 35-day default); flat dumps of the earlier layout age out on the same horizons. **Disk guard:** an attempt is refused (status `refused`, reason `DISK_LOW`) when the backup file system has less free space than max(`BACKUP_MIN_FREE_MB`, default 1024, twice the newest set). Every attempt writes `<impact home>/ops/backup-status.json` (result, reason, set, bytes, free and required MB, the set lists and the last success); it contains no secret.
- **On-server restore drill** (`deploy/restore-drill.sh`, run weekly by `impact-restore-drill.timer`, Sunday 23:15 UTC ±15 min, or by hand with an optional `daily|weekly/YYYYMMDD`). Compose profile `drill`: `drill-db` (postgres:17, anonymous volume, internal network `drill`, the backup volume read-only, a password generated per drill and passed only through the environment) and `drill-check` (the application image, same network, read-only backups). `deploy/drill_restore.sh` (inside `drill-db`) picks the newest complete set, checks `SHA256SUMS`, applies `globals.sql` without the bootstrap superuser's lines, creates both databases and restores both dumps with `--exit-on-error`, timing each step. `deploy/restore_check.py` then checks: every tar member is `<tenant>/<xx>/<sha256>` and hashes to its name; every restored `impact.file_blob` row has its object with the recorded digest and size; `scripts/migrate.py` as `impact_migrator` (one-time password in the throwaway cluster) finds every ledgered checksum equal to the image's files and reaches the image's schema; every `impact` table is owned by `impact_owner`; every forced-RLS table has a policy (and at least 50 are forced); `impact_app` sees no `object_registry` row without a tenant; the identity-provider database holds the `impact` realm. The containers and their volume are removed (also on failure). `<impact home>/ops/restore-drill.json` records outcome, error class, set, set creation time, **backup age at restore**, **end-to-end duration** (the measured recovery time of the databases at this size), per-step seconds, set bytes, restored table and row counts, object and blob counts and the migration result.
- **Alert check** (`deploy/ops-check.sh` + `deploy/ops_alerts.py`, `impact-ops-check.timer` every 5 minutes, and after each deployment and drill). Collects container states, backup and drill status, free space of `/` and Docker's data root, and `python -m impact_api.ops_metrics` run inside the API container on its own platform connection; writes `<impact home>/ops/ops-status.json` and merges `operations` and `alerts` into `deploy-status.json` (public and private copies; `update.sh` keeps them across deployments). Closed codes: `BACKUP_MISSING`, `BACKUP_STALE` (>26 h), `BACKUP_FAILED`, `BACKUP_REFUSED_DISK_LOW`, `DISK_LOW` (<10 % or <2 GB warning, <5 % or <1 GB critical), `CONTAINER_UNHEALTHY` (any of postgres, keycloak, api, worker, mailsink, caddy, backup absent, not running or unhealthy), `WORKER_STALE` (no RUNNING heartbeat within 120 s), `DELIVERIES_DEAD`, `QUEUE_BACKLOG` (>200), `SCHEMA_MISMATCH`, `OPS_SUMMARY_UNAVAILABLE`, `RESTORE_DRILL_FAILED`, `RESTORE_DRILL_STALE` (>8 days). Values of `secrets.env` are scrubbed defensively; nothing is sent off the server.
- **Operator metrics** (`apps/api/impact_api/ops_metrics.py`, `metrics_contracts.py`): `GET /v1/platform/metrics`, platform operators only (others 404, anonymous 401). In-process request counters by route family (tenant, platform, auth, health, client) and status class with a cumulative latency histogram (0.05–5 s buckets; reset on restart; no path, tenant or identity recorded), worker heartbeats (total, running, fresh, stale, newest beat age by the database clock, dead and failure totals), DEAD and held deliveries via `operator_delivery_attention` (capped at 50, `capped` flag), unsent deliveries and unfinished jobs summed over at most 200 tenants under control-plane custody via `tenant_work_impact`, tenants by lifecycle state, object-store disk space, and the last `ops-status.json` (`IMPACT_OPS_STATUS_FILE`, new optional setting `ops_status_file`, absolute path). The schema version is read on the application connection: the platform role cannot read `schema_migration`. The middleware observes every response.
- **Logs**: every Compose service (including the drill's) keeps json-file 10 MB × 5; `update.sh` installs `/etc/logrotate.d/impact` (deploy, ops and drill logs weekly, 8 kept, compressed, `maxsize 20M`; `admin-actions.log` monthly, 24 kept; `copytruncate`; `su root root` in each stanza, because Ubuntu's `/var/log` is group-writable `root:syslog` and logrotate otherwise skips those logs as "insecure permissions" and exits 1 — the first container-stack run failed on exactly that).
- **Host units**: `update.sh` renders and installs `impact-ops-check.{service,timer}` and `impact-restore-drill.{service,timer}` (rewritten only when changed, `daemon-reload`, `enable --now`), skipped without systemd or with `IMPACT_HOST_UNITS=0`. Compose gains `IMPACT_OPS_DIR` (a 0755 directory of status files only), mounted read-write into `backup` and read-only into `api`.
- **Owner console**: `deploy/list-users.sh` (e-mail, name and a plain status per account: not signed in yet, no authenticator, locked, switched off, active; from the new `keycloak_admin.py list`, which also reads the brute-force state); `deploy/reset-user.sh <email> [--totp]` (new one-time password printed in a box to a terminal only, refuses pipes, lifts a lockout, logs who and when to `admin-actions.log`, never the password); `deploy/first-admin.sh` prints a box with address, username and (while pending) the temporary password. DEPLOYMENT-GUIDE section 4 gains an "Everyday tasks for the owner" table; section 6 is rewritten (sets, drill, RPO/RTO, alert table, manual restore including objects and roles).
- **Smoke check**: the status file's secret-field test now matches whole words (`db_password`, `apiKey`, `IMPACT_COOKIE_SECRET`), not substrings — the service name `keycloak` contains `key`; the check reports the alert codes.
- **CI `container-stack`** now runs on `bash -eo pipefail` (GitHub's default `bash -e` did not fail a step whose check was piped into `tee`, so earlier smoke failures could pass unnoticed) and adds: `list-users.sh` and `reset-user.sh` (pipe refused, absent account refused, no password in state or logs); a synthetic content-addressed object in the evidence volume; a backup set taken, its status, manifest and checksums verified and its dump restored; the restore drill with every check passing and nothing left behind; the alert check with no critical alert, the status file carrying operations and alerts, the timers enabled and the logrotate file parsed; an injected failure (worker stopped) alerted by the next check (`CONTAINER_UNHEALTHY`, `WORKER_STALE`) and cleared after restart. The drill and alert figures are published as check-run notices.

## Recovery objectives (as delivered, not as agreed)

- Data damaged, server intact: recovery point up to 24 h plus the time a failing nightly run goes unnoticed (alerts after 26 h); recovery time = the drill's measured duration at the current size, plus swap-in and redeployment, plus human reaction time.
- Droplet lost: only DigitalOcean's droplet backups remain (daily or weekly, by the owner's plan); the nightly sets are lost with the droplet. Recovery time is DigitalOcean's restore plus one deployment run; not measured.
- VF-DR-001's target (RPO ≤ 15 min, RTO ≤ 4 h, in-region, files and governance state) is **not met**: there is no continuous archiving and no off-server copy. Off-server copies need an owner decision on a storage provider (e.g. a Spaces bucket, a paid add-on).

## Limits

- Single server: backups, the drill and the live data share one disk and one root account; a compromised root or a lost droplet defeats every layer except DigitalOcean's backups. No immutability or protection against alteration or credential compromise (VF-DR-003's protection clause unmet); no encryption of sets at rest beyond the droplet's disk.
- `objects.tar` is consistent with the dumps only in one direction (every referenced object present; an object written after the dumps may also be present). A tar of a large evidence volume is a full copy every night (no incremental); the disk guard is the only control.
- The drill restores into the same server's Docker; memory and disk pressure on a 4 GB droplet grow with the data. It does not replay deletions or revocations before reopening (TH27), does not compare row counts against the source at backup time, and does not start the application on the restored copy.
- Alerts go only to the status page: no paging, e-mail or history; someone must look. Request metrics are per process and in memory. The host check reads containers through Docker and the application through `docker compose exec`; if Docker itself is down, the timer's failure is visible only in `/var/log/impact-ops.log` and a stale `checked_at`.
- `QUEUE_BACKLOG` and DEAD counts cover only tenants under control-plane custody (`tenant_onboarding`), at most 200; DEAD counting is capped at 50.
- The worker's heartbeat staleness window (120 s) differs from the Workers panel's (60 s): the alert is deliberately less eager.
- Nothing was run against the staging server from here (rule: changes reach it only when merged).
