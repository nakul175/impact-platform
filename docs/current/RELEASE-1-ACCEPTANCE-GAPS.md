# Release 1 acceptance gaps

Build 0.25.0, assessed 1 October 2026 (updated for builds 0.26.0 and 0.27.0: see the update paragraphs in §1, §3 and §4; the ledger at build 0.27.0 is 113 PARTIAL, 194 PENDING, 0 accepted) against the Release 1 exit conditions of the [delivery plan](../DELIVERY-PLAN.md) §2 (scope decision SD-01), the [release acceptance record](RELEASE-ACCEPTANCE.md) and the [completion ledger](../COMPLETION-LEDGER.md) (generated by `make ledger`: 307 requirements, **103 PARTIAL, 204 PENDING, 0 accepted**). This is a list of what blocks acceptance, not a plan. Items marked *verified in code* were checked in the source on this date; the rest come from the ledger and release notes.

The exit conditions are: every P0 requirement in the Release 1 definition at PARTIAL with executed evidence or explicitly deferred by a recorded scope decision; G03 executed natively with separate login roles; G04 executed against a live provider with MFA; a staging deployment operated with backups, monitoring and a restore drill; UAT with representative users and named approvers; security-assessment items on the delivered surface remediated.

## 1. Blocks UAT on the hosted service (highest impact)

These stop a tenant created through the proper onboarding steps on staging from doing what Release 1 promises ("one organisation can run its real monitoring, evaluation and learning cycle end to end on hosted infrastructure with real logins"). Until they are fixed, the [UAT pack](UAT-PACK.md) runs the measurement cycle on a local fixture workspace (Track L) only.

**Update, build 0.26.0 (v0.26a usable staging, [RELEASE-0.26a.md](../RELEASE-0.26a.md)):** A1–A4 are resolved in code and tests — governed reference-data commands with a one-click standard set (A1), the generated profile `initial-access-v2` whose ceiling also covers the purpose-bound capabilities (A2; tenants that already applied v1 keep their ceiling, no reviewed widening yet), a second platform operator nominated and accepted in the web application (A3), and reviewed purpose-bound grants (A4). No independence rule was relaxed: a first organisation still needs three different people (DEPLOYMENT-GUIDE §4.1). A5 is unchanged. The rows below keep the original assessment.

**Update, build 0.27.0 ([RELEASE-0.27.md](../RELEASE-0.27.md)):** A5 is resolved in code and tests ([RELEASE-0.27-imports.md](../RELEASE-0.27-imports.md)): an imported value's source key is `<unit key>/<indicator id>/<period id>`, so an approved plan names it in advance; imported approved values count as planned at close; unplanned imported values still block close, and a reviewed plan amendment naming the exact key clears it (both tested in `test_import.py`). The first organisation can now import into a planned indicator and close the period. Two related corrections at integration: a late value can no longer enter a programme's locked period when the tenant has a second reporting calendar (`test_import.py::test_a_locked_period_refuses_late_values_when_another_calendar_overlaps_it`), and the onboarding profile gained 16 capabilities, so an organisation that applied initial access before this build cannot grant them until a reviewed ceiling widening exists (designed in RELEASE-0.27-operators.md). The A5 row below keeps the original assessment, as the A1–A4 rows were kept.
