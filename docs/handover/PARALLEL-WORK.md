# Parallel work: several builders and one integrator

How builds 0.24.0 to 0.27.0 were produced: several engineers (human or AI agents) each build one bounded slice on its own branch from the current `main`, and one integrator merges all slices into a single integration branch, renumbers migrations, regenerates generated files, bumps versions once, runs every suite and opens one pull request. The method is model-agnostic; nothing here depends on a particular assistant. The binding engineering rules are in [AGENTS.md](../../AGENTS.md) and [CLAUDE.md](../../CLAUDE.md) (the full engineering brief, despite its file name). Ready-to-run slices are in [BACKLOG.md](BACKLOG.md).

## 1. Builder rules (one slice, one branch)

1. **Scope and time box.** One slice from the backlog, branched from the current `main` head (`release/0.28-<topic>`, `qa/<yyyy-mm>-<topic>`, `ux/0.28-<topic>`, `docs/<yyyy-mm>-<topic>`). Agree a time box (a working session of a few hours); cut scope rather than overrun, and list what was cut under "Not delivered".
2. **Migration placeholder.** A slice that needs a migration names it **`0033_<topic>.sql`** (the next free number after build 0.27.0, whose last migration is 0032). Every builder uses 0033; the integrator renumbers in merge order by renaming the file only, so never write the migration number inside the SQL in a way that matters, and never edit an existing migration (0001–0032). Follow CLAUDE.md §6 (one `BEGIN;`/`SET LOCAL ROLE impact_owner;`/`COMMIT;`, additive only, forced RLS and `tenant_fence` on every tenant table, grants to the narrowest role) and add the file's register row and SQL section to `docs/current/CURRENT-DATA-DICTIONARY.md` under its placeholder number (the integrator rebuilds them).
3. **No version bumps.** Do not change `VERSION.json`, `apps/web/package.json` or its lock. New routes may carry the next minor (for example `1.18.0`) as `x-contract-version`; the integrator confirms the final value.
4. **No shared-document edits.** Do not edit `docs/IMPLEMENTATION.md`, `QUALIFICATION.md`, `NEXT-DELIVERY.md`, `DELIVERY-PLAN.md`, `docs/current/CHANGELOG.md`, `CURRENT-API-INVENTORY.md`, the CSV registers (`SCREEN-COVERAGE.csv`, `EXECUTION-REGISTER.csv`, `TRACEABILITY.csv`), `docs/COMPLETION-LEDGER.*`, `README.md`, `DOCUMENTATION-INDEX.md`, `CLAUDE.md`, `AGENTS.md` or `docs/HANDOVER.md`. Write the lines you would add there into your release note's "Integration notes" instead.
5. **Generated files.** Regenerate the contracts in your branch (`python scripts/build_contracts.py && python scripts/export_implemented_api.py`) so that your own CI passes; if you add a capability, also run `python scripts/build_access_profile.py` (the onboarding profile's hash then changes — say so). Expect these files to conflict at integration; the integrator regenerates them.
6. **Release note.** `docs/RELEASE-0.28-<topic>.md` with: a first line of build/schema/API/ledger effects ("no version bump; schema +1 (placeholder 0033); domain API +n operations; ledger proposals below"), **Delivered**, **Contract and persistence**, **Limits**, **Reproduction**, **Not delivered** (if anything was cut) and **Integration notes**: proposed requirement movements with the exact test names that justify them, the lines for each shared document, the files touched (especially shared ones such as `main.py`, `service.py`, `worker.py`, `main.tsx`, `styles.css`, `scripts/run.py`, the Makefile, the CI workflow), and risks for the integrator. Report any defect you find outside your ownership there; do not leave it only in a test comment.
7. **Tests: focused only.** The development machine has 2 CPUs and 7 GB. Run only your own files (`IMPACT_PORT=<unique> .venv/bin/python scripts/run.py test --pytest-path qualification/test_<area>.py`), your new unit file and, if you changed the UI, your browser group (`scripts/run.py <group>-browser`). Never run the full PGlite, native or browser suites while other builders work. Use a unique `IMPACT_PORT` (port 8000 is everyone's default). A focused run overwrites `docs/evidence/`: restore it before committing (`git checkout -- docs/evidence/ && git clean -f docs/evidence/`).
8. **Pushes.** One push, plus at most two fix pushes. Each push runs the four CI jobs twice (push and pull_request) and the GitHub Actions budget has run out twice.
9. **Never merge.** Open a pull request to `main` for the record; the integrator merges it into the integration branch. Never weaken a test, never relax an independence rule, never add a synthetic or login-less approver, never commit credentials, `.local/` or personal data.

## 2. Integrator checklist

1. **Collect.** Fetch every branch (`git fetch origin 'refs/heads/*:refs/remotes/origin/*'`), list the open pull requests (`gh api 'repos/nakul175/impact-platform/pulls?state=open'`), read each release note's Integration notes and note which pull requests never had a complete CI run: treat those as unverified.
2. **Order.** Quality and infrastructure first, then features, user-interface-heavy slices last, documentation-only last of all. Branch `integration/<build>` from `origin/main` and merge each with `git merge --no-ff` (a real merge commit, so GitHub marks the component pull requests merged when the integration pull request is merged with a merge commit). Commit messages end with the attribution lines your tooling requires.
3. **Conflicts.** Resolve additive registries as unions: `service.py` routes and actions, `main.py` explicit routes, `scripts/bootstrap.py` capability lists, `scripts/build_contracts.py` registrations (with `augment_reference` **last**), the `main.tsx` navigation and its `areaCapabilities` gate, `styles.css`, the Makefile (`unit` file list, `browser` groups), `scripts/run.py` modes, the CI workflow, `worker.py` job classes, `deploy/` scripts and `compose.yaml`. For generated files (`packages/contracts/*`, `docs/API-INVENTORY.md`, `bootstrap_profile.json`) take either side and regenerate.
4. **Migrations.** Rename each slice's `0033_<topic>.sql` to the next contiguous number in merge order (file rename only — never edit migration bytes); fix references in code comments, tests and docs; rebuild the data dictionary: one header paragraph for the build, register rows with recomputed SHA-256, and the SQL sections copied from the renamed files. If two migrations change the same CHECK, make sure they compose (the `pg_get_constraintdef`/`regexp_replace` DO-block pattern of 0006–0012).
5. **Regenerate and bump.** `python scripts/build_contracts.py && python scripts/export_implemented_api.py`; `python scripts/build_access_profile.py` (record the `PROFILE_HASH` consequence: pending initial-access requests must be re-proposed; tenants that already applied keep their ceiling); bump `VERSION.json` (build; domain and platform API to the highest minor any slice declared, or the next minor if they disagree), `apps/web/package.json` and its lock; regenerate the contracts again.
6. **Integration checks.** New capability families need an entry in `areaCapabilities` (`apps/web/src/main.tsx`) or their area stays hidden; new pure unit files belong in the Makefile `unit` target; set `IMPACT_UPGRADE_BASELINE` in the CI native job to the schema deployed on staging; grep `tools/browser/` (including `training-video.mjs`) for selectors a UI slice changed.
7. **Verify locally, in this order:** `make lint`, `make unit`, `npm run build --prefix apps/web`, the full native run on a private PostgreSQL 16 UTF8 cluster (`initdb -E UTF8`; empty `impact_test_<suffix>`; `IMPACT_UPGRADE_BASELINE=<deployed schema> make native`, which includes the restart check, the restore drill and the populated upgrade check), every browser group (`make browser`, or one `scripts/run.py <group>-browser` at a time with a unique `IMPACT_PORT`), then the full PGlite gate (`make test`) and `make reference` on the final tree. Fix every failure at its root; never weaken a test. Re-run any full suite whose code changed after it ran. Publish evidence files only from clean full runs; restore them after focused runs.
8. **Shared documents** from each slice's Integration notes: an umbrella release note `docs/RELEASE-<build>.md` (what each slice delivered, migration renumbering, versions, counts, limits, owner-facing notes, which slices had no CI), `IMPLEMENTATION.md`, `QUALIFICATION.md` (real counts only), `NEXT-DELIVERY.md`, `DELIVERY-PLAN.md`, `CHANGELOG.md`, `CURRENT-API-INVENTORY.md`, the dictionary header, the three CSV registers, the ledger groups in `scripts/build_completion_ledger.py` then `make ledger` (promote only on named passing tests; never "accepted"), `README.md`, `DOCUMENTATION-INDEX.md`, `CLAUDE.md`, `AGENTS.md` (its rules section is copied verbatim from CLAUDE.md §4) and `docs/HANDOVER.md`.
9. **One pull request** to `main`, then poll its check runs (`gh api repos/nakul175/impact-platform/commits/<sha>/check-runs`). If every job fails with zero steps, that is the Actions spending limit, not the code: stop and tell the owner. If jobs run and fail, read the annotations (`gh api repos/nakul175/impact-platform/check-runs/<id>/annotations`), fix and push (at most three fix pushes). **Never merge into `main` without all four jobs green and the owner's confirmation**: `main` deploys itself to the staging server within about three minutes, and `container-stack` is the only check of the deployment path.

## 3. Lessons from the parallel builds (1–3 October 2026)

- **Session limits.** Ten simultaneous builders hit the AI account's session limit within about ten minutes on 2–3 October 2026; four or five at a time worked well on 1 October.
- **GitHub Actions budget.** Each push runs four jobs twice (push and pull_request); one night of ten builders used roughly 80 job runs and exhausted the spending limit twice — jobs then fail instantly with zero steps, and four of the eleven slices of build 0.27.0 (#68, #69, #74, #77) never had CI on their final heads. Push once per builder, at most two fix pushes, and verify locally first.
- **Machine.** The development machine has 2 CPUs and 7 GB RAM: builders run only their focused tests with a unique `IMPACT_PORT`; full PGlite, native, browser and container runs happen once, at integration and in CI.
- **Conventions.** Builders never bump versions, never edit shared documents and all name their migration with the same placeholder number; the integrator renumbers contiguously, recomputes the SHA-256 rows of the data dictionary, regenerates the contracts and the access profile, bumps versions once and updates the shared documents from each release note's Integration notes.
- **Merge order and merge commits.** Quality and infrastructure first, then features; real merge commits (`--no-ff`) so GitHub marks the component pull requests merged when the integration pull request is merged with a merge commit.
- **Worktrees, scratch, ports.** Agents need the repository as the working directory to create worktrees; keep helper scripts in a unique scratch folder per agent (shared scratch files were overwritten); browser checks contend for port 8000 unless `IMPACT_PORT` is set.
- **Deployment.** `main` deploys itself to the staging droplet within about three minutes of a merge: never merge without all four CI jobs green (`container-stack` is the only check of the deployment path and cannot run in the development sandbox).
- **Order-dependent tests (build 0.27.0).** A builder's focused run with files given in a non-alphabetical order hid an order dependence that the alphabetical full suite exposed (#74's tests picked "the latest sweep" by a timestamp another test had moved hours ahead). In tests, identify the record a step created by its identity, never as "the newest by some timestamp"; the integrator's full run is the first run in suite order.
- **Defects outside the slice.** #68 found a period-lock defect outside its ownership and reported it in its Integration notes instead of fixing it; the integrator fixed it with a regression test. That is the right split: report precisely, let the integrator fix with a test.
- **Tools that drive the UI.** A UI slice that turns a form into a dialog breaks every script that drives that form, not only the browser checks (the training-video generator of #67 needed the same change as `tenant-check.mjs`). Grep `tools/browser/` for the changed selectors.
- **Profile hash.** Every slice that adds a capability regenerates `bootstrap_profile.json`; after merging, regenerate once more and state the consequence for tenants on staging.
- **Several migrations in one build.** Rehearse the upgrade from the schema actually deployed (`IMPACT_UPGRADE_BASELINE`), not only from the previous migration.
- **Makefile lists.** A note saying "`make unit` gains n tests" is not the same as adding the file to the `unit` target; check the target.
