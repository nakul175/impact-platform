# Imprana Commons QA v1.3 reconciliation plan

Status: proposed follow-up to the documentation audit of 11 October 2026. Source application `8a1e405f0086033dfb25ad834689a08bfe9f1eea`; audited documentation baseline `b01a628e9a5463c92609fc7c7221fff82fd1feb2`. These steps do not change the release scope, original criteria, financial permissions or existing owner authority.

## 1. Publish one current testing edition

Create a source-bound current strategy and context that reconcile the old Markdown, Word and Excel editions with the actual selected application candidate and the current product plan. Preserve the original 825-case catalogue and its IDs as history; the 1,328 product acceptance scenarios are a different population and must not be added to, divided by or substituted for that case count. Link the relevant exact build records instead of repeating their results as current passes.

The edition needs its actual scope, authoritative versions, test environments, supported platforms, data permissions and retention, accountable quality/specialist roles, decision-dependent unknowns and existing readiness/completion/AI-assurance links. Recommend the roles in the adoption package; do not appoint a person or assert an approval on their behalf.

## 2. Bind the complete criteria population

Export the selected PM criteria population independently of tests and coverage rows, preserving existing IDs, source scenario text, versions and documented aliases. Review the complete population, including unknown applicability and justified exclusions. Pin exact source bytes, count and the package-defined sorted ID/version hash in a scope snapshot. Record a real source-owner completeness review when it exists; an agent-authored export and checksum do not supply that approval.

Build the AC inventory separately. Map criteria to actual case versions and their original epic/story/task identities without creating a competing backlog. Keep all 779 existing task prerequisites intact. Existing source gaps remain visible: 37 missing scenario phases, seven supplemental assertion groups and 13 stories with proposed qualification duties. Clarifications supplement rather than replace source Gherkin.

## 3. Separate case design, links and immutable executions

Use the package's normalized AC, case, links-only traceability, immutable run and explicit coverage-selection schemas when adoption is authorised. Preserve the current execution register and every original failure/retry; any migration needs a reviewed compatibility record. Do not infer full build, artifact, configuration, fixture or reviewer identity from a legacy row that lacks it.

Bind real automated tests to actual code locators and case/version markers through reviewed changes. Unimplemented automation remains a planned binding. Do not label everything manual or copy fictional package results into live registers to obtain a structural pass. No execution row means derived NOT_RUN; a designed case is not an executed test.

## 4. Make applicable domain gates measurable

Reconcile the unit, integration/API, smoke, regression, browser/E2E, UAT and exploratory plans. Add source-bound risk, test-data and environment records, security/privacy and accessibility review obligations, representative performance/reliability/recovery protocols, and AI evaluation slices/corpus/prompt/model/fallback records where applicable. Keep thresholds provisional until actual authority and measurement design exist. Record populations, slices, uncertainty, repetitions and stop rules before a qualification claim.

Existing synthetic/component/PGlite evidence retains its narrow meaning. Native concurrency, real identity/provider behavior, manual accessibility/UAT and held-out AI quality need their own actual procedures and evidence; a documentation review cannot clear them.

## 5. Reconcile results, defects and exceptions

Keep execution, freshness, applicability, approval, readiness, delivery and learning as separate status dimensions. Version defect events instead of overwriting them; translate historical severity scales explicitly. Any severity decrease needs a reviewed rationale. Closure needs current passing evidence for the same failed case and the exact candidate, with first failures and retests retained.

Bound exceptions by scope, eligible unmet gate, compensating evidence, real authority, expiry and retest trigger. They cannot waive tenant isolation, current authority, natural-person independence, deterministic official arithmetic or immutable approved history. Use selected required mappings and the complete AC inventory for coverage. Show numerator, denominator and scope; absent or unknown populations cannot become 100%.

## 6. Verify existing repository enforcement

Retain the existing `docs/CODEOWNERS` and declared owner. Check actual target-branch ownership, owner permissions, required code-owner/fresh reviews, named trusted checks and bypass settings. Verify source-narrowing and validation-control changes remain blocked without required review using safe authorised PRs, or implement independently controlled canonical-source reconciliation. A CODEOWNERS file and local workflow text do not authenticate live enforcement. Record unverified state honestly.

The four existing qualification jobs and `checks` remain required under repository policy. Adopting a QA record gate or an always-run completion aggregator requires reviewed workflow changes and separately verified enforcement. No paid CI, protection change, main merge or deployment is authorised by this audit.

## 7. Qualify one bounded scope before broader rollout

Select an existing story or candidate whose dependencies and data/environment authority are available. Establish its case/oracle versions first, execute the affected checks, retain red and green evidence, obtain separate reviews and make an actual scoped decision. Expand mappings and records without silently narrowing the canonical release denominator. Use the package's Low-tier route for eligible small changes rather than creating a release dossier for every documentation edit.

Completion of this reconciliation is documentation/process adoption. Product acceptance and release readiness still require current observed evidence and the actual decision owner's separate approval.
